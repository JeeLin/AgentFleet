# 设备 / Agent 平台 —— 新仓库设计（v0.1 草案）

> 本文件**不以 REX 为基础**。REX 仅作为「踩过的坑」参考，其架构不继承。
> 产品设定已变，代码设计因此重新推导，而非改造。

---

## 1. 产品定义

**自托管的设备 / Agent 平台。** 把自己拥有的设备（服务器、PC、手机、树莓派）
注册为节点；在一个网页里管理全部节点，并可在节点上打开文件浏览与交互式终端；
Agent 会话跑在指定节点上。

- **第一版只做 self-host**，单用户。这是范围选择，不是能力妥协。
- **节点主动外联**，Hub 不需要任何到设备的入站访问。

### 1.1 非目标（显式）

异构设备张量并行推理 · 多用户 / RBAC / 团队 · 通用文件同步引擎 ·
会话 transcript 集中存储 · 带 DAG 的调度器 · 任何需要消息中间件的设计。

---

## 2. 术语（先钉死，避免 REX 式的命名污染）

| 词 | 含义 |
|---|---|
| **device / node** | 一台注册的设备及其上运行的服务进程 |
| **Agent** | **仅指 AI agent**。绝不用来指设备进程 |
| **Hub** | 自托管的服务端，用户自己跑 |
| **connector** | 节点上提供的一类能力（terminal / files / exec） |

REX 的教训：进程名叫 `rex-agent`、表名叫 `agents`，后来 AI agent 出现，
内部命名直接冲突。本仓库从第一版起就只允许 `device` / `node` 指设备。

---

## 3. 架构

```
浏览器 ──HTTPS──> Hub（自托管）
                   │
      ┌────────────┴────────────┐
      │  设备注册表（持久）      │
      │  连接注册表（内存）      │
      └────────────┬────────────┘
                   │  WS，由设备主动建立（无入站端口）
        ┌──────────┼──────────┐
     设备 A      设备 B      设备 C
```

### 3.1 三层

| 层 | 职责 | 是否自建 |
|---|---|---|
| **节点层** | 注册、身份、心跳、能力上报、在线状态 | 自建（无标准覆盖） |
| **执行层** | 本地 PTY、本地文件系统、进程执行 | 自建 |
| **会话层** | Agent 会话与恢复 | 用 **ACP**，不自建 |

> 设备管理层**必须自建**：MCP（工具/资源）、ACP（编辑器↔agent 会话）、
> A2A（agent↔agent 委托）三者都**不覆盖**设备/端点管理。

### 3.2 与 REX 的**刻意差异**（不是"轻一点"，是"不同"）

| # | REX 的做法 | 本仓库的做法 | 为什么 |
|---|---|---|---|
| 1 | `Environment` 同时是注册令牌、路由决策、资源分组的父实体 | **不设 Environment 层级**。可达性只是设备当前网络的**观测属性**（标签），不是实体 | REX 的"Hub 直连还是经节点"按网络决定，导致一个环境无法混放节点内外的资源 |
| 2 | 一张多态 `Resource` 表 + **65 处协议字符串分支**散落在 6,049 行共享层 | **没有通用 Resource 抽象**。设备能力是**独立的、有类型的**概念（terminal / files / exec），各自独立演进 | 多态资源层是"重"的真正来源；加一个协议要在 6 处改 |
| 3 | 单 WS 复用，帧为 `[u32 BE channel_id][payload]`，channel_id **全局跨设备** | 通道键为 **`(node_id, channel_id)`**；每通道**独立流控/信用**；ACP **走独立 WS** | 全局 channel 表在第二台设备就会撞 ID；每设备一个 `mpsc` 会让一个跑飞的传输拖死该设备全部终端 |
| 4 | 设备身份由 `find_agent_by_env_id` 的 `LIMIT 1` 推出 | **注册时由 Hub 签发 `node_id`**，与任何分组无关；连接表以 `node_id` 为键 | `LIMIT 1` 会让同环境第二台设备抢走第一台的身份并覆盖其连接槽，前者静默掉线却显示在线 |
| 5 | 心跳只写 version/ip，os/arch/hostname 被丢弃 | 心跳即**能力上报**：os / arch / hostname / 版本 / 支持的 connector | 设备平台必须知道设备上有什么，否则无法路由 |

## 4. 数据模型（初版）

```
device(
  id              TEXT PK,        -- node_id，注册时 Hub 签发
  name            TEXT,           -- 用户可读
  key_fingerprint TEXT,           -- 设备公钥指纹（认证用，非静态共享 token）
  enrolled_at     TEXT,
  last_seen_at    TEXT,
  status          TEXT,           -- online / offline
  os, arch, hostname, agent_version,
  capabilities    TEXT            -- JSON：支持的 connector 及参数
)
```

- **没有** `environment` 表。
- **没有** `resource` 表。
- 认证：注册时设备生成密钥对，Hub 记录指纹。**不使用静态共享 bearer token。**

> 存储选型建议 SQLite，但**建库时必须设 `journal_mode=WAL` 与 `busy_timeout`**。
> （REX 实测：零 PRAGMA，默认回滚日志 + 每次心跳都写 → 多设备重连必 `SQLITE_BUSY`。）

---

## 5. 传输

- 设备 → Hub：**一条 WS**，承载控制 + 数据通道。
- 通道标识：`(node_id, channel_id)`，每通道独立信用/流控。
- **ACP 走独立 WS**，不与终端/文件共用管道（ACP 是 JSON-RPC，语义与字节流不同）。
- 心跳 30s，同时作为能力上报与续期。

---

## 6. 执行层（本平台的核心价值）

- **本地 PTY**：节点进程直接提供 shell，不需要节点上装 `openssh-server`，
  也不需要 Hub 能拨入。这是与"远程 SSH 客户端"的根本区别。
- **本地文件系统 connector**：浏览 / 读写节点本地目录。
- 进程执行带**工作区根**，写操作限制在该根内。

---

## 7. 会话层：ACP

- 接入 **Agent Client Protocol**（Apache-2.0，官方 Rust crate 可用）。
- Hub **不存储** transcript；只存 `acp_session_id` + 归属 `node_id`。
- 恢复走 ACP 的 `session/load`。
- 会话在 Workbench 里作为一个面板类型渲染，不建独立页面。

---

## 8. 分布式推理（结论，早定以免返工）

**异构消费级设备做真实张量并行不可行**（张量并行每层多次跨设备归约，
受互联带宽限制；llama.cpp 张量模式为实验性且不支持 MoE；exo 仅限 Apple
Thunderbolt 5 生态、Linux 上仅 CPU；Petals 自 2024-09 停更）。

可行路径（由稳到险）：
1. **每设备全量副本 + 一个 OpenAI 兼容网关路由** —— 唯一稳健选项
2. 流水线并行（可容忍慢互联）
3. 投机 / draft 卸载
4. 分层卸载（仅限有线局域网）

**对外表述：一个由你 N 台设备支撑的 OpenAI 兼容端点。**
不是「N 台设备合成一台大模型机」。

---

## 9. 里程碑

| | 目标 | 验收 |
|---|---|---|
| **M0** | 设备注册 + 身份 + 心跳/能力上报 + 在线状态 | 三台设备同时在线，Web 能看到各自真实 os/arch/hostname |
| **M1** | **首个演示**：本地 PTY + 本地文件浏览 | 从浏览器**在树莓派本机开终端并浏览 `~/`**，不装 openssh-server、不开任何入站端口 |
| **M2** | ACP 接入 | 在某台**指定**设备上开一个 agent 会话并对话 |
| **M3** | 推理网关 | 一个 OpenAI 兼容端点，背后是 N 台设备各自的全量副本 |
| **M4** | （决策门）跨设备任务连续性 | 仅当确有需求才做 |

**首个演示是 M1，不是 M2。** 「我的树莓派在浏览器里有 shell 和文件浏览，
且零入站端口」是这个产品本身；ACP 面板是一项功能。

---

## 10. 技术选型

- **Rust**（Hub + 节点进程）。设备端要跑在树莓派/小内存机器上，
  单二进制、无运行时、交叉编译是硬需求。
- 节点进程需支持 **amd64 / arm64** 交叉编译。
- Web：待定（建议沿用团队熟悉的 Vue 3 + Bun，但这是独立选择，可换）。

> **不要**用 Rust 写 LLM 推理内核 —— 没有 Rust 栈支持分布式推理。
> 推理交给 llama.cpp 等，Rust 只做编排与网关。
