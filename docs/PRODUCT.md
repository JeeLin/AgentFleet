## 1. 产品定位 / Positioning

个人自托管的**项目平台**。

你有一个项目、一堆设备、一堆 coding agent。AgentFleet 让**项目**成为唯一的主轴：
把项目托管在 Hub 上，给每台设备登记一份绑定，然后**对一个项目说话**——
接话的是一个常驻的**管家（Butler）**，它把话拆成任务、派到某台设备上跑、
盯着跑、最后给你写总结。你不必记得哪个任务在哪台机器上、上次做到哪。

第一版只做 self-host、单用户。这是范围选择，不是能力妥协。

Self-hosted, single-user **project platform**. The project is the axis: hosted on the Hub,
bound to devices, and talked to through a resident butler that turns intent into tasks,
dispatches them, tracks them, and writes the summary. You never have to remember which
machine ran what.

### 1.1 非目标（显式）/ Non-goals (explicit)

- 多用户 / RBAC / 团队 / SaaS 计费
- 通用文件同步引擎（跨设备自动同步目录）——**项目≠目录同步**，见 §3.4
- 带 DAG 的重型调度器、消息中间件
- 外部 issue 系统的**双向同步**（只做单向导入 / 导出，见 §5.4）
- 异构设备张量并行推理作为第一版卖点（本地推理后置，主线是 AI Gateway，见 §6.2）
- 多态 Resource 抽象（connector 是有类型的、独立演进的能力）
- 设备级的多资源长驻管理台（终端 / 文件 / git 仍是会话内面板，见 §3.3）

## 2. 用户画像与核心价值 / Users & value

- **你有一堆设备**：服务器跑重活、PC 随手用、手机在外看进度、树莓派常驻角落。
- **你用各种 agent 软件**：不同厂商、不同协议，希望统一接入、统一看它们的动作。
- **你有若干长期项目**：每个项目都要在好几台设备上推进，而「上次做到哪、为什么这么改」
  这类知识现在散落在聊天记录和人脑子里。
- **你不想把数据交给 SaaS**：自托管，数据在你手中，且**不被锁死在产品里**（项目就是 git 仓库）。

**核心价值一句话**：把「项目」变成一个能对话、有记忆、会自动派活的对象。

## 3. 产品主干 / The spine

```text
Project（三种形态）
  ├── Butler 管家        项目的唯一入口、长期记忆的持有者
  ├── Task 看板          默认视图，任务的真身
  ├── 历史              时间线视图（真相的下钻路径）
  └── Binding            项目 ↔ 设备上的固定目录
        └── Device
              └── Agent
```

**读法**：从上到下是「意图」到「执行」，从下到上是「产出」到「验收」。

**设备与 agent 不再承担「做事」的入口，但仍然是「管理」的对象——两者不是一回事，别混。**

| | 归谁管 | 它的页面回答什么 |
|---|---|---|
| **项目** | **主轴** | 这个项目卡在哪、要做什么、做到哪了 |
| **设备** | **保留的管理面** | 这台机器在线吗、装了什么 agent、agent 版本对不对、**磁盘还剩多少**、**绑定了哪些项目 / 绑在哪个固定目录**、**它上面的执行失败集中在哪一类** |
| **agent** | **保留的管理面** | 装了哪些、哪些 `available: false`、启动配置是什么、有没有漂移 |

- **「做事从项目进」**：派活、看进度、验收，入口都在项目。
- **「管理从设备 / agent 进」**：加设备、装 agent、配启动参数、看磁盘、改配额与清理策略，入口都在设备 / agent。
- 新主轴下设备页**内容变多不变少**：多了绑定关系、磁盘配额与用量、失败归因
  （`env_broken` 连续 3 次就该标脏这台机器）。

> **与「不做设备级多资源管理台」的关系（别误读成砍掉设备页）**：
> 那条硬约束管的是**终端 / 文件 / git 三个面板不能脱离会话独立存在**（它们绑在
> `(node_id, path)` 上，随会话建立与释放）；它**不是**「不许有设备管理页」。
> 设备页管的是**设备的配置与健康**，不是「在设备上开一堆资源窗口」。这两件事不同。

### 3.1 五个实体 / Five entities

| 实体 | 是什么 | 身份 |
|------|--------|------|
| **Project** | Hub 上的一个 **git 裸仓库** + 一份绑定映射 | 项目名 |
| **Butler** | 绑定到项目、跑在 Hub 上、拥有该项目长期记忆的 agent | `(project, butler)` |
| **Task** | 一次「要做什么」的持久化记录，看板上的一个卡片 | task id |
| **Binding** | 项目 ↔ 设备上的**固定目录** | `(project_id, node_id) → path` |
| **Snapshot** | 一次快照 = 一个 **commit** | commit hash（内容寻址） |

细节见 `docs/architecture/project-and-snapshot.md`（Project / Binding / Snapshot）
与 `docs/architecture/butler.md`（Butler）、`docs/architecture/task-model.md`（Task）。

### 3.2 项目的三种形态 / Three project shapes

| 形态 | 代码在哪 | Hub 存什么 | 「起点」是什么 |
|------|---------|-----------|--------------|
| **中心式** | Hub 的裸仓库 | 全部代码 + 元数据 | Hub 上的 commit |
| **镜像式** | 上游（GitHub 等）+ Hub 镜像 | 镜像的全部代码 + 元数据 | Hub 上镜像的 commit |
| **隔离式** | **只在指定设备上，永不出该设备** | **只有元数据** | 该设备上的 commit hash，Hub **不验证内容** |

#### 项目主题色 / Project theme color

每个项目可选一个**主题色**（如蓝 / 绿 / 紫 / 橙），用于：

- 看板卡片的左侧边框或标签色
- 全局任务流中的项目标签
- 项目页的页眉 / 辅助色

主题色仅用于**视觉区分**，不影响任何业务逻辑。项目创建时选，之后可改。

#### 项目生命周期：可归档，不可删除

项目支持**归档（archive）**，不支持**删除**：

- **归档后**：不再出现在项目列表与看板首页，任务停止派发，但历史执行记录、管家总结、轨迹全部保留；可随时取消归档。
- **删除**：**第一版不提供**。项目是 Hub 的真相源，删除会让已合入的任务历史、失败归因、成本记录一并丢失，代价太高。

> 为什么不可删除：**失败归因和审计需要历史**。一个项目哪怕跑了十次失败，这些记录对排障比「一个干净的空项目」更有价值。

**形态是项目的一个属性，不是三种产品**。三种形态共用同一套 Task / Binding / 看板 / 管家，
差别只在「代码从哪来、到哪去」这一层。**用户可以随时把隔离式转成中心式**（推上去即可），
反之不提供——把已经上传的代码收回，产品做不到真收。

**其余形态变更一律不提供**，包括中心式 → 镜像式：镜像式要指一个上游，而中心式的代码
没有上游，改过去等于凭空造一个上游出来。所以形态变更**只有 `隔离式 → 中心式` 这一条**，
且升级时 Hub 要真的把代码推上去、建好裸仓库才算完成（不是改一个字段）。

### 3.3 看板是默认视图 / Board first

进入一个项目，默认落在 **Task 看板**：

```text
待办        排队中      执行中      待验收      已完成      失败
pending     queued      running     review      done        failed
```

- **看板是默认视图**，不是「任务页」。项目的首页就是它。
- **时间线是第二视图**，回答「什么时候发生了什么」；看板回答「现在卡在哪」。
  两者是**同一批事实的两种投影**，不是两套数据。切视图不改变数据，只改变排布。
- **「待验收」是价值锚点**：任务跑完了不等于做对了。合并主干、关闭任务，都必须经过这一列。
- 看板上有**卡片上的因果链**：一张卡点进去，能看到它由哪句话（意图）而来、
  经过哪几次执行、每次为什么失败、最后是谁（人还是管家）判的完成。

#### 3.3.1 看板的可读性：过滤、搜索、批量（新）

> **看板超过 30 张卡就没有可读性。** 过滤不是「以后加」，是看板能用的前提。

**过滤维度**（可叠加，状态栏显示当前生效的过滤）：

| 维度 | 例子 |
|---|---|
| 设备 | 只看跑在 `device-b` 上的 |
| agent | 只看 `opencode` 跑的 |
| 创建者 | 人建的 / 管家拆的 / 外部导入的 |
| 来源 | 外部 issue 导入的（带源标签） |
| 时间 | 最近 24h 有更新的 |
| 关键词 | 标题 / 描述 / 分支名全文搜索 |

**批量操作**（选中多张卡后）：

- 批量移到某列（只允许**合法**的状态迁移，非法迁移的卡自动排除并提示）
- 批量取消（`running` 的会先走 ACP `session/cancel`，不杀进程）
- 批量重试（**每张卡换设备**，遵守 §2.1① 的换条件规则）
- 批量归档

> **批量重试必须逐张检查约束**。不能因为「批量」就跳过 `allowed_devices`——
> 那样会把约束降级成偏好（`task-model.md` §4.1）。

### 3.4 项目 ≠ 目录同步 / Project is not file sync

这一句必须钉死，否则整个设计会被误读成 Syncthing：

> **同步的是「内容」，不是「文件夹」。** 同一起点由 **git commit + 环境声明** 两层身份保证；
> 依赖目录（`node_modules` 等）**永远不搬运**，按 lockfile 在本地重建（`DECISIONS.md` D9：
> x86-64 与 aarch64 装出来的不是同一份东西，**根本不存在「同一份依赖」可搬**）。

同理 **Hub 是唯一真相源**：不引入设备间 P2P 直传，不用 Syncthing 当主同步通道，
节点密钥永不上传。

### 3.5 固定目录 + worktree / Fixed directory + worktree

**每个设备处理同一个项目时使用固定目录**（Binding 钉死一个 `path`），
目录内用 **git worktree** 给不同任务开不同工作树。

- **为什么固定目录**：设备上的依赖缓存、构建缓存、IDE 配置都挂在路径上。
  路径一漂移，缓存就全部失效，每次任务都要冷启动——那比不缓存还糟。
- **为什么用 worktree 而不是多个 clone**：worktree 共享同一份 object store，
  第 N 个任务不多占一份仓库历史；而 clone 每多一个任务就多一份完整 objects。
- **代价（必须明说）**：worktree **不共享** `node_modules` / `target` 这类构建产物
  （它们是工作树级目录）。所以：
  - **依赖缓存按 lockfile 哈希复用**（同一 commit 的同一 lockfile → 同一份缓存，跨任务命中）；
  - **任务产物随工作树一起清**，不清缓存；
  - worktree 用完即删（`git worktree remove`），不累积。

一句话：**目录固定、工作树可弃、缓存可复、产物必清**。

> **磁盘也是任务分配的硬条件**，不只管事后清理——见 `scheduling.md` §3.2 / §3.3 与 §5.3。
> 三件事分开：**配额**决定「允许多大」，**调度**决定「现在跑不跑得动」，**清理**决定「跑完怎么收回」。

### 3.6 能力对 agent 的暴露：技能 / MCP（新）

> **接 REX 的协议实现，但换一个暴露方式。**

REX 的设备侧本来就能拨号连内网资源（`ssh` / `sql` / `redis` / `sftp` / `s3` / TCP 透传）。
AgentFleet 要接的是**这套拨号与协议实现**，不是 REX 的「Resource」产品模型。

关键在于**怎么给 agent 用**。`AGENTS.md` 约束 3 写着「connector 只面向页面用户，不向 agent 暴露」——
那条要**按新需求重新裁定**，但**不能简单删掉**，因为它防的是真问题：

| 暴露方式 | 可行性 | 判断 |
|---|---|---|
| **connector 直接对 agent 开放**（agent 能调任意 connector） | 技术上最简单 | ❌ **仍然禁止**。等于给所有 agent 开一条统一的提权通道，而我们替它维护权限 |
| **作为「技能」按需授予任务** | 可行 | ✅ **主路径**。任务级声明「这个任务可以连 `db-prod`」，与 `required_capabilities` 同一套机制 |
| **作为 MCP server 暴露给 agent** | 可行，且生态通用 | ✅ **并行支持**。设备上起一个 MCP server，agent 按标准协议连它 |

**为什么用「技能 / MCP」而不是「直接开放 connector」**：

- **技能**让它成为一个**显式授予**的东西——任务没声明就没有，不是默认能力。
- **MCP** 让它成为一个**标准接口**——agent 不用知道 AgentFleet 的内部协议，
  任何支持 MCP 的 agent 都能用，我们也不必为每个 agent 写适配。

**这条也是本项目原有的定位**：`AGENTS.md` 约束 3 的精神是「agent 用它自己装的能力，
我们不替它管权限」。技能 / MCP 恰好落在中间：**我们提供通道，但不替 agent 决定能不能用**——
能不能用由任务级声明（人给的）决定，不由我们运行时猜。

**安全边界（必须写死）**：

- 技能/MCP 暴露的凭据**不进 agent 的上下文**。agent 说「用 `db-prod` 执行这条 SQL」，
  凭据由设备侧注入，agent 看不见。这是 MCP 相比「把连接串塞进 prompt」的核心价值。
- **审计**：每一次经技能/MCP 的连接与操作都进轨迹（谁、什么时候、连了什么、做了什么），
  与 REX 的「审计日志」是同一件事。
- 隔离式项目下，技能/MCP 的操作**仍不出设备**——它本来就是设备侧拨号。

### 3.7 项目摘要：打开项目第一眼看到什么（新）

看板回答「任务到哪了」，但**没回答「这个项目整体怎么样」**。打开项目应该有第一眼摘要：

```text
┌ project: agentfleet ──────────────────────────────── 主题色 ▍蓝 ┐
│ 上次做到哪   2 小时前 合入了 #1038「修 connector 超时」          │
│ 正在跑       2 个执行（device-a / device-c）  ·  查看监控 →       │
│ 等你决定     1 条待决策  ·  2 个草稿待下发  ·  3 张卡待验收       │
│ 最近总结     管家 1 小时前：「这周在收口 v0.6.0，剩下 3 个问题」   │
└──────────────────────────────────────────────────────────────────┘
```

**四行，各回答一个问题**，且**每一行都可点进去**：

| 行 | 回答 | 数据来源 |
|---|---|---|
| 上次做到哪 | 「我上次离开后发生了什么」 | 最近一次 `done` / 合并事件 |
| 正在跑 | 「现在有没有东西在动」 | `projects/:id/executions`（§3.10） |
| 等你决定 | 「有没有事在等我」 | 收件箱的三个计数（草稿 / 待决策 / 待验收） |
| 最近总结 | 「整体在往哪走」 | 管家写的总结（`butler.md` §2.4） |

> **这一块就是管家的「写总结」在 UI 上的落点**——总结不是存档文章，是项目页的第一眼。
> 写出来没人看等于没写，而项目页是唯一必然会看的地方。

### 3.8 时间与成本 / Time & cost（新，必要）

自托管不等于不在意花销。每个项目与每个任务都要能回答「花了多少」：

| 维度 | 记什么 | 展示在哪 |
|---|---|---|
| **时间** | 每个 Execution 的起止、墙钟时长、**排队等待时长**（`pending→queued` 另记——**等设备和跑设备是两种成本**） | 任务详情 / 项目摘要 |
| **token** | 每次执行 agent 消耗的输入 / 输出 token（ACP 侧能拿到就记，拿不到标 `unknown`） | 任务详情 |
| **金额** | 按 AI Gateway 的模型单价折算；**没有 Gateway 时只显示 token，不算钱** | 项目摘要 / 设备页 |
| **磁盘** | 每个项目的 worktree + 缓存占用 | 设备页（配额旁） |

**两条硬规则**：

1. **拿不到就标 `unknown`，不估算**。估算出来的成本会让预算判断失效，比没有更糟。
2. **成本是统计，不是配额**。第一版不设「花超了就停」——那需要先有可信的计量。

### 3.9 失败与验收的操作形态（新）

> **这是你每天会用十次的地方，它比再讨论十个架构决策更能决定产品好不好用。**

失败之后能做什么、待验收里能做什么，**完整交互见 `architecture/task-model.md` §3.4 / §3.5**。
一句话：**任务详情里有唯一的失败面板与验收面板**，不许在别处提供第二套动作，
否则两处状态会打架。

### 3.10 执行监控：项目下的 agent 在做什么（新）

> **这是看板「`running` 那一列的放大镜**，不是看板的替代。

看板看**任务**（我要什么），这个页面看**正在干活的 agent**（它在干什么、卡没卡）。
看板天然缺失「此刻」这一维：一张卡在 `running` 列，你看不出它是刚开始还是卡了 40 分钟、
是在写代码还是在 `npm install`——而这两件事的处置完全不同。

| | 看板 | 执行监控 |
|---|---|---|
| 视角 | 任务为中心 | **执行体**为中心 |
| 时间粒度 | 任务生命周期 | **秒级：刚才在跑什么、现在在读哪个文件** |
| 数量 | 一个项目几十个任务 | **同时最多几个在跑** |

#### 三层信息，按新鲜度拆（硬规则）

```text
① 慢变摘要（轮询 / 低频推送）
   每个在跑的 Execution 一行：设备 / agent / 任务标题 / 已跑时长 / 当前阶段 / 最后动作摘要
   —— 这是页面主体，秒级刷新足够

② 当前动作（订阅，且只订阅这一条）
   点开某一行才订阅它的实时事件流。未展开的不订阅。
   —— 硬规矩：20 个任务同时展开 = 20 路流 = 前端被压死

③ 进度怎么来的（必须诚实）
```

#### 「进度」不许编百分比

agent **不会自己上报「我做了 40%」**——ACP 里没有这个字段，编一个进度条就是自欺。
所以「做到什么进度」只能靠**可观测的代理指标**：

- 已跑时长（最可靠，也最易误导：跑很久可能是在装依赖）
- **本 Execution 的实际动作**：改了几个文件、跑了哪条命令、`base_commit..HEAD` 的 diff 在长
- `done_when` 是否被验证（**可判定**时这是真进度；不可判定就只能说「还在跑」）
- **卡住信号**：超过 N 分钟没有新的 `tool_call` → 标「**疑似无动静**」

> **最后一条最有价值**：用户真正想知道的往往不是「完成 40%」，是「**它是不是卡了**」。
> 所以核心展示不是进度条，而是「**它最后一次动是什么时候、在做什么**」。

#### 路由与边界（别做成设备级管理台）

- **合法**：`projects/:id/executions`——以**项目**为入口，跨设备汇总这个项目正在跑的执行。
- **越界**：`devices/:id/agents`——以**设备**为入口列出「这台设备上的所有进程/资源」。

同一个数据，入口不同，产品含义完全不同。**入口搞反了，将来想砍就砍不掉了。**

#### 隔离式项目

**能看到全部三层**（对话、diff、动作都按需向设备拉取，见
`project-and-snapshot.md` §2.1.1），只是**每次都要走设备**、延迟更高。

### 3.11 执行复盘 / Execution replay（新）

> 看板能看到任务到哪了，但看不到**它是怎么跑过去的**。

把一次 Execution 的轨迹（User / Assistant / Tool 事件）按时间串成一个可滚动的时间轴：

- 回放、暂停、跳到某个工具调用看输入输出
- **失败任务优先**：`task_failed` 看 diff 看不出哪一步开始出错，复盘能
- **不新增数据采集**，只是已有轨迹表（`session-and-trajectory.md`）的一个新投影

**硬规则**：复盘是**只读**的。不许在复盘里编辑、不许在复盘里重跑——
它和 §3.9 的失败面板是两个东西（**一个看，一个做**）。

### 3.12 执行间接力 / Task relay（新）

**同一项目在同一设备上的连续任务，不必每次冷启动。**

- 记录 `parent_execution_id`；调度时**优先选最近跑过这个项目的设备**——这是**打分项，不是硬过滤**
  （硬过滤只认 `allowed_*` 与隔离策略，`task-model.md` §4.1）。
- **共享的是缓存，不是工作树**。工作树仍在任务结束后清理（§3.5）；
  复用的是按 lockfile 哈希的依赖缓存与构建缓存。
- 卡片上显示「接力自执行 #N，复用缓存 X MB」——**让人看得见省下来的东西**，
  否则这条优化做了也没人知道。

### 3.13 任务模板 / Task template（TODO，但强烈建议早做）

同一项目的同类任务（「修这个 bug」「加这个测试」）会重复创建几十次。模板保存的是
**任务级约束的快照 + `done_when` 骨架**：

```text
模板「修 bug」：  done_when = cargo test 全绿（criteria）
                  allowed_devices = [device-a, device-b]
                  required_capabilities = [git, rust-1.75]
                  retry_limit = 2
```

- **模板不是任务**，是新建任务时的一个下拉。
- **模板属于项目**，跨项目不共享（不同项目的约束不该混）。
- **第一版记为 TODO**，但它是**被低估的高频操作**——没有它，每次新建任务都要重填五个字段。

### 3.14 独立成产品还是一部分：**AgentFleet 一个**（用户已裁定）

> **2026-11-01 裁定：REX 不是并列的第二个产品，最终只有一个产品 —— AgentFleet。**

因此 REX 的处置是**吸收其能力，不保留其产品模型**：

| REX 的东西 | 处置 |
|---|---|
| 协议实现（SSH / DB / Redis / S3 / SFTP / TCP 透传，设备侧拨号） | **接**，作为 connector 插件与**技能 / MCP**（§3.6） |
| 文件传输引擎（数据不经浏览器） | **接**，服务 packfile 与大数据传输 |
| 内网反向隧道的经验 | **接**（已同构） |
| **多态 Resource 抽象 + 设备级资源管理台** | **拒**（`AGENTS.md` 约束 3 + 本项目已排除的形态） |
| SIP / 浏览器直连资源 | **拒**（与项目主轴无关，只增加攻击面与维护量） |

**关键**：接的是**实现**，不是**模型**。这些能力在本产品里的形态是
「任务级授予的技能 / MCP」，不是「一张能连上去操作的资源列表」。

## 4. 管家 / The Butler

### 4.1 它是什么

> **管家是绑定到一个项目、跑在 Hub 上、拥有该项目长期记忆的 agent。**
> 它是这个项目的**唯一入口**——你对项目说的每句话，都先进它。

**它明确不是调度器。** 这是最容易搞混的一处：

| | 管家（Butler） | 调度器（Scheduler） |
|---|---|---|
| 回答 | **做什么**、做到什么算完 | **在哪跑** |
| 依据 | 项目记忆、意图、历史 | 能力、负载、隔离策略 |
| 有记忆吗 | **有**，长期 | 无，每次现算 |
| 会改代码吗 | 不会（它写的是任务与总结） | 不会 |

管家派任务时**调用**调度器，而不是自己挑机器。

### 4.2 四项能力 / Four jobs

1. **接意图 / Listen** —— 把一句人话接住，必要时反问澄清，落成一条**意图记录**。
   **不急着拆任务**：一句话可能只够一个任务，也可能根本不该派活。
2. **建派任务 / Dispatch** —— 把意图拆成任务、给出任务级约束（§5.1），交给调度器。
3. **督进度 / Watch** —— 任务卡住、失败、超时、待验收太久，它先说，不用你去翻。
4. **写总结 / Summarize** —— 任务（或一批任务）结束后写一份人能读的总结：
   做了什么、为什么这么做、哪里不对、下一步建议。

### 4.3 记忆放在两处 / Two memory homes

| | 放哪 | 存什么 | 为什么 |
|---|---|---|---|
| **结构化事实** | Hub 库 `project_memory` | 约定、决策、偏好、待办钩子，可查询 | 要能被查询、被过滤、被程序读 |
| **叙事记忆** | 项目仓库 `.afleet/MEMORY.md` | 「我们为什么这么改」这类人读的长文 | **随 git 走**，用户能直接编辑，**数据不被锁死** |

**为什么不全放库里**：全放库 = 你的项目知识锁死在这个产品里，产品一停就没了。
**为什么不全放仓库里**：仓库里没法做查询与过滤，管家的「回忆」会退化成全文检索。
两处并存是刻意的：**可查询的归库，可迁移的归 git**。

> `.afleet/MEMORY.md` 在项目仓库里是普通文件，**用户可以手动改**，管家下次读到的就是改后的版本。
> 这是特性，不是后门。

### 4.4 管家不该做的事 / What the butler must not do

- 不直接改代码——它没有工作区，改代码是任务的活。
- **不假装记得**。记忆里没有的，说没有，去问，或者去查历史。

### 4.5 合并权：三档可配，默认最保守（用户已裁定 2026-11-01）

「管家能不能自己合主干」这个问题**在没用过之前无法回答**。所以不定死，做成三档，
**默认档 0**：

| 档 | 行为 | 适用 |
|---|---|---|
| **档 0（默认）** | **只能人或显式规则合并**。管家可以推一把、给判断，但合主干要你点头 | 起步阶段，还没建立信任 |
| **档 1** | 管家可合并，但**每次合并写进总结并通知** | 用过一段时间，想省一点操作 |
| **档 2** | 管家可合并，**仅通知**（不写总结） | 已经信任，只要知道发生过 |

- **档位是项目级设置**，不是全局——不同项目该有不同答案。
- **升档必须由人操作**，管家不能自己请求升档（自我扩权）。
- **无论哪档，合并动作都要留痕**：谁合的（人 / 管家）、什么时候、合了哪个分支到哪。
- **档 0 下「显式规则」的含义**：你可以预先声明「如果 `cargo test` 全绿且只改了 `src/`，
  允许自动合并」——那也是一条人给的规则，不是管家自己判断的。

> 为什么默认最保守：**合主干是唯一会污染主干的动作**。
> 其他所有错误都还能回退到某次执行，只有合错了会变成「历史里的一行」。

### 4.6 超时降级的默认值（用户已裁定 2026-11-01）

决策请求必须带 TTL，超时后的默认处置**按「可不可逆」区分**：

| 请求类型 | 超时默认 | 理由 |
|---|---|---|
| **业务决策**（用 Redis 还是 SQLite） | **选标注 `default` 的选项继续**；没有 `default` 就中止（转 `interrupted`） | **可逆**——选错了下一步还能改回来。让执行继续比停住更有价值 |
| **磁盘清理确认** | **保持中止，不自动清理** | **不可逆**——删了就没了。不可逆操作不该有「超时默认执行」 |

**共同点**：超时后**都必须留痕**（「超时未答，按默认继续」/「超时未答，保持中止」），
且**收件箱里那条不消失**——你回来时仍能看到它发生过什么。

## 5. 任务 / Task

### 5.1 任务模型 / Task model

- **Task : Execution = 1 : N**。一个任务可以执行多次（重试、换设备、换 agent），
  **每次都留现场**，不覆盖上一次。
- **任务级约束**（派活时定，执行时必须满足）：
  - `allowed_devices` —— 只许在这些设备上跑（隔离式项目的实现方式）
  - `allowed_agents` —— 只许用这些 agent
  - `required_capabilities` —— 必须具备的能力（git / terminal / 某架构 / 某内存阈值）

**过滤顺序固定，不可调换**：

```text
① 任务级 allowed_*（派活人说了算）
② 项目级隔离策略（形态决定谁有资格）
③ 调度器按能力 / 负载排序（谁更合适）
```

**任何一层过滤为空 → 任务停回待办并说明原因，不降级凑数。**
「没设备能跑，那就随便找一台试试」是本产品要明确避免的失败方式——
它会产出一个看起来正常但不可信的结果，比报错更糟。

### 5.2 六态 / Six states

| 状态 | 含义 | 谁推进它 |
|------|------|---------|
| `pending` | 待办：被接住了，还没派 | 管家 / 人 |
| `queued` | 排队中：已选中设备，等设备接活 | 调度器 → 设备 |
| `running` | 执行中：设备上有一次 Execution 在跑 | 设备 |
| `review` | **待验收**：跑完了，等判定 | **人或显式规则** |
| `done` | 已完成：验收通过，产出已合入主干 | 人 / 规则 |
| `failed` | 失败：停在失败列，**不自动回待办** | 设备 / 管家标注原因 |

三条硬性规则：

1. **重试必须有上限，且必须换条件**（换设备 / 换 agent / 换起点）。同一个原地重试三次
   只是在浪费电；用户已明确要求「失败重试时换一台设备重新调度」。
2. **失败必须留「为什么」**。没有原因串的失败，等于没发生——下次还会犯。
3. **失败停在「失败」列，不自动回待办**。自动回待办会让失败被稀释成背景噪声，
   而失败恰恰是最需要人看一眼的东西。

失败的具体形态与处置见 `docs/architecture/task-model.md` §3。

### 5.3 磁盘：四层处置 / Disk discipline

每个设备都在堆构建文件，这是本产品最容易失控的地方。四层处置：

1. **任务级**：任务跑完 → `git clean -xdf` + 回主分支（或直接 `worktree remove`）。
2. **缓存级**：依赖缓存按 **lockfile 哈希**复用；**任务产物必清**（缓存不是产物）。
3. **配额级**：Binding 上设磁盘配额；**磁盘超 90% 就不再往这台派任务**，
   并在看板 / 设备页说清原因。
4. **策略级**：绑定时可选三档清理策略（保守 / 平衡 / 激进），决定缓存保留多久、产物留不留。

**不准「先跑起来再说」**：磁盘满了不是性能问题，是任务会静默失败的问题。

### 5.4 收件箱 / Inbox

> **收件箱不是通知列表，是「等你做决定的东西」队列。**

通知是广播（「任务完成了」，看不看都行）；收件箱是**待办事项**（「这个必须你选，否则卡住」）。
混在一起，完成通知会把真正需要决策的事淹没。

**两个区，默认打开「待决策」**：

| 区 | 内容 | 处置 |
|---|---|---|
| **待决策**（默认） | 需要你选一个的事：agent 的业务决策、管家的待决事项、磁盘清理确认 | 不处理就一直是待决策，相关执行标 `waiting_for_user` |
| **动态** | 完成 / 失败 / 进度提醒 / 外部 issue 导入 | 可批量已读，**无阻塞** |

#### 设备上的请求怎么到 Hub：三条通路，别混

| 来源 | 走哪 | 进哪个区 |
|---|---|---|
| 设备上报的事实（状态、失败原因、磁盘告警） | 控制连接 + 心跳 | 动态 |
| **agent 的权限确认**（能不能执行这条命令） | **只在本机，绝不经过 Hub** | **不进收件箱** |
| **agent 的业务决策**（用 Redis 还是 SQLite） | 控制连接 → Hub → 收件箱 | **待决策** |
| 管家自己的待决事项（连败 3 次怎么办、磁盘不够要不要清） | 直接进 | **待决策** |

> **为什么 agent 的权限确认绝不能经 Hub 中转**：那等于把 Hub 变成设备的**远程控制面**——
> 攻击者拿到 Hub 就能对设备说「用户已批准执行这条命令」。
> `AGENTS.md` 约束 1「Hub 不需要任何到设备的入站访问」的意义就在这里，不是为了省端口。
>
> **界线一句话**：**安全许可**（能不能执行）只在本机；**业务决策**（该怎么做）可以进 Hub。

#### 四条硬规则

1. **必须带 TTL**。人在睡觉，执行不能无限等。超时 → 执行标 `interrupted`
   （**不是 `failed`**——它没做错，是在等人）。
2. **必须能降级**。超时后按预设处理：选默认方案继续 / 中止。**不能无声卡死。**
3. **答案必须留痕**：谁答的、什么时候、选了哪个、是否超时。
4. **同一问题的答案可复用**：「以后都别问我这个」→ 写进 `project_memory`，下次直接按答案走。

#### 磁盘清理的确认（用户已裁定，2026-11-01）

任务因 `disk_exhausted` 中止时，**不直接判失败**，而是**先问你要不要清理**——
并且**必须说清准备清理什么**：

```text
「device-b 上 task-1042 的 worktree 占 12.4 GB：
   node_modules 4.1 GB / target 7.8 GB / 其它产物 0.5 GB
   清理后可释放 12.4 GB（保留前 3 个产物做诊断，约 40 MB）
   → [ 清理并续跑 ]  [ 只清理，不续跑 ]  [ 不清理，判失败 ]」
```

- **不清理任何东西之前必须被选中**。磁盘清理是不可逆操作，不能默认执行。
- **必须在超时后也有明确归宿**：超时未选 → 保持中止状态（不自动清理、不自动续跑），
  在收件箱里留着等你回来。
- 续跑从**检查点**起（`task-continuity.md` §3），不是从头重跑。

### 5.5 外部 issue：只做单向 / One-way issue sync

**不做双向同步。** 外部 issue（GitHub / Gitea / Jira …）只做：

- **导入**：把外部 issue 拉进来**生成一条 Task**，从此**任务的真身留在 Hub**。
- **导出**：把 Task 的状态 / 结论回写一条评论或改一次状态，**单向**。

**为什么不双向**：「两边都是真相」意味着任何一次写入都要解决冲突，而冲突的解法只能是
「以某一边为准」——那另一边的用户看到的就是假数据。单向导入把真相钉死在 Hub 一侧，
外部 issue 退化成「一个通知渠道」，这是可维护的。

**那我不去看 issue，别人提的问题我怎么知道？**（用户提问，这是核心顾虑）

答：**问题必须被推进产品里，而不是推着你去看。** 三层：

1. **Hub 内收件箱（Inbox）+ 通知**：导入进的任务直接进项目看板并标 `外部来源`；
   同时落一条通知（站内 + 可选的邮件 / IM webhook）。**你不需要去 issue 那边看，
   新东西会到你面前来。**
2. **管家先看一遍**：新导入的 issue 由管家初筛——重复的合并、不清楚的反问、
   能直接派的直接派。**它替你把「看 issue」这件事做了**，你只在它拿不准时报一次。
3. **回写单向、可配**：任务的结论回写到原 issue（一条评论，带 Hub 链接）。
   所以**对方在 issue 那边看得见进展**，你也不需要两边同步——你在 Hub 做的每件事，
   对外都是自动可见的。

> 一句话：**导入把别人提的问题搬到你门口；管家替你看第一遍；导出让你的结论自动回去。
> 你不去 issue 那边，issue 那边也照样知道你在做什么。**

### 6.1 第一版（必做）/ First release (must)

> **本表只定范围。** 哪项能力由哪个里程碑承接，以 `docs/DEVELOPMENT.md` §4

### 6.4 用户可见流程（第一版）/ Key flows

1. **接入一台设备**：`afcli run <hub-url>` → 自动 enroll → Hub 显示新节点 → 在线。
2. **建一个项目**：选形态（中心式 / 隔离式 / 镜像式）→ 中心式直接往 Hub push；隔离式只登记元数据；
   镜像式填一个上游 URL。项目**不填目录**——目录是绑定的事。
3. **给一台设备绑定项目**：选项目 → 选设备 → 指定**固定目录** → 选清理策略。
   之后这个项目在这台设备上永远是这个目录。
4. **打开项目**：默认落在**看板**。六列、卡片、卡上带因果链。
5. **对项目说一句话**：进项目即对管家说话。管家接住、必要时反问、拆成任务、派出去。
6. **看任务怎么跑**：卡点进去 → 看它派给了谁、跑了几次、每次为什么失败、当前产出 diff
   （即 `task.base_commit..HEAD`）。
7. **验收**：任务跑完进「待验收」，看 diff、看管家的总结 → 通过（合主干）或打回（写明原因）。
8. **设备掉线**：WS 断开 → 节点指数退避重连（1s/2s/4s…上限 30s）；连续心跳丢失 > 45s 转「离线」。
   离线期间任务在设备上仍存活，面板转只读。该设备上的绑定任务不再派新的，**但不迁移已在跑的**。
9. **任务失败**：失败停在「失败」列，带原因。重试**换一台设备**重新调度，且有次数上限。

## 7. 两个关键设计问题（结论）/ Two key design questions

### 7.1 一、任务的连贯性 / Task continuity

> 同一个任务在多设备、多节点之间流转时，状态、上下文、执行进度如何保持一致、不断裂、可续跑？

**结论：**

- **状态与上下文外置到 Hub（single source of truth）**：任务的 transcript、工具调用轨迹、
  工作区快照引用都存 Hub，节点只持有「当前执行所需的上下文切片」。节点掉线，任务状态不丢。
- **断点可恢复**：任务 = 持久化的状态机 + 事件日志；节点执行带**检查点（checkpoint）**，
  重连后从最后一个成功检查点续跑，不重做。
- **工作区/产物的定位交给 git**：跨节点续跑靠「从 Hub 的 commit 重建工作区」，
  不靠「上一台机器还在」。**不做设备间 P2P 直传**。
- **ACP 的 `session/load` 作为对话恢复机制**：agent 会话恢复走 ACP，而非自建。
- **轨迹 append-only**：所有动作写入 dsh 式事件流，既是 UI 回放源，也是断点续跑的审计源。
- **第一版的可恢复上限是节点级**：同一节点上的 ACP 会话重连可 `session/load`；
  跨节点续跑要等任务系统里程碑真正落地。

### 7.2 二、推理：AI Gateway 优先，本地 / 分布式推理记为 TODO

> **状态（2026-11-03 更新）：分布式推理与本地推理一律记为 TODO，暂时不考虑。**
> 连「AI Gateway」本身也不是第一版的内容——`PRODUCT.md` §6.2 已把它列为后续项，
> 里程碑表里只留一行、不排期（`DEVELOPMENT.md` §3）。**当前没有推理相关的开发任务。**
> 这一节保留的是**为什么现在不做**的理由，防止有人重新把它当成待办捡起来。

**结论（2026-10-15 定案，2026-11-03 收紧为 TODO）**：先做 AI Gateway，本地推理后置。

- **异构消费级设备做真实张量并行不可行**：张量并行每层多次跨设备归约，受互联带宽/延迟限制；
  llama.cpp 的 RPC 后端只做逐算子转发 + 层切分，没有集合通信原语。
- **主线是 AI Gateway**：统一端点 + 密钥托管 + 按 model/价格/延迟/可用性路由 + 故障转移 + 额度统计。
  **它同样不在第一版**（§6.2 后续），只是比本地推理更靠前。
- **本地推理不实现**，保留为「触发条件满足时再做」的待办（`ai-gateway.md` §4 第 6 条）。
- **分布式推理 → TODO**：把多台设备拼成一个大模型跑，需要多台强设备同时在线、同 build、
  低延迟内网，条件苛刻且与「零入站端口」冲突。**记为 TODO，不排期、不设计、不占里程碑。**

详见 `docs/architecture/ai-gateway.md`（需求权威来源）与 `inference.md`（调研存档，非主线）。

## 8. 术语 / Glossary

| 词 | 含义 |
|----|------|
| **project / 项目** | Hub 上的一个 git 裸仓库 + 一份绑定映射。三种形态：中心式 / 隔离式 / 镜像式。**产品的主轴** |
| **butler / 管家** | 绑定到一个项目、跑在 Hub 上、拥有该项目长期记忆的 agent；项目的唯一入口。**不是调度器** |
| **task / 任务** | 「要做什么」的持久化记录，看板上的一个卡片。真身在 Hub，不在设备上 |
| **execution / 执行** | 任务的一次尝试。**Task : Execution = 1 : N**，失败留现场不覆盖 |
| **binding / 绑定** | 项目 ↔ 设备上的**固定目录**，`(project_id, node_id) → path` |
| **snapshot / 快照** | 一次快照 = 一个 commit。身份是 commit hash（内容寻址），不可伪造 |
| **review / 待验收** | 任务跑完但未判定的状态。**价值锚点**：合并主干必须经过它 |
| device / node | 一台注册的设备及其上运行的节点进程。**不是「做事」的入口**（做事从项目进），但**仍是「管理」的对象**——设备页管配置与健康，不是被砍掉的 |
| agent | **仅指 AI agent**；绝不指设备进程 |
| Hub | 自托管的服务端，用户自己跑；**唯一真相源** |
| connector | 节点上提供的一类**有类型**的能力（terminal / files / git / exec / ssh / db / …），可插件化 |
| trajectory | dsh 式的会话动作事件流，Web 逐条回放 |
| 会话 / 会话页 | 会话容器：一个页面（`/sessions/:id`），持有对话流与面板坞。挂 agent 时 `session.agent_id` 非 NULL，且建会话当时该 agent 在目标节点上必须**可用**（否则 409 `agent_unavailable`） |
| workspace | 工作区：设备上的一个 `(node_id, path)`，**会话的一个字段**，不是路由、不是页面 |
| worktree | Git 工作树：同一仓库的多个独立工作目录，**共享 object store**。用于固定目录内按任务隔离 |
| Workbench | 会话工作台：**会话页的布局外壳**（标题栏 + 会话 tab 条 + 面板坞 + 轨迹抽屉），**它自己没有路由** |
| ~~baseline~~ | **已不需要**：diff 改由 git 面板直接问工作区的 `status` / `diff`。项目主轴下等价物是 `task.base_commit..HEAD` |
| ~~artifact~~ | **已撤销（2026-10-26）**：产物归档到 Hub。现在由「任务分支 push 回 Hub」承担 |
| CAS | 内容寻址存储：Hub 侧以内容哈希存 blob。**现已完全撤销**；项目主轴下由 git object store 承担同一角色 |

> **三分法，别混**：
> **会话页** = `/sessions/:id`，有路由；**工作区** = `(node_id, path)` 字段，**没有路由**；
> **Workbench** = 会话页的布局外壳，**没有路由**。
> 「工作区不是路由」仍是硬约束：工作区一旦有地址，它就成了可枚举、可跳转、可长期持有的句柄，
> 于是「设备级多资源长驻管理台」在结构上成为可能——而那正是 §1.1 排除的形态。
