# 设计规范 / Design System

> AgentFleet Web 控制台的设计语言。**这是最高优先级产出**——原型会变，规范不该变。
> M1 实现阶段（Vue 组件）照 §3 的组件契约写，前端照 §4 的交互范式接线。
>
> 规范正文只讲**是什么与为什么**；具体取值在 `packages/web/src/styles/tokens.css`
> （原型那份 `prototype/assets/tokens.css` 只是转发 shim），
> 可视化核对在 `prototype/components.html`，双击即可打开，零依赖零构建零网络请求。
>
> 决策背景见 `PRODUCT.md`（功能边界）与 `docs/architecture/`（协议与数据模型）。
> 范围纪律：本规范只描述 M1 范围内的界面，ACP 会话、git 面板、任务分发、AI Gateway
> 一律只留结构位置、不画实现。

## 0. 怎么用这份文档

| 你在做 | 看哪节 |
|--------|--------|
| 定一个颜色 / 间距 / 字号 | §2 token（每个取值带理由与「什么时候**不**该用」） |
| 写一个 Vue 组件 | §3 组件契约（状态用 `data-*` 属性表达，契约一次定死） |
| 接键盘、接浮层、接焦点 | §4 交互范式（**焦点栈、键位表、密度档、错误态语义**） |
| 决定一个界面元素放哪 | §5 信息架构与页面 |
| 想知道某个决策为什么这么定 | §7 八个设计决断（附被否决的方案） |
| 实现 `/api/devices` | §6 数据契约（mock 形状 = 将来 API 的形状） |
| 判断能不能用某个组件 | §3.21 禁用清单（这些组件**不存在**） |

**三条阅读纪律**：

1. **规范与原型冲突时，规范对**（原型是设计依据，不是代码资产）。但如果原型的做法暴露了
   规范里的错误，改规范并在 §8 记一笔，不要偷偷改原型。
2. **§8「留待验证」里的条目不要当成结论用**。它们是判断把握不足的地方，
   实现前应该先看真实设备上的表现，或者直接来改这一节。
3. **§4 的三条硬规则（焦点栈 / 键位表 / 落点）不是建议，是纪律**。
   它们各自对应一类「看起来能跑、实际不可用」的缺陷，见 §4.8。

## 1. 基调与它带来的四个硬取舍

`PRODUCT.md` §4 与 `AGENTS.md` 的设计基调：**深色优先、等宽字体、高信息密度、键盘优先，
一致交互范式贯穿全站**。

这四个词不是四个审美偏好，是**四个取舍**。每一条都在砍掉某些常见做法：

| 基调 | 它砍掉了 | 代价（我们接受什么） |
|------|---------|-------------------|
| **深色优先** | 主题开关、双主题 token、浅色模式 | 浅色版从未被验证；将来若必须做，要补全语义槽位而不是加 `body[data-theme]` 分支 |
| **等宽字体** | 无衬线的正文可读性优势 | 中文正文在 13px 下阅读密度高、长段落偏累。长说明文案应该被拆短而不是换字族 |
| **高信息密度** | 大点击区、大留白、卡片阴影 | 部分控件命中区只有 26px 高 → 必须有替代路径（搜索过滤、键盘、`⋯` 收拢次要动作） |
| **键盘优先** | 纯 hover 可见的信息、tooltip 承载的唯一信息 | 键盘用户与鼠标用户的路径不完全等价，需要在两处都做（`:focus-visible` 与 `:hover` 同规则） |

**最需要克制的一条**：基调说的是「深色优先」，不是「深色到没有层次」。
本系统的全部空间层次只由四层半表面（`surface-0..3` + `inset`）承担，
相邻层差值极小（ΔL ≈ 0.006），靠**1px 描边 + 2% 层差 + 阴影**三者合力表达。
一旦某处需要「明显更亮」才能看清，正确的做法是改信息密度或改字号，不是加第五层表面。

## 2. 设计 token

全部定义在 `packages/web/src/styles/tokens.css`（129 个变量），那是被 grep 检查的唯一真相源；
原型那份 `prototype/assets/tokens.css` 只是转发 shim（`@import` 生产副本），不再抄一份内容。
下面只写**判断依据**。

### 2.0 三条纪律

1. **语义先于观感。** 产品代码只许用语义槽位（`--af-danger`），
   不许用观感槽位（`--af-red`）；`--af-term-ansi-*` 只许出现在终端渲染层，
   它的含义是「这条字节带的是哪个 ANSI 码」，不是「这条字是红的」。
2. **对比度不是审美。** 每个前景槽位都对着它的合法背景量过（§2.1），
   **没有量过的取值不许进来**。
3. **每个取值后面必须有理由注释。没有理由的取值不许进来。**

### 2.1 颜色：四层半表面 + 四级前景 + 六功能色

**表面**（`surface-0..3` + `inset`）——全站唯一的空间语言：

| 槽位 | 值 | 角色 | 对 surface-1 的 ΔL |
|------|-----|------|------------------|
| `surface-0` | `#080a0d` | 页面底 / 最深的呼吸位 | — |
| `surface-1` | `#0f1318` | 应用外壳：侧栏、顶栏、卡片 | 基准 |
| `surface-2` | `#151a21` | 浮起一层：面板头、选中行、输入框 | ≈0.006 |
| `surface-3` | `#1c222b` | 浮起两层：hover 行、Modal、帮助面板 | ≈0.007 |
| `inset` | `#04060a` | 凹进去：终端画布、代码预览、diff | 更深 |

**为什么 ΔL 这么小**：高信息密度意味着相邻格子要多，格子之间不能再塞明显的分隔带。
层级靠 **1px 描边 + 2% 层差 + 阴影**三者合力。阴影的职责**只**是表达「浮在页面之上」，
所以它只出现在 Modal / 抽屉 / 命令面板 / 键位帮助上——页面内的层级一律不用阴影。

**前景四级**（实测对比度，对着 `surface-1`）：

| 槽位 | 值 | 对 s1 | 用途 | 为什么是这个对比度 |
|------|-----|-------|------|------------------|
| `fg-primary` | `#dde3ea` | 14.42:1 | 标题、值、正文 | 远高于 7:1，正文不需要妥协 |
| `fg-secondary` | `#98a4b2` | 7.36:1 | 标签、次要说明、表格单元格 | 超过 7:1，密排也不累 |
| `fg-tertiary` | `#6a7787` | 4.08:1 | 可选信息：时间戳、计数、单位 | 压在 AA 4.5 门线下，**只许承载小字**（11–12px） |
| `fg-disabled` | `#47515d` | 2.31:1 | 禁用控件文字 | 豁免对比度要求，见 §2.5 |

**为什么 `fg-tertiary` 敢压在 4.5 线下**：WCAG 的门线随字号变。
13px 正文的门线是 4.5:1，但 11–12px 的辅助信息在 4.08:1 下仍可读，
而把它提到 7:1 会让它与 `fg-secondary` 失去区别——四级前景必须真的分四级，
否则「四级」这个设计就落空了。**它的使用范围被限制在小字，这是使用许可不是妥协**。

**描边**（全部远低于 3:1，这是有意的）：`subtle` 1.11 / `default` 1.29 / `strong` 1.69 /
`focus` 10.87 / `disabled` 1.83。

**为什么描边可以是 1.1:1**：WCAG 1.4.11 管的是「必须看懂的东西」。
在一个每个非文本可交互元素都带 ≥4.5:1 文字标签的界面里，
**边界不承担识别任务**——它只是「这里有个东西」的形状提示。
而在密度优先的控制台里，一条 3:1 的黑边会把行与行切碎成一张张卡片，每屏少 3–4 行。
**三条例外必须 ≥3:1**：输入框（框就是控件本身）、焦点态、开关滑块轨道。

**六个功能色**，角色按「用户该做什么决定」分配，不按色相：

| 槽位 | 值 | 对 s1 | 角色 |
|------|-----|-------|------|
| `accent` 青 | `#5fd9c8` | 10.87:1 | 可交互 / 在线 / 焦点 |
| `ok` 绿 | `#3fbf80` | 7.97:1 | 完成 / 已就绪 |
| `warn` 琥珀 | `#e09a30` | 7.84:1 | 等待 / 降级 / 重连中 |
| `danger` 红 | `#e0525c` | 4.91:1 | 阻断 / 越界 / 离线 |
| `info` 蓝 | `#5b9ad8` | 6.27:1 | 说明性（这不是状态，是解释） |
| `agent` 紫 | `#a97ff5` | 6.25:1 | 来自 agent 而非用户的事件 |

**红色的稀缺性是一条设计规则**：`accent` 青与 `danger` 红是对立轴上的一对（品牌 vs 阻断），
所以**一屏里红色的出现次数本身就是告警密度指标**。
把一个「正在正常重试」的状态染红会稀释这个指标的全部价值（§7.3）。

**每个功能色有四个变体**：本体（图形/描边）、`-fg`（小字，提到 ≥7:1）、
`-bg`（12% 底）、`-line`（28% 边）。**小字永远用 `-fg` 不用本体**——
本体的对比度是按图形算的，用在 11px 文字上不够。

### 2.2 字族：整个控制台只有一个字族

**选择**：`JetBrains Mono` → `IBM Plex Mono` → `Noto Sans Mono CJK SC` → 系统等宽。

**五个条件按权重排序**：① 中文必须覆盖（纯拉丁等宽会掉进系统 CJK，
中英基线与字宽都不受控）② `0`/`O`/`l`/`1` 可分 ③ 零连字 ④ 有 CJK 等宽版本
⑤ **不联网**（原型必须双击即开）。

**最重要的连带决定：正文也用等宽（13px），不引入无衬线。**
理由是界面上 80% 的内容天然是等宽内容（终端、`node_id`、路径、版本、日志、树、表格），
混用两套字体会让界面像两个产品的缝合，而等宽里那 20% 的正文反而成了补丁。
`--af-font-sans` 被**刻意定义成 `--af-font-mono`**——换字族是全局决定，
不是「这块用无衬线」的局部决定。

**文字宽度上限 64ch** 就是从 13px 等宽量出来的最宽可读值。
中文在 `Noto Sans Mono CJK SC` 下的字宽是拉丁的两倍，换行位置可预测——这在窄列里比无衬线更好。

### 2.3 字号、行高、字重

**9 档字号 + 4 档行高**。**高信息密度不靠更小的字，靠更短的行**——
13px 是等宽中文长文本的下限，再小笔画就糊。

**所以 13px 必须是读的量最大的那一档的实际基线**，不能只是一个几乎没人用的
「正文」名号：表格主列、树、终端才是这个产品里读得最多的东西，把它们放在
下限之下等于把这条下限用在它自己的例外上。

| 档 | 值 | 用途 |
|----|-----|------|
| `text-2xs` | 10px | **符号与单行注解**：kbd、竖排标签、状态字形、指纹/id、工具提示、对话流的日期与说话人名、把手提示、终端脚注 |
| `text-xs` | 11px | 数字：时间戳、毫秒数、单位 |
| `text-sm` | 12px | 辅助说明、表头、按钮、徽标 |
| `text-md` | 13px | **表格主列、树、终端、正文**（实际基线） |
| `text-lg` | 15px | 面板标题 |
| `text-xl` | 18px | 页面标题 |
| `text-2xl` | 22px | 概览数字 |
| `text-3xl` | 28px | 登录页标题 |
| `text-4xl` | 34px | 原型总览 hero |

**为什么最小两档的许可范围是「符号与数字」而不是「次要内容」**：10px / 11px 都在
13px 下限之下，它们的合法性只能来自「不是长文本」——kbd、竖排标签、状态字形是符号，
时间戳、毫秒、单位是数字，指纹与 id 是等宽字符串。一旦放开到「次要列」「徽标」这种
**会装短句**的位置，它们就会顺着「再小一点更密」的惯性往正文里爬，这正是这张表上一版
（12px 定为表格主列、11px 定为表格次要列）的样子。

**「不是长文本」是可判定的**：这一档的每个位置都必须是**单行、不成句**的注解——
一句话（十几个字连成句）就不合格，哪怕它在视觉上是「次要的」。判据是「这段文字
被读出来时是否需要句子结构」，不是「它是不是重要内容」。

**改字号前先改这张表**：档位的用途写在这里，实现在
`packages/web/src/styles/tokens.css` 的 `--af-text-*`。只改数值不改这张表，
「什么时候该用哪一档」就失去依据，下次还会漂回去。

**4 档行高**：`tight` 1.35（表格、树、终端）/ `snug` 1.5（UI 文案）/
`base` 1.65（说明性散文）/ `loose` 1.8（登录页等需要呼吸的地方）。

**2 档行高常量**：`row-compact` 26px（表格、树、日志）/ `row-regular` 32px（按钮、导航项）。
**为什么只有两档**：第三档必然是「两个档之间的妥协」，而妥协档会被大量使用，
最后变成事实上的默认档——那还不如承认只有两档。

**字重只有 4 档**：400 / 500 / 600 / 700。字重的区别必须与字号或颜色搭配使用，
**单独加粗**不构成层级。

### 2.4 间距、圆角、动效、层级

**14 档间距，2px 基数**：2 / 4 / 6 / 8 / 10 / 12 / 14 / 16 / 20 / 24 / 32 / 40 / 56 / 72。

**为什么 2px 基数**：等宽字体的行高天然是 4 的倍数，2 是能与任何行高对齐
又不产生半像素的最大基数。高信息密度意味着间距要小，但**小不等于不可分辨——
相邻格子至少差一档（2px）**。

**4 档圆角，最大 8px**：`none` 0 / `sm` 2 / `md` 4 / `lg` 8 / `full` 999px。
等宽 + 高密度的界面里大圆角会让格子看起来像气泡，**削弱「这是一张表」的语义**。
8px 只给浮层（Modal / 抽屉 / 面板 / 帮助）。

**3 档 z-index，与焦点栈同构**：`shell` 10 / `sticky` 20 / `drawer` 40 /
`modal` 60 / `palette` 70 / `help` 80 / `toast` 90。
**数字越大 = 越内层 = 焦点优先级越高**。inert 由 JS 管、z-index 由 CSS 管，
**两边必须一致**——否则会出现「焦点在里面、视觉在底下」的撕裂。

**3 档动效**：`instant` 80ms（hover/按下/选中）/ `fast` 140ms（浮层进出）/
`slow` 240ms（抽屉、布局变化）。

**默认无动效。** 动效只用在「状态真的变了」的时刻，且必须能被 `prefers-reduced-motion` 关掉
（tokens.css 里降为 0ms）。**数据刷新不加动效**——那会让「刷新」本身变成一件需要等待的事。

### 2.5 禁用态为什么可以是灰的

禁用控件的文字是 `fg-disabled`（2.31:1），远低于任何对比度门线。这是**豁免**不是妥协，
理由是禁用控件的 WCAG 豁免条款：它不对应任何可执行的操作。

**但禁用态不只靠灰**。三管齐下：

1. **不透明度**（`opacity: 0.5`）
2. **`pointer-events: none`**
3. **`aria-disabled="true"`**

**为什么三样都要**：只变灰的禁用态在**色觉障碍用户**眼里与可用态几乎无异；
只加 `pointer-events` 的禁用态在**键盘用户**眼里仍然可聚焦。
`aria-disabled` 让屏幕阅读器读出「不可用」，而不是让用户自己发现按了没反应。

**而且每个禁用控件旁边必须有理由文字**——见 §7.4 第④路。
「灰着但不说为什么」会让用户去改终端、去换路径、去重启，做一堆与根因无关的操作。

## 3. 基础组件契约

22 组组件，全部在 `packages/web/src/styles/components.css`（22 节：§0 复位 + §1–21 组件）；
原型那份 `prototype/assets/components.css` 同样是转发 shim。
状态一律用 `data-*` 属性表达（`data-state` / `data-open` / `data-inert` / `data-tone` /
`data-level`），**不用 JS 加 class**——class 是样式实现，`data-*` 是契约。

**两条组织纪律**：

1. **每个组件的四态（hover / active / focus / disabled）在同一个块里写完**，
   不允许散到文件末尾的「状态补丁」区——那是状态漏画的开始。
2. **焦点态不在组件里重复定义**（tokens.css §13 已全局统一），
   组件只负责「别把它盖住」：不写 `outline: none`，
   不加 `overflow: hidden` 到聚焦元素的外层容器。

### 3.1 Button

- **尺寸 3 档**：`sm` 22px（行内、表格里）/ 默认 26px / `lg` 32px（认证页）。
- **变体 4 个**：`default`（surface-2）/ `primary`（accent 底 + 深字）/
  `danger`（danger-bg 底）/ `ghost`（无边框）。
- **四态一次写完**。`primary` 的三态是**同色相的三档亮度**（hover 提亮、active 回落），
  不换色相——换了色相用户会以为是另一个按钮。
- **文字永远不换行**（`white-space: nowrap`）；按钮宽度由内容定，不设固定宽。

### 3.2 Input / Select / Textarea / 字段

- 输入框高度 = `row-compact`（26px），与表格行高对齐。
- **框就是控件本身，所以边界 ≥3:1**：hover 时边框提到 `--af-border-strong`，
  focus 时边框变 `--af-accent` **加** 2px 焦点环（双保险）。
- 错误态用 `aria-invalid="true"` + `--af-danger` 边框 + `af-field__error` 文字，
  **三者同时出现**。只给红框不给文字，用户看不到错在哪。
- 字段三段式：label / 控件 / hint 或 error。**hint 与 error 不同时出现**——
  出错时 hint 被 error 替换，不是两者叠在一起。

### 3.3 Checkbox / Radio / Switch

**全部 `appearance: none` 自己画**——系统默认样式在暗底上不可见
（Windows 深色模式下的 checkbox 是一个亮灰方块）。

- Checkbox 14×14px，勾用旋转 45° 的两段边框。
- Radio 圆形，选中态用 `inset` 圆点。
- Switch 30×16px，滑块轨道是控件本体 → **边界 ≥3:1**。

### 3.4 StatusDot / State / Badge

**状态是四通道：颜色 + 字形 + 填充 + 必带文字。**

| 状态 | 色 | 字形 | 文字 |
|------|-----|------|------|
| `online` | ok 绿 | `●` 实心 | 可省（颜色+字形已够） |
| `reconnecting` | warn 琥珀 | `◐` 半轮（走带动画） | **必带**「重连中 + 已重试时长」 |
| `offline` | danger 红 | `○` 空心 + 斜纹 | **必带**「离线」 |
| `unknown` | fg-tertiary 灰 | `◌` 虚点 | **必带**「状态未知」 |
| `active` | ok 绿 | `●` 实心 | 可省 |
| `disconnected` | warn 琥珀 | `◐` 半轮 | **必带**「断线」 |
| `ended` | fg-tertiary 灰 | `○` 空心 | 「已结束」 |

**为什么四通道**：色觉障碍（最常见的红绿色觉障碍恰好命中我们最关键的一对）、
灰度打印、8px 缩略图、`prefers-reduced-motion`（走带动画没了）——
任一条件下颜色单独都不够。**任何一个通道都不单独承担识别。**

**Badge 是另一种东西**：它标注一个**属性**（`M2`、`路径锁定`、`推`），
不是状态。`af-badge--off` 表示「此阶段不做」，不是「状态未知」。

### 3.5 Panel

**head 固定，body 滚动**——长内容不能把标题顶出视野。

- 面板是「一块有标题的内容区」，**不是**卡片：卡片有阴影有内边距，面板有边框没有阴影。
- `af-panel__state` 是面板顶部的状态条（不是 body 的一部分），
  用来表达「这个面板连上了吗」而不占用内容区。

### 3.6 Tabs

**只有真的互斥时才用 tabs。**

**终端与文件是同时看的 → 不用 tabs**（§7.1）。这是本页最容易被违反的一条：
「顺手做成 tab」是原型里最常见的形状退化。

tab 用 `role="tablist"` / `role="tab"` / `aria-selected`，
**不是** `[aria-pressed]`。两者的语义不同：tab 是「在几个视图里选一个」，
pressed 是「这个开关开着吗」。

### 3.7 Table

- **紧凑行高 26px**——一屏能放更多行。
- **选中行走 `aria-selected`**（辅助技术可读），不只是加背景色。
- `data-inert="true"` = 降亮但**不禁用**——离线设备仍可选中复制它的 `node_id`。
  真正禁用会让用户连想复制个设备名都做不到。
- 表头 `position: sticky` + `--af-z-sticky`。

### 3.8 Tree

**每一行是 `<button>`，不是 `div`。**

这是本设计里最重要的一条组件纪律：按钮天然 Tab 可达、Enter 天然触发、
屏幕阅读器天然播报「按钮」。上一版用 `div` + `tabindex="-1"` + 全局 Enter 代理，
结果是 **Tab 根本进不去那棵树**——键盘用户完全无法使用文件树。

- 行结构：`twisty`（12px）+ `name`（`flex: 1`）+ `meta`（右对齐，等宽数字）。
- 目录用 `aria-expanded`，展开状态影响 `twisty` 的旋转。
- **被排除的节点照常显示**（斜纹底 + 删除线 + `⊘` 前缀），**不隐藏**——
  理由见 §7.4。

### 3.9 Toast

**分两类，这是语义不是样式**：

| | 自动消失 | sticky（不消失） |
|---|---|---|
| 用于 | 已经成功的通知 | **可恢复的失败** |
| 角色 | `role="status"` | `role="alert"` |
| 动作 | 无 | 至少一个按钮 |

**离线、越界、保存冲突走 sticky**：这三件事都需要用户做什么，
自动消失的提示等于「用户还没反应过来就消失了」。

- 位置固定右下，不跟随滚动。
- **Toast 是唯一不参与焦点栈的浮层**——它抢焦点会打断正在输入的用户。
  所以 toast 里**不许**放需要立即响应的唯一控件。
- 每次创建时按 sticky 决定 `role`，不是事后改。

### 3.10 Modal / 抽屉 / 命令面板 / 焦点陷阱

**三个都走焦点栈**（§4.1）。CSS 只负责层级与外观，**JS 负责背后 inert 与焦点返回**。

- **禁止缓存 focusables 快照。** 每次 Tab 重新查。
  快照在模态 `innerHTML` 重写后失效，圈住的是上一批按钮——
  上一版 `trapFocus` 就是这么坏的。
- Modal 页脚**只有**「取消 / 确认」两种，加一个危险动作。
  第三种按钮会让「这个按钮会做什么」变得不可预测。
- 命令面板层级高于 Modal（`palette` 70 > `modal` 60）——它是模态的替代品，不是补充。

### 3.11 EmptyState

**文案三段式**：字形 + 标题 + **下一步**。

```
▢
没有进行中的会话
在设备上开会话就会出现在这里。→ 新建会话
```

**空态必须给出路**。只说「这里是空的」等于把「然后呢」留给用户自己想。

### 3.12 Skeleton

**空态 = 「这里本来该有东西但没有」；骨架 = 「正在加载」。**

两者必须一眼能区分，否则用户分不清「等一等」和「没有了」。
骨架走 shimmer 动画，**尊重 `prefers-reduced-motion`**。

**已知不足**：骨架的宽度分布来自假数据，真实实现应该按内容的典型行宽生成。

### 3.13 Tooltip

**键盘用户也要看得到**：tooltip 在 `:focus-visible` 时同样出现。

**且 tooltip 内容必须同时存在于 `aria-label` 或正文里**——
不许让信息只活在 hover 中。这是「键盘优先」最常被绕过的一处：
设计时想着 hover，实现时忘了 focus。

### 3.14 文件预览：必须给结论

**不许只显示「无法预览」**。三档结论，每档给下一步：

| 情形 | 显示 |
|------|------|
| 正常文本 | 内容 + 行号 |
| `> 1 MB` | 只读前后各 4 KB + 中间「已截断，N 行未显示」+ **「编辑整份请让 agent 做，浏览器不是 IDE」** |
| 二进制 | 类型 + 大小 + 「不支持预览」 |

**为什么大文件不整份载入**：它是远程资源，1 MB 意味着 WebSocket 上的一个整帧
（约束 4：每通道独立流控）。而且它在浏览器里编辑整份文件没有意义——
本项目的执行主体是 agent。

### 3.15 拆分把手与尺寸轨道

**把手必须可聚焦**：`tabindex="0"` + `role="separator"` + `aria-orientation` +
`aria-valuenow/min/max` + **方向键调尺寸**。

**上一版的把手是鼠标专属的**（没有 `tabindex`、没有 `role`），
而「可拖拽」是写在设计决断里的——键盘用户根本调不了分栏宽度。

### 3.16 只读遮罩

**断线冻结用「压一层极淡斜纹」而不是盖遮罩。**

遮到不透明等于清屏，而 `PRODUCT §3.3` 流程 7 明确承诺「显示最后已知状态」，
清屏会毁掉这条承诺。斜纹是「这里盖着什么」的形状信号，纯暗底像「这里没了」。

遮罩中央**必带一句事实**：「设备上它还活着，Hub 暂时够不着」。

### 3.17 退避走带

指数退避的等待**不是「转圈圈」**——让用户看见「下一次重连在什么时候」。

### 3.18 Kbd

`kbd` / `.kbd`：18px 高、`border-bottom-width: 2px`（物理键帽感）。
**kbd 内容必须与键位表一致**——页面上写 `<kbd>g s</kbd>` 而表里没有 `g s`，
就是 §4.2 禁止的那种漂移。

### 3.19 认证页布局

**登录 / setup 是仅有的两个「宽屏也居中窄列」的页面。**

单用户自托管下**没有第二个人在看**，宽屏铺满只会让一个表单显得慌张。
背景用一层极淡的 accent 径向渐变暗示方向，不做插画。

**密码强度条四级，用 `aria-live` 播报**——只靠颜色传达强度会把色弱用户排除在外。

### 3.20 命令面板

浮层里输入即筛选，`↑↓` 选，`⏎` 执行，`Esc` 关闭。

**命令面板里只列「现在能做」的命令**，不列当前页面不适用的——
一个灰掉的命令项等于在告诉用户「这里本来该有功能」。

### 3.21 禁用清单（这些组件**不存在**）

写在这里是为了让实现阶段的人知道「不是漏了，是不许有」：

- **没有卡片阴影组件**——层级靠表面色差（§2.1）
- **没有圆角 > 8px 的容器**
- **没有双主题切换**——深色优先是范围选择（§1）
- **没有 hover 才可见的唯一信息**——键盘用户看不见
- **没有模态页脚第三种按钮**
- **没有设备级的工作区页面**——见 §5.2 的否决项
- **没有把 terminal/files 做成 tabs**——它们是同时看的（§7.1）

## 4. 交互范式

**这一节是本规范里最该被实现者逐条对照的一节。**
§4.1–4.3 是**硬规则**，违反它们的界面会「看起来能跑，实际不可用」。

### 4.1 焦点栈：焦点归最内层活动容器

**规则一句话**：焦点归**最内层活动容器**。容器打开时背后全部 `inert`，
容器关闭时焦点还给打开它的那个元素。

```
push(container, opener)   打开浮层：背后 inert，焦点移入容器
pop(container)            关闭它：背后解除 inert，焦点还给 opener
```

**为什么用原生 `inert` 而不是手工 `aria-hidden` + `tabindex`**：
`inert` 同时管**焦点、指针事件、辅助树**三处。
手工管三处必然漏一处——漏了指针事件就会出现「背后看不见但点得到」的幽灵控件。

**为什么每条关闭路径都必须走 `pop()`**：
Esc、点遮罩、点关闭按钮、路由跳转前——四条路四条实现，
只要有一条忘了还焦点，键盘用户就「丢了」。所以**关闭必须只有一条路**。

**焦点还给 opener 时的兜底**：opener 可能已经被移除（比如点它的那一行刚被删了）。
这时退到 `main[tabindex="-1"]` 而不是留下悬空引用。

**焦点陷阱每次 Tab 重新查**（§3.10），且**焦点不在容器内时拉回第一个**
（用户可能从地址栏回来了）。

### 4.2 键位表即文档

**规则一句话**：`?` 面板由 `KEYS` 表渲染，所以「文档写的键位」与「按下会发生的键位」不可能漂移。

三个配套约束：

1. **注册不存在的 act 会抛错**（`AF.register` 检查 act 在表里）。
   写不进来的 handler 说明键位表漏了——而漏了的键位用户找不到。
2. **表里有 act 就必须有 handler**，`AF.unimplemented()` 列出缺失项并在控制台报警。
3. **一个 act 不许注册两次**。上一版两个页面各注册一个 `dock:open`，
   行为取决于加载顺序，**没有任何提示**。

**为什么不允许「表外键位」**：用户能发现的键位 = 能查到的键位。
一个不能被 `?` 查到的键位，对键盘用户等于不存在。

**当前键位表（22 个 act）**：

| 组 | 键位 | act | 说明 |
|----|------|-----|------|
| **全局** | `?` | `help:toggle` | 打开 / 关闭键位帮助 |
| | `/` | `search:focus` | 聚焦搜索框 |
| | `Esc` | `layer:escape` | 关最上层浮层；无浮层时取消选中 |
| | `Tab` | `focus:next` | 焦点前进（有浮层时在浮层内循环） |
| | `⇧Tab` | `focus:prev` | 焦点后退 |
| | `⌃B` | `rail:toggle` | 折叠 / 展开侧栏 |
| **跳转** | `g s` | `nav:sessions` | 会话列表 |
| | `g n` | `nav:new-session` | 新建会话 |
| | `g d` | `nav:devices` | 设备列表 |
| | `g a` | `nav:agents` | Agent 目录 |
| | `g ,` | `nav:settings` | 设置 |
| **列表 / 树** | `↑ ↓` / `j k` | `list:move` | 移动焦点行 |
| | `⏎` | `list:enter` | 进入选中项 |
| | `Space` | `list:toggle` | 展开 / 收起，或多选切换 |
| **会话工作台** | `o` | `panel:open` | 打开一个面板 |
| | `[` `]` | `panel:prev` / `panel:next` | 切换已打开的面板 |
| | `\` | `dock:toggle` | 打开 / 收起面板坞 |
| | `t` / `g g` | `traj:toggle` | 轨迹抽屉 |
| **终端** | `⌃L` | `term:clear` | 清屏 |
| **文件** | `⌃S` | `file:save` | 保存当前文件 |
| | `Backspace` | `file:up` | 回到上一级目录 |

**为什么只有 22 个而不是更多**：上一版有 31 个键位，其中 **15 个没有 handler**
（按了没反应），还有 5 个走 `g` 前缀序列却没有取消路径。
**键位不是功能清单，是承诺**——每一个键位都是一句「按这个会发生某事」，
写不出那句承诺的键位就不该进表。

**`g` 序列的纪律**：
- 800ms 窗口。
- **没配上的第二个键不吞**——用户只是在打一段以 `g` 开头的字。
- `g g` 与 `t` 是同一个 act 的两个键位（alias），这是允许的；
  但**两个 act 共用一个键位描述**会在表构建时抛错。

**scope 的语义**：表里声明了 scope（`list` / `session` / `panel`），
但**生效与否由「本页有没有注册 handler」决定**。
所以「在设备页按 `o` 没反应」是**正确行为**（键还给了浏览器），
不是上一版那种「表里有、实现里没有」的死键。

**输入区判定**：单键（`?` `/` `o` `t` `[` `]` `\` `j` `k`）
在 `input` / `textarea` / `select` / `contenteditable` 内**一律不抢**。
修饰键（`⌃B` `⌃L` `⌃S`）**照常生效**——用户可能在终端里按它。
中文拼音选字期间（`e.isComposing`）全部让路。

**Space 的例外**：有按钮/链接聚焦时 Space 是「按下按钮」，不抢。

### 4.3 跳转后焦点有确定落点

**规则**：每个页面的主区是 `main[tabindex="-1"]`，页面加载后由外壳统一聚焦它。

```js
main.focus();                                   // 把焦点从 <body> 拿出来
main.querySelector('h1').tabIndex = -1;         // 让「⇧Tab 回标题」成为可能
```

**为什么必须显式做**：
上一版 12 个页面 **0 个 `autofocus`、0 个 `main[tabindex="-1"]`**。
跳转后焦点回到 `<body>`，于是：
- 屏幕阅读器**不播报**「你到了一个新页面」；
- 键盘用户第一次按 `Tab` 回到侧栏，得 Tab 过整个导航才到内容；
- 后续所有键位都作用在一个「不知道焦点在哪」的页面上。

**为什么用 `main` 而不是 `h1.focus()`**：`main` 的 `tabindex="-1"` 是
「这里是一片内容的起点」的语义，比「这里是标题」更准确；
而 `h1` 单独给 `tabindex="-1"` 是为了让 `⇧Tab` 能回到标题（跳过的链接列表）。

**认证页与元页面**（`index.html` / `components.html` / `login.html` / `setup.html`）
不用外壳，但同样有 `main[tabindex="-1"]`——**规则不因页面类型而豁免**。

### 4.4 列表导航：标准 listbox 模式

**容器是一个 tab stop，行是 `tabindex="-1"`**：

```html
<div data-role="list" tabindex="0" role="listbox" aria-label="设备">
  <button data-row tabindex="-1" role="option" aria-selected="false">…</button>
</div>
```

- `Tab` 进容器，**焦点由容器交给当前行**（没有当前行就第一行）。
- `↑↓` / `j k` 在行间移动焦点并写 `aria-selected`。
- `⏎` 的语义由行自己决定：`data-href` 跳转 / 内含 `a` 或 `button` 就点它 /
  否则抛 `af:enter` 事件给页面接。
- `Esc` 取消选中（焦点留在容器上）。

**否决「全局 Enter 代理」**：上一版靠一个全局 keydown 猜「用户想激活什么」，
于是 Enter 在输入框里、在按钮上、在树里行为都不一样。
**Enter 的语义属于行，不属于键盘监听器。**

**树同构**：容器是 `[data-role="tree"]`，目录行用 `aria-expanded`，
`Space` 展开 / 收起。

### 4.5 焦点环

**全站只有一条**（tokens.css §13）：

```css
:where(a, button, input, select, textarea, [tabindex]):focus-visible {
  outline: 2px solid var(--af-border-focus);
  outline-offset: 2px;
}
```

**为什么用 `outline` 而不是 `box-shadow`**：
`outline` 不会被父容器的 `overflow: hidden` 裁掉，
且在 Windows **高对比度模式**下仍然可见（`box-shadow` 会被强制颜色模式吃掉）。

**为什么用 `:focus-visible` 而不是 `:focus`**：
`:focus-visible` 由浏览器判定（按过键盘就显示，点过鼠标就不显示），
**不靠我们记「上一个输入设备是什么」**——那种状态在多窗口、多设备下必错。

**`forced-colors: active` 时描边全部提到 `CanvasText`**：
密度优先的界面在高对比度下会「看不见边界」，这个模式下刻意放弃密度换可读性。

### 4.6 密度档

**只有两档**：`row-compact` 26px（表格、树、日志、工具调用块）/
`row-regular` 32px（按钮、导航项、表单）。

**为什么不做三档**：第三档必然是两个档之间的妥协，
而妥协档会被大量使用，最后变成事实上的默认档（§2.3）。

### 4.7 错误态的两种语义

| | **可重试** | **不可重试 / 需要别的动作** |
|---|---|---|
| 形态 | 输入框边 + 错误文字（就地） | 模态解释面板 或 sticky toast |
| 例子 | 密码错、字段校验失败 | Hub 未初始化（该跳 setup）、离线（该重连）、越界（该换工作区） |
| 下一步 | 重试 | **换一个动作** |

**五种登录错误必须分开呈现**（`login.html`）：密码错 / Hub 未初始化 /
会话失效 / 429 限流 / 无错。
**把它们压成一句「登录失败」等于把「下一步该做什么」还给用户瞎猜**——
未初始化要跳 setup，限流要告诉用户等多久，两者都需要不同的动作。

**setup 的三种失败同样分开**（`setup.html`）：token 不匹配 / 已失效被锁 /
Hub 已初始化，各给**下一步命令**。

### 4.8 空态与加载态的分工

见 §3.11 / §3.12。**一句话**：空态回答「这里本来该有东西但没有」，
骨架回答「正在加载」。混用会让用户以为东西没了。

## 5. 信息架构与页面

### 5.1 导航骨架

```
┌──────┬──────────┬────────────────────────────┐
│ 图标 │  侧栏    │  顶栏：面包屑 / 搜索 / ?     │
│ 轨   │  （可折叠）│────────────────────────────│
│      │          │                            │
│      │  一级导航  │         主区                │
│      │          │      （焦点落点）             │
├──────┴──────────┴────────────────────────────┤
│ 状态条：Hub 状态 · 全局键位提示                │
└───────────────────────────────────────────────┘
```

### 5.4 会话工作台

```
┌────────────────────────────────────────────────────────┐
│ 会话标题 · 状态 · 设备 · agent · 路径（锁定）· 打开面板  │
├────────────────────────────────────────────────────────┤
│ [● 修 ws 断线重连 1 ✕] [◐ 重构 hub-storage ✕] …          │  ← 会话 tab 条
├──────────────────────────┬───┬─────────────────────────┤
│                          │   │ 面板坞标签：终端 / 文件   │
│   对话流（左，56%）        │把 │  ┌───────────────────┐  │
│   User / Agent / Tool     │手 │  │                   │  │
│   / System                │ ⇔ │  │    面板内容        │  │
│                          │ ⇔ │  │                   │  │
├──────────────────────────┤ ⇔ │  └───────────────────┘  │
│  输入区                   │   │                         │
└──────────────────────────┴───┴─────────────────────────┘
                            └─ 轨迹抽屉（覆盖层，不是第三栏）
```

**对话与面板并置**，理由见 §7.1。面板坞**默认关着**——
它是「对话过程中按需打开」的，不预开。

**轨迹是抽屉不是第三栏**：轨迹 = `trajectory_event` 的 append-only 流水，
对话是它按 kind 折叠后的读法。做成两个 tab 会暗示「两套不同的数据」，
于是用户去比「对话里有几条、轨迹里有几条」——而它们本来必须逐条对齐。
第三栏又会把对话挤到 1/3 屏宽。

轨迹列表每行带齐审查维度第 7 条要求的五项：`seq` / `kind` / 内容 / 耗时 / 归属。

**轨迹抽屉在 M1 恒空，空态文案是定死的**（M1 子任务 13d 定稿，UI 与文档
必须逐字一致，两边任一处改了都要同步改另一处）：

| 字段 | 文案 |
|------|------|
| 标题 | **M3 起有数据** |
| 正文 | 轨迹是 `trajectory_event` 的 append-only 流水，对话是它按 kind 折叠后的读法；M1 的会话容器不产生这条流（ACP 归 M3）。这里不画假行。 |

三句各回答一个不同的问题，缺任何一句空态都会被读错：
「M3 起有数据」回答**这是暂时的还是坏了**（前者）；
第二句回答**轨迹和对话是什么关系**（同一条流的两种读法，不是两套数据）；
「这里不画假行」回答**为什么这一块什么都不显示**（不是加载失败、不是还没滚到）。

**把手**在断线时**不冻结**（设备状态与布局状态是两件事）。

### 5.5 会话 tab 条：同时看多个会话

**能同时开多个会话**，切换器是 tab 条，紧贴在工作台标题栏下方、
与它共享同一条发丝线（两块读起来是一整块 chrome）。

#### 5.5.1 三个必须先定的语义

| 问题 | 结论 | 理由 |
|------|------|------|
| **切 tab 会关面板吗** | **不会**。tab 是**视图切换器**，不是生命周期边界 | 边界是「关掉这个 tab」或「离开会话列表」。否则来回切两次就重建 PTY，用户丢掉了刚跑出来的输出 |
| **有代价吗** | **有**：N 个 tab = N × 面板数条活跃通道 | 所以每个 tab 显示自己的**面板数徽标**——**让代价可见**，而不是让用户猜。**且**：同设备的所有通道共享一条读侧令牌桶（`protocol.md` §6.1，每连接 4 MiB 突发 / 1 MiB 每秒回补），并发输出的总吞吐有上限——N 个会话同时输出时，实时性随 N 线性退化，不只是「通道数变多」 |
| **切 tab 后焦点去哪** | **进工作台正文**，不回 tab 条 | 用户意图是「去那儿干活」，不是「继续看标签栏」。`⇧Tab` 一步回到 tab 条 |

#### 5.5.2 每个 tab 持有自己的一份会话状态

这是「支持多个」的全部技术代价。如果只有一个全局 `state`，
切到 B 会把 A 的面板、终端内容、文件树目录全冲掉——于是
「支持多个」只剩一条 tab 条，是个假的。

所以会话状态挂在 **tab 对象**上（`{ dock, panel, mounted }` + 终端输出 + 文件树 cwd），
由 `activateTab(id)` 整体换掉。终端输出与目录位置**存回 tab**，
这样切走再切回来时**滚动记录还在**。

#### 5.5.3 键盘

整条是**一个 tab stop**（roving tabindex，只有当前 tab 是 `tabindex=0`）：

| 键 | 行为 |
|----|------|
| `←` `→` | 移动**并激活**（像浏览器 tab 条） |
| `Home` `End` | 两端 |
| `Delete` | 关当前 tab |
| `⇧Tab` | 从工作台正文回到 tab 条 |
| `Tab` | 走到关闭按钮 |

**为什么移动即激活而不是「移动后再按 ⏎」**：切一个 tab 便宜且可逆
（不丢任何状态），没有理由让用户多按一次；真正不可逆的动作（关 tab）才需要停顿。

#### 5.5.4 关闭按钮必须是真 `<button>`

```html
<div class="af-tab">
  <button class="af-tab__label" role="tab" aria-selected="true" tabindex="0">…</button>
  <button class="af-tab__x" aria-label="关闭会话：…">✕</button>
</div>
```

**否决** `<span role="button">` 塞在 tab 按钮里：那样它既不在 Tab 序列里
（父按钮把它从顺序里拿走了），又让父元素的 `:focus-within` 永远不成立——
于是「键盘用户能关掉一个会话」这件事在**结构上**做不出来。
关闭会释放通道、丢未保存改动，是**不可逆**动作，不许是鼠标专属。

**没有全局的关闭快捷键**：`⌃W` 是浏览器的，拦不住；
把一个冲突的键绑到不可逆动作上比不给键更危险。

#### 5.5.5 关 tab 的落点

关掉当前 tab → 落在**原位置的右邻**，关掉最后一个就落在**左邻**。
落点 tab 的名字按钮获得焦点（焦点必须落在能解释「发生了什么」的地方）。

**索引必须在过滤前取**：过滤之后数组里已经没有这个 tab，
再 `indexOf` 会得到 `-1`，于是「该激活哪一个」永远算错。
这是本节唯一一个实现期真出过的 bug，记在这里因为它**看起来不像 bug**——
它只在「关掉最后一个 tab」时表现成跳错会话，更早的时候完全正常。

#### 5.5.6 tab 条不是可寻址对象

`/sessions/:id` 只表达「**激活**这个 tab」，不表达「第 3 个 tab」。
**tab 集合本身不可深链接**——你不该能链到「第 3 个标签页」。
（原型不实现集合持久化；实现阶段的落点是 `sessionStorage`，刷新后仍开着。）

#### 5.5.7 未选中 tab 的离线标记

未选中的 tab 若其设备离线/重连中，**左边一道 1px 色标**
（红 / 琥珀），选中态不给——选中 tab 的底色已经是页面色，
再叠一条红边只会把它与其他 tab 的区别搅浑。tab 条上**不写动画**：
重连抖动每 1.4s 跳一次，一排同步闪烁的点会被读成「界面在闪」。

## 6. 数据契约

Mock 形状 = 将来 API 的形状。前端只读。

### 6.1 `GET /api/devices` → `DeviceSummary[]`

```jsonc
{
  "id": "dev-mbp",              // node_id，永不变（升级只换 worker）
  "name": "mbp.local",
  "platform": "darwin/arm64",
  "agent_version": "0.1.0",
  "status": "online",           // online | reconnecting | offline
  "last_seen": "12s",           // 人读格式；API 应给 ISO 时间戳
  "cpu": 34,                    // 0–100，来自心跳能力上报
  "mem": 61,
  "gpu": false,
  "agents": ["claude-code"],    // 已装且就绪，不是「支持」
  "derived": false              // true = status 是前端自推的，非持久化
}
```

**`reconnecting` 只在 Hub 内存里**（WS 断开 + 心跳年龄 ≤45s 由前端自推），
所以它标 `derived: true`，UI 上带一个「推」徽标——
**让用户知道这个状态的来源比让他知道状态本身更重要**。

**`agents` 是「已装且就绪」不是「支持」**：目录里出现一个 agent
意味着用户现在可以用它开会话。

### 6.2 工作区

**工作区不是一个可获取的对象**，它只是会话上的一个字段：

```jsonc
{ "id": "s-7f3a", "path": "~/src/AgentFleet", "path_locked": true }
```

`path_locked` 恒为 `true`：**路径是创建期输入，建立后只读**。
不可变 ⇒ 会话无法退化成多资源句柄 ⇒ 设备级管理台在结构上不可能出现（约束 3）。

**落库模型与这条不矛盾**：Hub 库里 `workspace` 表是主实体、`session.workspace_id`
引用它（子任务 5c 的裁决），但**「主实体」是存储层的事，不是可寻址的事**——
没有 `GET /api/workspaces`，工作区没有路由、不能收藏、不能跳转。
页面上它出现的地方只有两处：`GET /api/sessions` 的每一项里，以及
`POST /api/sessions` 的响应里。所以 M1 的 `/api/sessions` 每一项带
`workspace { node_id, path, path_locked }`（`node_id` 在前，因为通道键是
`(node_id, channel_id)`，约束 4）。

## 7. 八个设计决断

这一节是本规范里最该被挑战的部分。每条给出**选择、理由、以及被否决的方案**。

### 7.0 入口是会话还是工作区

**选择**：入口是**一次对话**；工作区没有页面、没有路由。

**否决**：**「设备 → 工作区 → 面板」三级入口**。

它的致命处不在难用，在于**工作区一旦是页面，就成了可枚举、可跳转、
可长期持有的句柄**——而「设备级的多资源长驻管理台」正是 `AGENTS.md` 约束 3
明文排除的形态。

把工作区降格为**建会话时的一个输入**（第三步选路径），
它就成了会话的属性而不是目的地；面板于是在对话过程中打开，离开会话即消失。

**约束从「靠纪律遵守」变成「靠结构保证」**——这是本设计里最重要的一次取舍，
它同时决定了 §5.2 的路由表。

### 7.1 会话工作台的布局：双面板并置 + 可拖拽分栏

**选择**：对话在左（默认 56%），terminal / files **空间并置**在右，中间一条可拖拽把手。

**否决**：

- **标签页**（terminal / files / git 三个 tab）：终端与文件是**同时看**的两件事——
  改代码 → 跑命令 → 看报错。tabs 把它们变成互斥视图，等于强迫用户来回切，
  而每次切换都要重新建立视觉定位。高信息密度在这里与互斥视图直接冲突。
- **终端主区 + 文件侧栏**：文件树的内容宽度由**路径**决定，路径经常被省略号截断。
  侧栏宽度一旦小于 320px，路径就变成「srv/ag…」，用户失去判读依据。
  而终端需要的恰好是宽度。两者都要宽度 → 必须能由用户自己分配 → 必须是可拖的。

**为什么并置不违反「进入才建通道、退出即释放」**：面板通道按 panel **懒建立**——
第一次与它交互才 `open_channel`，关闭该面板才 `close_channel`。
并置只影响布局，不影响建通道的时机。

**为什么并置是并置而不是叠加**：叠加意味着两个面板在同一个位置
互相遮挡，用户永远只能看到一个——那就等于 tabs，只是更难切换。

**把手键盘可操作**（§3.15）：`←→` 调 4%、`Home`/`End` 到 30%/70%。

**响应式**：< 900px 时面板坞覆盖式展开（对话全宽）。
**下界定在 900px 而不是 320px**：这个控制台是「笔记本 / 大屏」优先的，
树莓派本身可能没有浏览器。

### 7.2 工作区生命周期的可见性：给三个字，不给 channel_id

**选择**：面板头右侧一个**状态标签**——`建立中` → `已连接`，关闭面板时变 `已释放`。

**否决**：

- **完全不可见**：像本地程序一样「打开就有」。但这里的资源是**远程的**——
  通道建不出来时用户看到的是一个不响应的输入框，而「为什么」只能靠猜。
- **常驻显示 channel_id / 信用余额 / 帧计数**：那是排障信息，不是状态信息。
  把它们放前面等于每个用户都要读一遍自己不需要的东西。
  调试信息要放在**主动去看的地方**（顶栏状态条、`?` 面板、未来的 `afhub log`）。

**面板头左侧重复会话的工作区路径**——同时开两个终端时必须能一眼分清它们。

**「退出即释放」怎么表达**：关闭面板是一个**显式动作**，
动作完成后该面板头立刻变 `已释放`，并在 toast 里说「重新打开会按 `(node_id, path)` 重建」。

这比在用户准备关闭时弹一个确认框更诚实——关闭面板不是不可逆动作，没有理由拦着。

**只有「结束会话」才要确认**（它会关掉终端 PTY、丢弃未保存改动）。

### 7.3 断线态：reconnecting 不阻断，offline 才冻结

**选择**：两种断线态**视觉与行为都不同**。

| | reconnecting（WS 刚断，< 45s） | offline（心跳超 45s） |
|---|---|---|
| 颜色 / 字形 | 琥珀 / `◐` 走带 | 红 / `○` 空心斜纹 |
| **终端输入** | **不禁用** | **冻结** + 斜纹只读遮罩 |
| 解释文案 | 「设备上的 shell **仍然活着**，所以这里**不禁用输入**」 | 「设备上的 PTY 仍然活着，Hub 只是暂时够不着」 |

**这是本设计最容易被做错的一格，理由是架构文档里写明的**：

> `security-and-lifecycle.md` §5：调度硬过滤把 `reconnecting` **视为可用**——
> PTY 活着、工作区活着、会话活着。

所以在 45s 判离线之前冻结终端是**与架构文档矛盾的**：
那会把一台调度器仍认为可用的设备，在 UI 上表现为一台死设备。
而且它对用户是错的——他刚敲的命令可能正在设备上正常跑着。

**代价与补偿**：这段时间里下行输出会丢（PTY 流不重传，`protocol.md` §7），
所以状态条给出**丢帧数**。这不是「加个提示就完了」，
它是一个「不冻结 + 明确标注不确定性」的组合。

**只读态要让用户看懂「为什么不能敲」**（不是只把输入框变灰）：

1. **遮罩上写清楚三件事**：状态（离线）、事实（设备上的进程还活着）、
   **边界**（Hub 够不着，期间禁止新操作）。
2. **保留最后已知内容且可全选复制**——`PRODUCT §3.3` 流程 7 明确承诺
   「显示最后已知状态」。遮到不透明等于清屏，清屏会毁掉这条承诺。
3. **斜纹底而不是纯暗底**（§3.16）。
4. **语义上区分两种「不能动」**：离线是**暂时**的（给「立即重连」），
   未保存是**持久**的（给理由而不给重连）。

**转 offline 的判据用 45s 而不是「3 分钟」**——`security-and-lifecycle.md` §5
明确否掉了 3 分钟那套时钟（判定只看心跳年龄，因为设备可能心跳超时但重连成功，
此时连接是通的，标 offline 会让调度把它排除）。
**`PRODUCT.md` §3.3 流程 7 已按此对齐**（M1 子任务 1 消解 §8.1 第 1 条时改）。

### 7.4 越界的可见反馈：四路证据

**选择**：不是「路径高亮」也不是「错误提示」，而是**四路同时在**。

| 路 | 形态 | 管什么 |
|----|------|--------|
| ① 树上的标记 | 斜纹底 + 删除线 + `⊘` + 「不可进入」 | 持续可见的**事实**：「这个目录里有些东西我进不去」 |
| ② 面包屑 | 每一层都可见，越界那一层标红 | 边界被**画出来** |
| ③ 点击的反馈 | 解释性错误面板：为什么进不去 + 怎么才能进去 | **导航越界**给下一步动作 |
| ④ 写操作的 409 | 就地错误块 + 输入框标红 + `path_outside_root` | **写越界与导航越界分开**，因为下一步不同 |

**否决**：

- **只给错误提示**：提示只在用户撞上它的那一刻出现。
  「这个目录里有些东西我进不去」是需要**持续可见**的事实，不是事件。
- **干脆隐藏树外节点**：隐藏会让用户以为树不完整（设备上明明有 `target/`），
  「为什么少了」比「有但进不去」更让人不安。而且用户会用 `ls` 在终端里看到它们——
  届时界面与终端的不一致比任何越界反馈都更伤信任。
- **只禁用不解释**：灰掉但不给理由，用户会去改终端、去换路径、去重启，
  做一堆与根因无关的操作。

**关键补充**：这个边界**只对页面用户生效**。
`architecture/README.md` §4.2 写明 agent 用它自己装在设备上的工具，
不经过 files connector，所以这条约束**管不到 agent**。
因此每条越界提示都要写明这一点，否则用户会以为
「打开工作区就能让 agent 也被限制住」——那是本项目反复强调不要搞混的两条独立路径（约束 3）。

### 7.5 轨迹是抽屉不是第三栏

见 §5.4。核心论证：**对话与轨迹是同一份事件流的两种读法**，
做成两个并列视图会暗示「两套不同的数据」。

### 7.6 Agent 目录和会话的分界

**分界线是有没有正在跑的运行期。**

- **目录**回答「哪个节点上能用什么」，来自心跳的 `capabilities.agents`
  （已装且就绪，非「支持」）。它是**静态聚合，没有时间轴**。
- **会话**回答「它现在在干什么」。它有运行期，断线会冻结成只读。

两者长得太像，最容易被合成一页。所以：

- 目录行**没有**「最近活动」；
- 实例离线时**目录仍在**（它描述的是「装了什么」，不是「现在在不在」）；
- 目录行的**唯一**动作是「用它开会话」——不是「进入目录」；
- 页首与页尾**各说一次**这个区别（用户在页面上下两端都可能需要它）。

### 7.7 等宽字体族

见 §2.2 的完整论证。

### 7.8 设备三态的视觉表达

见 §3.4 的表格。两条容易漏的：

- **`unknown` 必须与 `offline` 严格区分**：「不知道」和「知道它不在」是两种事实。
  Hub 刚重启时所有设备都是 `unknown`（`last_seen_gen` 归零，但还没有心跳），
  如果把它显示成灰色 offline，用户会以为自己的设备全挂了——
  **实际上它们会在下一个心跳周期（15s）内自动回来**。
- **`reconnecting` 是琥珀不是红色**：它是**等待**不是**阻断**。
  红色在本系统里是稀缺资源，于是红色的出现次数本身成了告警密度指标（§2.1）。

### 8.2 原型验证不了的东西（实现阶段第一件事）

这几条**在原型里看不出来**，因为原型用 HTML/CSS 模拟了真实实现：
它们不是「原型做得不好」，是「原型的表达方式本身做不到」。

1. **终端的 ANSI 渲染是这个原型里最大的谎言。**
   原型用 HTML/CSS 模拟，真实实现是 xterm.js。两者的关键差异在原型里**看不到**：
   框宽计算（`measureText` vs xterm 的 `CharSize`）、CJK 宽度折叠、零宽字符、
   控制序列跨帧切分、选区与滚动条的行为。
   §4.5 的尺寸协商参数是按 xterm 的约束写的，但**没有在 xterm 上验证过**。

   > **子任务 8 的验证结果（只覆盖设备侧，xterm.js 仍未验证）**：
   > `TIOCSWINSZ` 这条链是真的——`Pty::resize` 之后**同一个 PTY 上的
   > `stty size` 会报新值**，判据落在内核属性上而不是「我们自己改了个变量」。
   > 另有一条原型看不到、实测才暴露的事实：**PTY 的输出不是「响应」，
   > 是「产出」**。它必须在没有任何下行帧时也能被推出去，否则敲一次 `ls`
   > 然后干等就永远看不到结果（见 `node-core/src/channel.rs` 的 `poll_all`）。
   > 仍未验证：控制序列**跨帧切分**——xterm.js 拿到半条 `ESC[` 时必须自己
   > 缓存到下一帧，这一条要等前端（子任务 13b）在真 xterm.js 上验。

   > **M1 子任务 13b 验证**：已验——上一段的「仍未验证」就此消解。
   > `TerminalPanel.vue` 走真 `@xterm/xterm`，而字节到画面的**唯一**解释器
   > 就是那个实例（node 侧明确不解释转义序列——
   > `node-core/src/connector/terminal.rs`「node 只搬字节，不做终端仿真」）。
   > 于是**半条控制序列不会被人从中间截断**：页面只做
   > `output += bytes`（append-only 的累积字符串），按已写长度把增量
   > `write(output.slice(written))` 交给 xterm，跨帧的那一半留在它自己的
   > 解析器里等到下一帧。帧边界与解析边界因此**无关**——这正是把「按行切开
   > 画 `<div>`」换成 xterm 的直接结果：原型做得到「按行切」，真终端做不到。
   > 尺寸协商同样落在 xterm 上：`FitAddon.proposeDimensions()` 按其
   > `CharSize` 量出 cols/rows，再走既有控制帧
   > `POST /api/channels/{id}/resize`（不新增消息类型，约束 14）。
   > **仍未验证**（在 13b 的范围之外，记在这里别丢）：真设备上的端到端
   > 观感——真 PTY 的产出量级、以及 CJK 宽字符在**没装**
   > `Noto Sans Mono CJK SC` 的机器上的折叠（见本节第 3 条）。13b 验的是
   > 「页面这一侧的形状站得住」，不是「跑起来好看」。

2. **`inert` 与 `z-index` 的协同只在三个现代浏览器上验证过。**
   原生 `inert` 在旧 WebKit 上有兼容问题；实现时如果需要支持旧 Safari，
   要写 fallback 并**重新验证焦点不会漏出去**。

3. **CJK 在 `Noto Sans Mono CJK SC` 下的实际字宽**取决于系统是否装了这份字体。
   装不到的机器会掉进系统 CJK fallback，此时「等宽」的承诺失效——
   §2.2 的「中文必须覆盖」是字族选择的第一权重，不是可以牺牲的。

### 8.3 我认为最需要后续迭代的三件事

1. **密度是猜的，不是量的。** 26px 行高、22px 树行、56/44 默认分栏、
   全部来自「密集工具」的通用经验，**没有在真实数据上量过**。
   M1 实现后应该拿一台真树莓派 + 真项目跑一遍，
   记下「一屏能看几个文件、终端折成多少列」，然后回来改这几组数字。

2. **纯键盘走查还没做。** 本规范要求所有交互在 `:focus-visible` 与 `:hover`
   下表现一致，也定义了焦点栈与落点，但**没有真的只用键盘把全站走一遍**。
   实现后应该做一次走查：`Tab` 序列、`?` 面板、焦点返回、
   以及最关键的——**只靠键盘能不能建一个会话并敲一条命令**。

3. **22 个键位在真实使用中的手速还没测过。** `g` 序列的 800ms 窗口、
   `[`/`]` 切面板、`\` 收起面板坞——这些是我按「密集工具」的通行做法定的，
   **不是按实际使用数据定的**。M2 有了真实用户后应该看事件日志：
   哪些键位按了但没用、哪些动作没有键位而用户反复用鼠标做。

### 8.4 一个我主动留给后续的问题

**面板坞的三种状态要不要合并成一种。**
现在是「关着 / 开着」两态（§5.4），但超宽屏下「覆盖式展开」可能比「挤压对话」
更合适（对话全宽、面板浮在上面）。我没有真实使用场景的数据判断哪边更好。
建议 M3 有 agent 会话面板之后重新评估——到那时「三面板并置」会是一个真实的需求。

### 9.1 焦点栈是本规范的核心机制

`keynav.js` 是三样东西的唯一真相源，值得单独记一笔，因为
**「原型能跑」和「键盘用户能用」之间，差的全是这一份文件**：

| 机制 | 位置 | 解决什么 |
|------|------|---------|
| `AF.focusPush/Pop` | keynav.js §3 | 焦点归最内层容器；背后 inert；关闭一定还焦点 |
| `AF.focusablesIn` | keynav.js §4 | 每次 Tab 重算，不缓存快照 |
| `AF.register` | keynav.js §2 | act 必须在表里；不许注册两次 |
| `AF.unimplemented` | keynav.js §2 | 表里有、没人实现的项 → 控制台报警 |
| `AF.renderHelp` | keynav.js §6 | `?` 面板**由表渲染**，文档与实现不可能漂移 |
| `AF.focusMain` | keynav.js §9 | 跳转后的落点 |

**这六个是同一条纪律的六个切面**：焦点与键位不许分散在页面里。
上一版 7 条焦点缺陷的共同根因就是「焦点散在各页面各写各的，无统一所有权模型」。
