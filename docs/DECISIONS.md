## D1. 设备端进程模型：同二进制双角色（supervisor / worker）

**决策**

```
afcli run                 → supervisor（默认角色，父进程）
  └─ spawn: afcli run --worker    ← 同一个二进制，只多一个 flag
       └─ 持有 identity.json + WS 连接 + 心跳 + 重连
```

- **supervisor 不碰 WS、不碰业务**。唯一职责：保证有一个能用的 worker。
- **回滚由 supervisor 执行**，而 supervisor 是**没被替换过的旧代码**。
- Docker 模式：`afcli run --worker` 直接跑 worker，无 supervisor、无特判分支。

### 为什么是 `run --worker` 而不是顶层 `--worker` 或环境变量

| 形式 | 评价 |
| --- | --- |
| `afcli run --worker` ✅ | `run` 是"启动守护进程"这个动词，角色是它的修饰符。supervisor spawn 时**把自己的 argv 原样传下去再追加 `--worker`**——用户给的 `--data-dir` 之类参数自动继承，不用重新拼一遍 |
| `afcli --worker` | 没有动词，与 `afcli log` / `afcli status` 这类子命令不一致；看起来像全局开关，实际只影响 `run` |
| `AFCLI_WORKER=1` 环境变量 | ❌ **不采用**：(a) `ps` 里看不见角色，排查"这进程是 supervisor 还是 worker"得翻 `/proc/<pid>/environ`；(b) 环境变量会被孙进程继承，worker 再 spawn 任何东西都会误以为自己是 worker；(c) 与 argv flag 并存就是**两条代码路径**，而覆盖率门禁要求 100%，多一条路径就多一份要单独构造的分支 |

**只有一条进入 worker 角色的路径**：argv 里含 `--worker`。
（原设计同时保留 env var，现删除——两条路径不增加表达能力，只增加要测的分支。
REX 用 env var 是因为它 spawn 时只透传原始 argv；追加一个 flag 一样能做到，还顺带可见。）

**幂等**：若 supervisor 自己就是带 `--worker` 启动的（人手误敲、或 Docker 里直接指定），
它**不再追加**，直接以 worker 角色运行——不会出现 `run --worker --worker`。

**理由**

「执行回滚的代码不参与被回滚」——新二进制再坏也坏不到 supervisor 里，
坏 worker 只会 `exit(11)`，supervisor 照样能把它换回去。
supervisor 职责极小 ⇒ 没有 bug 面 ⇒ 恰恰是最需要永远可靠的那个进程。

**被否决的替代方案**

| 方案 | 否决原因 |
| --- | --- |
| A. supervisor 持 WS，IPC 转发给 worker | 要写一层帧转发 + req_id 映射表，M0 worker 是空壳，为不存在的转发需求付 100% 覆盖率的账 |
| B. worker 持 WS，supervisor 只拉起 | 方向对，但不如双角色彻底——仍需处理 WS 生命周期 |
| 单进程 + `execv` 原地换映像 | **根本性缺陷**：新二进制自己回滚自己。为"同 PID"这个假收益，放弃了唯一真正重要的属性 |

**参考实现**：REX（`rex-common/src/supervisor.rs`）。本方案在其基础上修了 6 个缺陷，
见 [D2](#d2-升级与回滚时序)。

## D2. 升级与回滚时序

**决策**：版本号**由 Hub 通过 WS 下发**，不自己探测 GitHub Releases。

```
Hub ──heartbeat 应答带 update{version,url,sha256}──► worker
                                                      │ 下载 → SHA256 校验
                                                      │ 写 update-state.json (phase=Requested)
                                                      │ exit(10)
                                                      ▼
supervisor: 备份 exe → .bak  →  rename(staging → exe)  →  phase=StartingNew
                                                      │
                                             启动新版 worker
                                                      │
                              健康检查：30s 内完成握手且 node_version == 目标版本
                                                      │
                                    失败 → exit(11) → supervisor rollback()
```

- **worker 立即生效新代码**；**supervisor 懒生效**——文件已换成新的，进程继续跑旧映像，
  下次被 systemd/docker/用户拉起才更新。
  - 前提（**显式承诺**）：supervisor 的 ABI 是极小的稳定接口 = `spawn` + 退出码协议 + `update-state.json`，必须向后兼容。
  - 附带解决 Windows：没有 systemd 兜底，懒生效让 supervisor 永远不必为了自己的新代码而退出。

### 对 REX 参考实现的 6 处修正

| # | REX 的问题 | 本项目的修法 |
| --- | --- | --- |
| ① | `fast_crash` 判定在读 update-state **之前** → 坏版本把 supervisor 直接拖死，**永不回滚**（砖设备） | 判定移到读 state **之后**；本轮有 pending update → 走 rollback 而非 exit |
| ② | 退出码 0 不算 fast_crash → 「启动即干净退出」的 worker 以 1s 间隔无限重生，**永不回滚**，Hub 看到心跳风暴 | 改为**时间窗内连续退出计数**，与退出码无关（10s 内 3 次 → 不可恢复 → rollback） |
| ③ | 备份失败后仍 rollback → 用**上一轮**遗留的 `.bak`，**降级到几个月前的陈旧版本**且用户不知情 | **备份先行且必须成功**才进下一阶段；state 记 `generation`，rollback 只认本轮备份，对不上 → `phase=Failed` 大声报错 |
| ④ | 错误全线静默（`let _ = rename`、三层 `if let Ok`、`.ok()`）→ 磁盘满时后续阶段全错，日志一行没有 | 所有 I/O 失败必须 `tracing::error!`；**state 写失败 = 放弃本次更新**（宁可不升级，不可进到"说一套做一套"的阶段）。本项目 `let_underscore_must_use` / `unwrap_used` 是 deny，这类代码本来就编不过 |
| ⑤ | 回滚防死循环是 rename 消耗掉 `.bak` **偶然形成**的，无文档、无计数 | 显式 `rollback_count ≥ 1` → `phase=Failed` + 大声报错，不依赖 rename 副作用 |
| ⑥ | 崩溃在 `rename(exe)` 与 `write StartingNew` 之间 → 重启后 state=Requested 但 staged 已挪走 → **误回滚一次已成功的更新** | supervisor 启动时 **reconcile**：staged 不存在 && 二进制已是目标版本 → `phase=StartingNew` 继续；否则 `phase=Failed` |

另：`std::process::exit()` 不跑 drop，`tracing` 最后几行日志会丢 → 改为从 `main` 返回。

### 决策逻辑必须纯函数化

```rust
fn decide(exit: ExitInfo, state: Option<UpdateState>) -> Decision   // 纯函数，全分支单测
enum Decision { ReplaceAndSpawn, Rollback, Spawn, BackoffSleep, Stop }
// executor 只执行 Decision —— 薄到不需要单测，靠集成测试覆盖
```

**这不是洁癖，是被 100% 覆盖率门禁逼出来的**：REX 把决策内联在阻塞循环里，
里面真的 spawn 子进程、真的 rename 文件——在 100% 行覆盖下几乎没法测（测了就真删二进制）。

## D3. 升级触发方式与可见性

**决策**

- Hub 页面**显示每个设备的 CLI 版本号**
- 页面可**手动触发升级**
- 页面提供**自动升级开关**（开 / 关）

**理由**：设备状态必须在 Web 上"一眼可见"（产品基调）。升级失败必须在页面上看到
「设备 pi-1 升级失败，已回滚」，而不是只能 ssh 上去看日志。

**被否决 / 明确不做**

- ❌ 最短发布年龄（24h）—— 升级跟 Hub 走，Hub 自己决定何时推
- ❌ 不降级检查 —— Hub 不会下发比自己旧的版本
- ❌ 包管理器检测 —— 不进包安装体系（暂不考虑进包安装）

**协议影响**：需新增 `update_available{version,url,sha256}` 消息类型
（`protocol::message::types`，非必需集，老节点忽略）。同步更新 `docs/architecture/protocol.md` §2。

**验签分层**（此处修正此前的高估）：
- **M0：SHA256**（Hub 下发，防下载文件被污染 —— URL 走 CDN，这是真实威胁）
- ❌ ed25519 全量验签随 release 流水线一起立，**不阻塞 M0**
- 理由：信任根就是 Hub，Hub 本就能下发任意命令，签名防不住 Hub 被攻破，边际价值小

## D4. 日志：`afcli log`

**决策**

- 日志落盘：`<data-dir>/logs/afcli.log`，按大小 / 天数轮转，权限 **0600**
- supervisor 与 worker **写同一个文件**（追加，整行原子写）
- `afcli log` 默认 tail 最近 **200 行**；`afcli log -n <N>` 指定行数
- 所有 I/O 失败必须留痕（同 D2-④）

**理由**：`afcli` 是守护进程，**没有日志等于黑盒**——升级失败、回滚、重连退避这些
只在设备端发生的事件，用户 ssh 上去也看不到。这条把"日志落地"从 M1 拉进了 M0。

## D5. Hub 存储后端：sqlite 默认 / postgres 可选

**决策**（新立里程碑，**不并入 M0**）

- Hub 自身存储的**完整后端**：`sqlite://` 默认、`postgres://` 可选
- 导出为**一次性快照**（不是持续同步）
- 不引 Redis；不做多节点 Hub（多用户需求以后再说）

## D6. Windows 支持范围 ⬜ 待定

- **node 侧必须支持 Windows**（cli 要在 Windows 上，后续还要能操作电脑）
- **Hub 是否也要跑 Windows**：⬜ 未决。**建议 B：Hub 仍 Linux**（单用户 self-host，
  部署在 NAS/小服务器，无 Windows 诉求）

**Windows 改造面**（现有硬 Unix 依赖，供估算）：

| 依赖 | 位置 |
| --- | --- |
| `libc::umask(077)` | hub-storage/db.rs、main.rs |
| `PermissionsExt::mode(0o600)` | db.rs、identity.rs、setup.rs |
| `libc::kill(SIGTERM)` | afhub_process.rs |
| `libc::execv` | 自更新 |
| `/proc/net/tcp` + `/proc/<pid>/fd` | ws_flow.rs |

⚠️ **约束 13 的「0600/0700/umask 077」在 Windows 上无语义等价物，需按 NTFS ACL 重定义。**

⚠️ **`self_replace` 在 Windows 的已知坑**（Mise #12062）：先移走 exe 再从 TEMP 启 helper，
路径超 `MAX_PATH`(202) 时 `CreateProcess` 失败 → **安装目录变空、设备变砖**。上 Windows 必须预检路径长度。

## D7. Hub 自身不参与自更新

- **Hub 不实现自更新**：`afhub` 没有 `update` 子命令，也没有 `self_replace` 路径。
  M0 的升级机制（D2 的 supervisor/worker + 退出码协议 + 回滚）**只服务 node 侧**。
- **为什么**：supervisor 那套机制的可靠全押在「执行回滚的进程未被替换」上。Hub 若是
  单进程（Docker / systemd 托管），替换正在运行的二进制仍需一次重启，而那正是 D2
  想避开的东西；把 supervisor 再套一层到 Hub 上，收益为零而复杂度实打实。
- **Hub 怎么升级**：换镜像 / 换二进制后由外部进程管理器重启，与 D3 一致——
  **Hub 升级是部署动作，不是产品功能**。
- **与 D6 的关系**：Windows 改造面里 `libc::execv` 那一行**只属于 node 侧的自更新**，
  Hub 不上 Windows 不影响它；反过来 Hub 若真要上 Windows，也不必因此获得自更新能力。
  两项互不牵连，可分别裁决。

## D9. 环境一致：绑定声明，不绑定产物

**决策**：环境一致性靠**声明的可哈希指纹**（`env_signature`）保证，
不靠把已构建产物搬过去。sub-task 的**跨设备分发推迟到 M8**，
M5 只做**同一设备内**的 sub-task 编排。

### 为什么「搬产物」这条路是错的

「sub-task 换机器时用一样的环境」这个诉求，默认解法是同步整份依赖目录。
这条路有三重硬阻，任意一条都足以否掉它：

1. **依赖目录按架构分化**。`node_modules` 里是平台相关的二进制，
   x86-64 与 aarch64 装出来的不是同一份东西——**根本不存在「同一份依赖」可搬**。
2. **体积**。`workspace-and-sync.md` §3.3 的永不传输清单里 `node_modules/`、
   `.venv/`、`target/` 都在列，理由是「体积爆炸、平台相关、可能含绝对路径」。
3. **绝对路径**。虚拟环境与部分构建产物内嵌构建机路径，搬过去即失效。

### 为什么 mise 是答案的一半，不是全部

`mise.toml` 的 `[tools]` 已经钉死 `rust` / `bun` 版本，其注释里的理由
（重编译全树、覆盖率跨工具链不可比）与 sub-task 换机器是同一个理由。
但它**只管工具链版本**，管不到：

| 层 | 内容 | 载体 | 谁负责 |
|---|---|---|---|
| 工具链 | rust / bun / node / python 版本 | `mise.toml` | mise |
| 项目依赖 | `Cargo.lock` / `bun.lock` / `uv.lock` | 各语言 lockfile | 包管理器 |
| 系统能力 | openssl / cmake / pkg-config 版本 | **无载体，需新增声明** | 无人（缺口） |

第三层是最容易漏的一层：`rust = "1.99.0"` 装得上，但 `openssl-sys`
要的 `libssl-dev` 是宿主 OS 的东西，树莓派上是 OpenSSL 3.0、开发机上是 1.1。
同一个 rust、同一个 `Cargo.lock`，编出来的东西**不一样**。

### 三段式 env_signature

```toml
# 1. 工具链：mise.toml 内容哈希
[tools]
rust = "1.99.0"
bun  = "1.4.3"

# 2. 依赖：各语言 lockfile 内容哈希
#    rust: Cargo.lock / node: bun.lock / python: uv.lock

# 3. 系统能力：新增声明，随心跳上报
[env]
AF_SYS_REQUIRES = "openssl>=3.0,cmake>=3.22"
```

**定位：观测项，不是路由依据的独占来源。** 第一版路由仍按能力/负载打分
（`scheduling.md`），`env_signature` 只负责让页面能**说清「这台为什么跑不了」**——
差在哪一段（工具链不同 / lockfile 不同 / 系统库不满足），
而不是等 sub-task 跑崩了再猜。

**增量演进**：第一版只有 `os` / `arch`（M0 已在上报）；
第二版加 lockfile 哈希；第三版加系统库版本。每加一段是一次 capability 增量，
M7 的插件化来了正好接上。

### 为什么 M5 只做单设备

跨设备 sub-task 分发的三支柱里，两个在 M2（CAS + 工作区物化）、
一个在 M8（checkpoint 续跑），而真正回答本决策的那一层横跨 M2 与 M8。
在 M5 实现必然是残的，返工成本高于延后。

**M5 缩小后的样子**：任务记录 + 状态机 + 一个跑任务的方法。
注意语义变化——M5 不再是「Hub 决定派给哪台 node」（跨设备分发），
而是「Hub 建任务，**node 决定开几个 sub-task**」（node 侧编排）。
后者正是约束 8 说 Hub 不该做的事，所以 M5 砍掉跨设备分发**不损失能力**，
只是移走了原本就不属于 Hub 的部分。

### 被否决的替代方案

| 方案 | 否决理由 |
|---|---|
| 同步整份依赖目录到目标设备 | 架构上不可能「一样」（平台相关），且违反永不传输清单 |
| 设备间 P2P 直传 | 违反约束 10：Hub 必须保持唯一真相源 |
| 只钉工具链版本（当前 mise.toml） | 系统能力层无载体，`openssl` 差异会静默改变产物 |
| 现在就做跨设备分发 | 三支柱缺两个，返工成本高于延后 |

## D10. 多会话 tab：视图切换器，不是生命周期边界

**决策**：会话工作台顶部 tab 条支持同时打开多个会话。**切 tab 不释放通道**，
关掉 tab 才释放。

### 为什么切 tab 不关面板

边界是「关掉这个 tab」或「离开会话列表」。若切 tab 也关面板，
则来回切两次就重建 PTY，用户刚跑出来的终端输出全丢——
**「支持多个会话」会退化成一条假的 tab 条**（切过去永远是空的）。

代价是实的：N 个 tab = N × 面板数条活跃通道。所以每个 tab 显示自己的**面板数徽标**——
**让代价可见**，而不是让用户猜。

**没有硬上限是有意的**：设上限就要在超限时做某种拒绝，
而拒绝谁（最早的？最重的？）是产品决策，不是设计决策。
实现阶段先加观测项，看真实使用里 N 实际到多大。

### 焦点落点

切 tab 后焦点进**工作台正文**，不回 tab 条——用户意图是「去那儿干活」，
不是「继续看标签栏」。`⇧Tab` 一步回到 tab 条（它是紧邻的上一个 tab stop）。

tab 条是一个 tab stop，`←→` 移动**并激活**（像浏览器 tab 条）：
切一个 tab 便宜且可逆，没有理由让用户多按一次 `⏎`；
真正不可逆的动作（关 tab）才需要停顿。

### 关闭按钮必须是真 button

曾设计为 `<span role="button">` 塞在 tab 按钮里。**否决**：
那样它既不在 Tab 序列里（父按钮把它从顺序中拿走），又让父元素的
`:focus-within` 永远不成立——**「键盘用户能关掉一个会话」在结构上做不出来**。
关闭会释放通道、丢未保存改动，是不可逆动作，不许是鼠标专属。

**没有全局关闭快捷键**：`⌃W` 是浏览器的，拦不住。
把一个冲突的键绑到不可逆动作上，比不给键更危险。

### 位置变更（v0.5.0）

**D10 的语义不变**：tab 仍是视图切换器、切 tab 仍不释放通道、关 tab 才释放。
变的是位置——tab 条从「页头下方」移到**页面最顶部**，成为会话页唯一的顶部导航。
理由与副作用见设计规范 §7.1.1；本条不因位置变化而改变任何行为承诺。

### 被否决的替代方案

| 方案 | 否决理由 |
|---|---|
| 切 tab 即关闭面板 | 来回切两次就丢终端输出，「支持多个」是假的 |
| tab 条可深链接（`?tab=3`） | tab 是瞬态的，不该能链到「第 3 个标签页」 |
| 硬上限 N 个 tab | 超限拒绝谁（最早/最重）是产品决策，不该由设计替他决定 |
| `⌃W` 关闭 tab | 浏览器占用，拦不住；冲突键绑不可逆动作更危险 |

## D11. 设备重注册后的身份接续：只换设备行的密钥材料，不动历史数据

**场景**：设备先注册，Hub 里是记录 A。用户清理了设备本地数据（`identity.json` 连同私钥一起没了），
重新注册后 Hub 里多出记录 B。想把 B「并进」A。

**决策**：提供手工操作，**只把 device 行的身份材料改成 B 的**——
`UPDATE device SET key_fingerprint=<B 的指纹>, public_key=<B 的公钥> WHERE id=<A>`，
然后删掉 B。**A 名下的历史数据（工作区、会话、轨迹）原地不动。**

### 为什么 node_id 会变，以及它不是 bug

`node_id` 是 16 字节 CSPRNG 随机串（`crates/identity/src/lib.rs` 的 `random_id()`），
与密钥对**没有任何密码学派生关系**。指纹是 `SHA-256(公钥)`，新密钥对必然是新指纹。
enroll 载荷结构上**不带** `node_id`，Hub 侧 `issue_node_id()` 的结果调用方也无法指定。

所以「清空本地数据 → 重注册」= 新指纹 + 新随机 id = 第二条记录。
**这不是「同一台设备又来了一次 enroll」**——后者会被指纹命中并复用原 node_id
（`Registry::enroll` 的快路径，`AlreadyRegistered` 分支不是错误）。

设备侧私钥与 node_id 同存 `identity.json`，`load_or_create` 在文件缺失时生成全新密钥对，
两者必然一起丢。**这不是设计缺陷，是「密钥丢了就得换身份」的直接后果**：
签名锚点是密钥对，密钥没了就没有任何东西能把「新来的这台」与「原来那台」绑在一起。

### 为什么不做「搬数据」

把 B 的历史改挂到 A 名下（改 `workspace.node_id`、逐行改轨迹事件的冗余 `node_id` 列）
技术上做得到，但**方向是反的**：那些数据本来就是 A 名下设备产生的，
它们描述的是「设备 A 在某段时间做了什么」，不是「新设备 B 做过什么」。
把 B 的数据搬到 A，等于往设备的历史里塞进从未发生过的事。

反过来的方向（把 A 的历史搬到 B）才说得通，但那需要先回答「旧工作区在新设备上还在不在」
——而工作区是**设备本地路径**，设备都重装了，那个路径大概率已经没有意义了。
所以两种搬法都不做，只保留 A 的历史、承认设备换了。

### 为什么不做「真合并」（A 和 B 的数据并集）

要先定义「同一 `(node_id, path)` 下两个工作区怎么处理」——冲突、并存还是报错？
这是产品决策不是技术决策。而且一轮合并后「身份唯一性锚点」会从密钥对退化成
「人工维护的合并历史」，将来出问题时无法判断某条记录是谁接上来的。

### 与硬约束的关系

约束 12（升级只换 worker，身份不变，**因此不需要身份抢占逻辑**）是**设计理由**不是禁止条款，
它的射程限定在**升级路径**。手工接续是用户显式声明「这台机器就是原来那台」，
不违反「升级导致 node_id 变化」这条红线（审查维度 10）。

约束 11（设备私钥永不上传）约束的是**密钥流向**：接续后 Hub 存的是 B 的**公钥**，
私钥始终在设备上。**「存了公钥」这件事本身不违反约束 11**——指纹不可逆，
验签必须要公钥，`DeviceRepo::set_public_key` 与 `pubkey_from_fingerprint`
就是为此存在。约束 11 的字面表述（「Hub 只存指纹」）应按「只存公钥与指纹，
绝不存私钥」理解。

### 必须满足的不变量

1. **任一时刻，一个指纹只对应一个 node_id**（`device.key_fingerprint` 的 UNIQUE 约束）
2. **任一时刻，一个 node_id 只对应一个指纹**
3. 接续后设备能正常重连：新私钥对上新公钥，验签通过
4. 接续**不产生任何身份抢占窗口**——操作期间 B 与 A 同时在线会被明确拒绝，
   不允许「两个私钥轮流用同一个 node_id」

### 被否决的替代方案

| 方案 | 否决理由 |
|---|---|
| 把 A 的历史改挂到 B | 设备都重装了，旧工作区路径在新机器上大概率无意义；搬过去等于制造假历史 |
| A/B 数据并集 | 「同一路径两个工作区怎么处理」是产品决策；合并后身份锚点从密钥对退化成人工历史 |
| 让用户指定 node_id | 破坏「指纹是唯一入口」，等于引入可枚举的弱身份；也违背约束 5 |
| 合并时保留旧指纹不换 | A 的公钥已随设备丢失，Hub 留着旧指纹会让人以为那台设备还在 |
| 升级路径复用此机制 | 升级只换 worker、身份不变（约束 12），与「设备被清空」是两件事，不该共用一条路径 |

### 未决（排期时必须先定）

- **合并操作的入口**：Web 设备页的按钮，还是 Hub CLI 子命令？前者要多一条带二次确认的 API。
- **是否要求 B 先离线**：倾向要求（不变量 4），但「B 在线」在 Hub 侧怎么判——心跳新鲜度阈值是多少。
- **是否留合并记录**：审计需要「谁在什么时候把哪台接到了哪台」，但这是新表，
  与「仅改一行」的轻量目标有张力。

## D12. 会话页自动收起全局侧栏：页态是页态，偏好是偏好

**决策**：进入 `/sessions/:id` 时全局侧栏自动收成 52px 图标轨，离开会话页恢复。
侧栏开关（`⌃B` / 侧栏底部按钮 / 顶栏按钮）**照常可用**，且它拨动的是**用户偏好**，
不是这一次的临时状态——在会话页里拨它，离开会话页后保持。

### 为什么是两个状态，而不是一个布尔

「自动收起」是**页面态**：它只在会话页成立，别的页面永不生效。
「侧栏开没开」是**用户偏好**：跨页面、跨会话、跨重启都该一致。

合成一个字段就答不出「用户在这个会话里手动展开过之后，路由还该不该覆盖他」。
所以分成两个：`rail`（用户偏好，只由用户写）+ `autoCollapsed`（页面态，只由路由写），
显示取 `autoCollapsed ? 'collapsed' : rail`。

### 开关的翻转基准是**可见态**，不是 `rail`

这是本决策唯一反直觉的地方，踩过一次：进会话时 `rail` 还是列表页的 `open`，
可见态被自动收起成 `collapsed`。若开关按 `rail` 翻转，用户点「展开」，
`rail` 从 `open` 翻到 `collapsed`，可见态**仍然是** `collapsed`——
**点了一次按钮，什么都没发生**，要按两下才展开。

所以 `toggleRail` 以 `effectiveRail`（用户眼前看到的）为基准翻转，再写回 `rail`。

### 被否决的替代方案

| 方案 | 否决理由 |
|---|---|
| 在会话页里就强制 `collapsed`（`autoCollapsed ? 'collapsed' : rail`） | 会话内的手动展开被同一个 computed 立刻盖回去，开关点了没反应 |
| 手动拨动只清 `autoCollapsed`、不写 `rail` | 侧栏本来就收着进会话时，清了标志回落到同样是 `collapsed` 的 `rail`，同样没反应 |
| 进会话拍快照、手动拨动丢快照（`frozenRail`） | `route.value` 是普通对象不是 ref，Vue 不会因它变化重跑 watcher；模板渲染触发的 computed **重新求值**会把丢掉的快照又算回来 |
| 离开会话页时写回「进入前的值」 | 那等于把用户在会话里明确表达的偏好撤销掉。「自动收起」才是该越界回收的那个，偏好不是 |

### 可证伪断言

三条变异各自都会让 `App.test.ts` 的「会话页自动收起侧栏」变红（实测）：
翻转基准改回 `rail`；离开会话时无条件写 `rail = 'open'`；`watch` 只写 `false`。

## D13. 右侧只有一格：换工具就释放旧工具的通道

**决策**：会话工作台右侧**同一时刻只显示一个工具**（终端 / 文件 / Git）。
坞头只有一个入口「＋」，它列出**全部三个**（含当前这一个），选中即**替换**。
被换掉那个工具的通道**释放**。点当前这一个**零副作用**。

### 为什么砍掉坞标签条

v0.4.0 的坞是「一排已挂载面板的标签 + 一个＋」。加上 C 之后右侧只剩一格，
标签条与「＋」就变成**两个**切换入口，而「当前是哪个工具」于是有两处真相源。
两处真相源是本仓反复踩过的同一类坑（D10 的「视图切换器」被实现成两个真相源）。

所以只留「＋」。它同时解决另一件事：v0.4.0 的候选会过滤掉「已挂载的」，
一格之后所有工具都算没挂载，这个过滤等于没过滤，干脆不列表——**候选恒为三个**。

### 为什么点当前那个必须零副作用

「＋」里含当前这一个，所以用户会点到它。如果走「先释放再重建」，
对终端就是**把正在跑的 shell 杀掉**，而用户只是点了一下自己已经在看的东西。
`addPanel` 因此在组件内判等返回、**不 emit**：不 emit 就没有任何一条路径能把
信号送到释放通道那一侧——这是**结构上**的保证，不是靠下游自律。

### 已知降级：换工具 = 杀 PTY

**这是有意接受的降级。** 终端通道释放走 `pty.close()`
（`crates/node-connector/src/connector/terminal.rs:305`），所以 `]` / 换工具会杀掉
用户正在跑的 shell。v0.4.0 多面板并存时来回切是不丢输出的。

**不缓解**：保住 shell 需要后台保活多个工具，等于把右侧重新做成多面板，
与本决策直接冲突。缓解属于新能力。本里程碑只做三件事：代码里就地注释、
键位文案如实写、e2e 断言旧工具真的没了。

### 面板数徽标 → 当前工具图标

v0.4.0 在 tab 上显示「面板数徽标」，目的是让 `N 个 tab = N × 面板数条通道` 的
代价可见。一格之后那个数**恒为 1**，一个永远是 1 的数字不承载信息。

**改为显示当前工具的图标，而不是删掉这个位置**：「这个 tab 现在开着什么」仍然
有用（切回去之前想知道会看到终端还是 Git），图标是最省的载体。改的是一个
**载体**，原则（让状态可见）没变。

### 被否决的替代方案

| 方案 | 否决理由 |
|---|---|
| 坞标签条与「＋」并存 | 「当前是哪个工具」有两处真相源；标签条只会列出「打开过的」，读起来像残缺目录 |
| 「＋」只列没挂载的 | 一格之后所有工具都算没挂载，过滤等于没过滤；当前工具会从候选里消失 |
| 点当前那一个走「先释放再重建」 | 对终端等于杀掉正在跑的 shell，而用户只是点了一下 |
| 删掉面板数徽标、不留替代 | 「这个 tab 开着什么」是有用信息，删掉是丢信息，不是去噪音 |
| 换工具时后台保活旧工具的通道 | 等于把右侧重新做成多面板，与 C 直接冲突；属于新能力 |
| 把 `mounted` 从数组收成标量 | 牵动 `closeDock` 的释放循环与多条测试前提，却不换来任何表达力。改为**注释钉住**「恒为 0 或 1 个元素」的不变量 |

### 可证伪断言

四个变异各自使测试变红（实测）：

1. 去掉 `addPanel` 里的判等 → PanelDock「零副作用」用例红；
2. 去掉 `openPanel` 里的 `releaseChannel(previous)` → SessionPage「每次替换都释放旧通道」红；
3. `candidates` 改回按 `mounted` 过滤 → 4 条红（候选恒为三个 / aria-current 等）；
4. TabBar 改回渲染数字 → 「开着工具的 tab 显示那个工具的图标」等 2 条红。

## D14. 分栏只有一个数字，且它按会话存

**决策**：会话工作台全页只有**一个**百分比坐标 `split` = 「对话列占正文宽度的百分比」，
30–70，步长 4，缺省 56，存在**每个 tab 的 workspace** 上。**没有纵向分栏。**
双击把手恢复缺省。`lib/split.ts` 的百分比口径（含「下限用百分比而不是最小像素」）
原样不动。

### 为什么不做 `splitH` / `splitV` 拆分

v0.5.0 的裁决 C 让右侧只剩一格，**没有第二处可拖**。拆成两个字段却不真的有
两处可调，只会让「哪个是哪个」变成新的认知负担，还白改 v0.4.0 已锁定的断言。
原两格方案担心「同一个数字被上下格复用会拖错」，那个担心随 C 自动消失。

没有第二个使用场景时给组件加 `direction` 参数，等于为一个不存在的需求预留 API。

### 为什么按会话存，而不是页面一个 ref 或 localStorage

- **不能是页面一个 ref**：两个 tab 会共用同一个数——切 tab 时比例跳一下，
  用户会以为分栏坏了。实测变异（v-model 绑死 `56`）让 4 条用例红。
- **不能写 `localStorage`**：tab 是瞬态的（D10），比例该跟着 tab 走。写全局存储
  会让新 tab 继承上一个会话的比例，而两个会话的工作内容未必同类。

### 为什么双击恢复缺省是必需的

右侧一格之后用户会更频繁地拖它：文件树要宽、终端要宽、git diff 也要宽，
三种需求差得远。「拖到极端怎么回去」从罕见变成常见。没有回头路的话，用户只能
靠方向键一格一格挪回去，而他还得先记得缺省是 56。

`SplitHandle` 只 emit `reset`，**不知道缺省值是多少**——那个数属于页面
（「对话列占多少」是布局决策）。让把手自己写死一个数就把那个数变成两处真相源。

### 被否决的替代方案

| 方案 | 否决理由 |
|---|---|
| `splitH` / `splitV` 两个字段 | 没有第二处可拖，纯粹增加认知负担；还白改已锁定断言 |
| 给 `SplitHandle` 加 `direction` prop | 没有第二个使用场景时加参数 = 为一个不存在的需求预留 API |
| 页面级一个 `split` ref | 两个 tab 共用，切 tab 比例跳变（变异实测红 4 条） |
| 比例写 `localStorage` | 新 tab 会继承上一个会话的比例，而两者工作内容未必同类 |
| 缺省值写死在 `SplitHandle` 里 | 把「对话列占多少」这个布局决策变成两处真相源 |
| 下限改成最小像素 | 像素下限随窗口宽度变化，同一 320px 在不同屏幕上是 22% / 31%（既有裁定） |
| 用按钮「恢复缺省」而不是双击 | 站内已有「双击标题栏 / 双击分隔条」的惯例；再放一个按钮会占掉面板头的稀缺宽度 |

### 可证伪断言

三个变异各自使测试变红（实测）：

1. `v-model` 绑死常量、回调置空（等价于退回页面级 ref）→ 4 条红；
2. 去掉 `SplitHandle` 模板的 `@dblclick` → 2 条红；
3. 页面不接 `@reset` → 「双击把手恢复缺省 56%」红。

## D15. 窄屏抽屉是浮层，宽屏不是：同一个 `dock` 状态，两套语义

**决策**：视口 ≤ 900px 时右侧一格变成**覆盖式抽屉**——铺在对话上、有遮罩、
点遮罩或 `Esc` 关闭、焦点圈在抽屉里、关闭后回到「打开面板」按钮。
宽屏下同一块内容是**并列的一列**，不入焦点栈、不设 `inert`、没有遮罩。

`dock` 仍是同一个状态（用户要看到面板），变的是「这一层是否模态」。

### 为什么窄屏态必须写在 JS 里

样式能做到「覆盖在对话上」，做不到「遮挡、`Esc` 关、焦点圈住、焦点归还」。
而这四件事的反面同样重要：**宽屏不能是模态**。宽屏是并列的两列，
凭什么右边抢走焦点、把对话区设 `inert`？那会让半屏界面点不动（实测变异：
去掉 `isNarrow &&` 之后 3 条用例红）。

### 断点只有一个字面量

CSS 的媒体查询 JS 读不到，所以 900 这个数天然有两份。`lib/media.ts` 的
`NARROW_MAX_PX` 是唯一字面量，样式表里的 `900px` 由 `media.test.ts` 对齐。
漂开的后果：JS 认为窄屏、CSS 认为宽屏，抽屉叠在对话上却按并列算宽度
（变异实测：常量改成 899 → 2 条红）。

### 抽屉与遮罩必须 Teleport 到 body

`focus.push` 的 `inertOthers` **只把「body 直接子节点里、不含浮层容器的那几个」
置 `inert`**。抽屉留在 `.af-wb__body` 里时，它所在的子树是整个 `#app`——
而 `#app` 是 body 唯一的子节点，于是「背后全部 `inert`」退化成「一个都没
`inert`」：遮罩盖住了视觉，背后的对话区仍可 Tab、可点。`TrajDrawer.vue`
与 `App.vue` 的帮助面板踩的是同一个坑。

宽屏时必须 `:disabled` 掉 Teleport，让它在原位参与 flex 布局。

### 窄屏缺省工具与宽屏一致

原方案把窄屏缺省定为终端（「窄屏只能看一块，先给能力最全的那块」）。
C 推翻了这条理由：**宽屏同样只能看一块**。两个屏宽给不同缺省，会让
「我打开会话看到什么」取决于窗口宽度——不可预测。

### 被否决的替代方案

| 方案 | 否决理由 |
|---|---|
| 只靠 CSS（不动 JS） | 遮罩、`Esc`、焦点圈、焦点归还样式做不到；更要紧的是「宽屏不能是模态」判不出来 |
| 用 `matchMedia` 但断点写死在两处 | CSS 媒体查询 JS 读不到，必然两份；只能靠「一份是唯一字面量、测试对齐另一份」来钉 |
| 抽屉留在原位、靠给兄弟节点逐个加 `inert` | 手写「哪个兄弟该 inert」等于重新实现一遍 `inertOthers`，且每加一个兄弟就得改一次 |
| `:target` / checkbox hack 开关抽屉 | 键盘与读屏不可用（D10 已为「关闭按钮必须是真 button」立过同一判据） |
| 窄屏缺省给终端 | 「窄屏只能看一块」在 C 下对宽屏也成立，缺省没有理由随屏宽变 |

## D16. 会话右侧一格：工具由「＋」互斥选择（落地 §7.1 的现行裁定）

**决策**（2026-10-29 用户答复）：会话工作台右侧**同一时刻只显示一个工具**，
工具由坞头的「＋」**互斥选择**，选中即替换。坞标签条去掉。

### 这条裁定是「沿用」，不是「推翻」

现行 §7.1 本就写着「面板坞在右、**同一时刻显示一个面板**」，并明写
「否决：在同一格里并排放置多个面板」。v0.4.0 的实现给它接了一个坞标签条，
那是**实现上多出来的一层**，不是设计要求的。本次做的是把那条裁定**落到实现**：

| §7.1 已写 | 本次落地 |
|---|---|
| 同一时刻显示一个面板 | `ws.mounted` 恒为 0 或 1 个元素 |
| 「＋」是进入其它工具的入口 | 「＋」是**唯一**入口，且列出全部三个（含当前） |
| 否决标签页 | 去掉坞标签条（标签条正是「一格里并排多个」的那层壳） |

所以本文**不写「推翻 §7.1」**——写「推翻」会让后来的读者去找一条并不存在的
设计变更记录，而真正的变更是「实现终于跟上了设计」。

### 为什么必须去掉标签条，而不是留着

标签条与「＋」并存时，「当前是哪个工具」有**两处真相源**。这与 D10 记的
「tab 条被当成两个真相源」是同一类坑，本仓已经踩过一次。

标签条还有第二个毛病：它只列出「打开过的」，读起来像一份**残缺目录**——
用户看不到文件工具，会以为它不存在。而「＋」列出全部三个，语义是完整的。

### 与 D13 / D14 / D15 的关系

- **D13**：换工具释放旧通道（已知降级）。本次的 e2e 断言 4/5/6 就是它的守门。
- **D14**：分栏只有一个数（左右），按会话存。
- **D15**：窄屏抽屉是浮层、宽屏不是。

四条合起来才是「右侧一格」的完整形态：**一格**（D16）、**一个数**（D14）、
**一套释放规则**（D13）、**两种屏宽语义**（D15）。

### 被否决的替代方案

| 方案 | 否决理由 |
|---|---|
| 保留标签条，「＋」只作为补充入口 | 两处真相源（同 D10 的坑）；标签条只列打开过的，读起来像残缺目录 |

## D17. 产品主轴改为「项目」：设备与 agent 降为资源，新增管家

**日期**：2026-11-01。**状态**：已定。

### 决定

AgentFleet 的主轴从「设备 / agent」改为「**项目**」：

```text
Project（中心式 / 隔离式 / 镜像式）
  ├── Butler 管家   项目的唯一入口、长期记忆的持有者、跑在 Hub 上
  ├── Task 看板     默认视图，任务的真身
  ├── 历史          时间线，第二视图
  └── Binding       项目 ↔ 设备上的固定目录 → Device → Agent
```

**同时作废** 2026-10-26 的产品裁定「不做任务分发、项目文件不在设备间传输」。
约束 10 中与本决定无关的三条（Hub 唯一真相源 / 不 P2P / 不同步依赖目录 / 密钥不上传）**原样保留**。

### 为什么改

旧主轴下，产品回答的问题是「**我有哪些设备、它们能干什么**」。
但用户真正的起点从来不是设备，是**一件事**：「把这个项目的构建时间降下来」。
旧模型要求用户自己把这件事翻译成「去哪台设备、开哪个 agent、用哪个目录」——
而**翻译本身就是产品应该承担的工作**。

改主轴的直接后果有四个，每一个都是旧模型给不出的：

1. **有了「记忆」的落脚点**。记忆属于项目，不属于设备，也不属于一次会话。
2. **「进度」有了意义**。没有项目，任务只是零散的会话；有了项目，才有「这个项目现在卡在哪」。
3. **重试换设备成了自然的操作**。Task 没有设备，Execution 才有——换设备是新生一次执行，
   不是改一条记录。
4. **数据不锁死有了具体形态**。项目就是 git 仓库，用户能 `git clone` 走。

### 五个关键取舍（连同被否决的替代方案）

| # | 取舍 | 被否决的方案 | 否决理由 |
|---|---|---|---|
| ① | 管家**不是调度器**：它管「做什么」，选设备交给调度器 | 管家按负载直接挑设备 | 有记忆的判断**不可复现**——同一任务今天派 A 明天派 B，没人说得清为什么 |
| ② | 记忆**分两处**：结构化事实进库，叙事进仓库 `.afleet/MEMORY.md` | 全放库 | 项目知识锁死在本产品里，产品一停就没了 |
| ② | 同上 | 全放仓库 | 没法查询，「上次决定不用 X」这类事实查不出来 |
| ③ | 设备上**固定目录 + worktree 分任务** | 每任务一个 clone | 每个 clone 一份完整 objects，第 N 个任务成本线性增长 |
| ③ | 同上 | 每任务一个临时目录 | 缓存挂在路径上，路径漂移 → 缓存全废 → 每次都冷启动 |
| ④ | 外部 issue **只做单向导入 + 单向回写** | 双向同步 | 「两边都是真相」→ 每次写入都要解冲突 → 解法只能是「以某一边为准」，另一边的用户看到假数据 |
| ⑤ | 项目形态**含隔离式**（代码不出设备，Hub 只存元数据） | 只做中心式 | 代码不允许离开某台机器的项目恰恰最需要「排队 + 有人盯」；只做中心式等于放弃这批场景 |

### 两条补充（2026-11-01，同日修订）

**D17-a：设备与 agent 管理**保留**，且在新主轴下内容变多不变少。**

改主轴时的第一版草稿写过「设备与 agent 不再是入口」，那是**越界**——用户要的是管理，
不是降级。正确的分工是：

- **「做事」从项目进**：派活、看进度、验收；
- **「管理」从设备 / agent 进**：加设备、装 agent、配启动、看磁盘、改配额与清理策略。

新主轴下设备页必须新增：**绑定关系**（绑了哪些项目 / 绑在哪个固定目录）、
**磁盘配额与已用**、**失败归因**（同类失败集中在这台机器就是信号）、清理策略；
agent 页新增：**该 agent 上跑过哪些任务 / 成功率**。

> 与硬约束「不做设备级多资源管理台」不矛盾：那条管的是**终端/文件/git 三个面板不能脱离
> 会话独立存在**，不是「不许有设备管理页」。设备页管配置与健康，不开一堆资源窗口。

**D17-b：执行中改需求，不是「重派 vs 通知」二选一，判据是 `done_when` 还成不成立。**

| 新话的性质 | 处置 |
|---|---|
| 目标不变、做法要换 | **通知当前 agent**（`session/cancel` → 新 prompt，保留上下文） |
| 目标变了 | **`superseded` + 新建任务**，留痕指向旧任务 |
| 只是加约束 | **通知 agent** + **写 `project_memory`** |

- **为什么目标变了不能塞给当前 agent**：让它追移动的靶子，会交出「看板显示完成但你要的不是它」——
  静默做错比报错危险。
- **为什么做法变了不能重派**：已有现场（读过什么、试过什么）比重新跑值钱。
- **打断三条硬规则**：不杀进程（保留现场）/ 必须留痕（记 `interrupted_by_intent`）/
  有上限（同一 Execution 打断 ≥2 次 → 判定任务定义不清 → 停手问人）。
- **`superseded` 是失败形态之一，且「不是失败的失败」**：不重试、不换设备、
  **不进失败归因统计**（否则设备页的失败归因会被用户改需求污染）。

**D17-c：磁盘是任务分配的**硬条件**，不是只管事后清理。**

原先磁盘只写在 `project-and-snapshot.md` §5.3 的「四层处置」里——那是**跑完怎么清**，
漏了「**派活之前谁来算**」。现在明确分成三件事，各归各处：

| 问题 | 归属 |
|---|---|
| 这台机器上这个项目**允许多大** | 绑定 / 设备管理面（配额与清理策略） |
| 现在派过去**跑不跑得动** | **调度**（`scheduling.md` §3.2 / §3.3） |
| 跑完**怎么收回** | `project-and-snapshot.md` §5.3（四层处置） |

调度侧四层：

```text
① 硬过滤：剩余空间 − 安全余量 < worktree 基础开销 → 排除这台
② 打  分：都够跑，按剩余空间充裕度排序（排在第 3.5 键，在负载与内存之后）
③ 进  行：执行中监控实际占用，超预算阈值提前中止 → disk_exhausted
④ 兜  底：同一 (project, device) 绑定默认串行，并行需显式开启 + 按磁盘算并发上限
```

- **判据**：不够会不会导致任务失败？会 → 硬过滤；够但吃紧 → 打分。
- **为什么硬过滤**：剩余空间不够时「这台比较闲」毫无意义，派过去只是把失败推后 20 分钟，
  且会把 `env_broken` 归因到设备——**真正的原因是调度器当初不该派**。
- **只有一半的数是可以事前算的**：worktree 基础开销（checked-out 文件 + 依赖重建体积）能算；
  任务峰值**事前不可知**，所以靠 ③ 执行时监控，**绝不猜一个数**。
- **`disk_exhausted` 单列为一种失败形态，不并进 `env_broken`**：责任方不同——后者要人修机器，
  前者要改调度与配额。并在一起会让磁盘问题永远被当成机器问题去查。
- **④ 比估算更有效**：worktree 不共享依赖与构建产物，两任务并行 = 磁盘占用乘上并发数，
  且缓存互相失效。串行是默认，不是限制。

### 已知代价（明说，不美化）
- **隔离式项目没有「同一起点」的强保证**。Hub 不能验证 commit，只能信设备的承诺。
- **隔离式项目没有叙事记忆**。`.afleet/MEMORY.md` 在设备上，Hub 上的管家读不到。
- **worktree 不共享 `node_modules` / `target`**。依赖必须按 lockfile 哈希复用，
  否则磁盘会失控。这是四层磁盘处置存在的原因。
- **形态只能单向迁移**（隔离式 → 中心式）。反向做不到「真收回去」。
- **看板比会话页早成为默认视图，会重排导航**。旧路由（`/devices`、`/sessions`）保留，
  但默认落地页从 v0.7.0 起改为项目看板。

### 可证伪断言

1. `docs/PRODUCT.md` §3 的主干图与 §3.1 的五实体表**逐项对应**，没有第六个实体。
2. `docs/DEVELOPMENT.md` §4.2 的每一行都能在 `PRODUCT.md` §6.1 找到对应能力，反之亦然
   （§4.1 对齐契约第 1/4 条）。
3. `AGENTS.md` 约束 10 **不再包含「不做任务分发」**，且仍包含三条保留项。
4. 管家文档里**不出现**任何「按负载 / 按空闲挑设备」的规则——出现即为职责越界。

## D18. 连接不再限定「每设备一条 WS」：按用途分连接

**日期**：2026-11-01。**状态**：已定（推翻 v0.1.0 的「每设备一条 WS」）。

### 决定

**推翻**「每设备一条 WS」的裁定，改为**按用途分连接**（控制 / 数据 / 批量），
并且**不再规定必须用 WebSocket**。

### 为什么

旧裁定成立的三个前提，两个已不成立：

| 前提 | 现状 |
|---|---|
| 消息量小（控制帧 + 心跳 + 少量终端字节） | ❌ 项目主轴下多了 git packfile、worktree 操作、依赖重建输出 |
| 每设备只服务一个浏览器会话 | ❌ 看板下多任务并发，（即便单用户）多标签页 |
| 一条连接让路由简单 | ✅ 仍成立，保留 |

最要命的是既有事实：令牌桶**按连接计**（4 MiB 突发 / 1 MiB 每秒），
一次 50 MiB 的 packfile 会把同设备上**其它任务的终端输出饿死 40 秒以上**。
旧产品里这是「已知代价」，新产品里它是**功能性错误**——看板的前提是「多任务并行、随时能看」。

**更根本的**：「必须用 WS」本身不是产品属性。WS 是为穿越企业防火墙选的实现手段。
产品只承诺三条：**节点主动外联 / Hub 不拨入 / 传输可鉴权可审计**。
用 WS、HTTP/2 流、QUIC、git Smart HTTP，都是满足这三条的不同实现。

### 四条硬规则

1. 三条连接**共用同一设备身份**，不因新连接重新 enroll；重连 / `superseded` / 心跳超时
   都按「**这设备的任意连接**」算。
2. **心跳只在控制连接上**；数据 / 批量断开**不判离线**。
3. **决策请求优先级高于批量传输**（收件箱里的选项不能等 40 秒）。
4. **物理可以仍是一条，但那是优化不是契约**：仅当能做到真正的按通道配额时才允许复用。

### 可证伪断言

批量连接传 ≥40 MiB 时：① 控制连接 RTT 增量 <200ms；② 终端吞吐下降 <20%；
③ 决策请求送达浏览器 <1s。任一条不成立即**不符合契约**。
不许用「令牌桶按连接计」辩解——那正是问题本身。

## D19. 收件箱是「待决策队列」，不是通知列表；agent 的权限确认绝不经 Hub

**日期**：2026-11-01。**状态**：已定。

### 决定

- **两个区**：**待决策**（默认打开）/ 动态。通知是广播，收件箱是待办——混在一起，
  完成通知会把真正需要决策的事淹没。
- **三条通路**：设备事实走心跳进动态；**agent 的权限确认只在本机**；
  agent 的业务决策与管家待决事项进待决策。
- **四条硬规则**：必须带 TTL；必须能降级（不能无声卡死）；答案必须留痕；
  同一问题答案可复用（写 `project_memory`）。

### 为什么权限确认绝不经 Hub

如果 agent 的权限确认可以经 Hub 转发、人远程批准，**Hub 就变成了设备的远程控制面**——
攻击者拿到 Hub 就能对设备说「用户已批准执行这条命令」。
`AGENTS.md` 约束 1 的意义正在此处，不是为了省端口。

**界线一句话**：**安全许可**（能不能执行）只在本机；**业务决策**（该怎么做）可以进 Hub。

### 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 全部通知合成一个列表 | 完成通知会淹没待决策项；「必须你选」与「告诉一声」混为一谈 |
| 权限确认也走 Hub 统一入口 | 等于远程控制面，破约束 1 |
| 决策请求不设 TTL | 人睡着时执行永久挂起，且无人发现 |

## D20. 隔离式项目：不出设备 ≠ 不给看

**日期**：2026-11-01。**状态**：已定（**纠正此前过严的自我限制**）。

### 决定

「隔离式项目的代码不出设备」的**全部含义**是：**Hub 拿不到完整仓库**。
它**不是**「Hub 看不到任何关于这次执行的东西」。

| 内容 | 落哪 |
|---|---|
| 源码树 / packfile / commit 对象 / 完整历史 | **只在设备上** |
| 本次执行的**对话详情** | Hub 可存 |
| 本次执行的 **diff / 改动清单** | Hub **按需拉取**，不长期存档 |
| 环境声明（只报哈希不报内容） | Hub 可存 |
| 决策请求的选项与结果（内容由设备裁剪） | Hub 可存 |
| `.afleet/MEMORY.md` | 设备上，**按需读、按需追加** |

**关键区分：`diff` 与 `仓库` 不是一回事。** 一次执行的产出是 `base_commit..HEAD` 的 diff
（几十 KB–几 MB），而仓库是全部历史（GB 级）。前者可以到 Hub，后者不行。

### 为什么纠正

把「没有完整仓库」实现成「什么都看不到」，会让隔离式项目变成黑盒——
而黑盒恰恰是没人愿意用的功能。看板、对话详情、diff、管家总结、执行监控**都该有**。
隔离式真正失去的只有三样：`git clone` 出完整仓库、Hub 侧 CI、**跨设备续跑**
（重建工作区需要完整 commit）。

### 可证伪断言

**看不到**：完整仓库、主干代码、跨设备续跑。

## D21. 最终只有一个产品：AgentFleet 吸收 REX 的能力，不保留其产品模型

**日期**：2026-11-01。**状态**：已定（用户裁定）。

### 决定

REX 不是并列的第二个产品，**最终只有一个产品 —— AgentFleet**。
REX 的处置是**吸收能力、不保留模型**。

| REX 的东西 | 处置 |
|---|---|
| 协议实现（SSH / DB / Redis / S3 / SFTP / TCP 透传，设备侧拨号） | **接**，作为 connector 插件 + **技能 / MCP** 暴露给 agent |
| 文件传输引擎（数据不经浏览器） | **接** |
| 内网反向隧道经验 | **接**（已同构） |
| **多态 Resource 抽象 + 设备级资源管理台** | **拒**（`AGENTS.md` 约束 3 + 已排除的形态） |
| SIP / 浏览器直连资源 | **拒**（与项目主轴无关，只增加攻击面） |

### 技能 / MCP：能力怎么给 agent 用（核心裁定）

`AGENTS.md` 约束 3 原写「connector 只面向页面用户，**不向 agent 暴露**」。
这条要**按新需求重新裁定**，但**不能简单删掉**——它防的是真问题。

| 暴露方式 | 判断 |
|---|---|
| connector 直接对 agent 开放 | ❌ **仍然禁止**：等于给所有 agent 开一条统一提权通道，而我们替它维护权限 |
| **作为技能按任务级授予** | ✅ **主路径**：任务没声明就没有，与 `required_capabilities` 同一套机制 |
| **作为 MCP server 暴露** | ✅ **并行支持**：标准接口，任何支持 MCP 的 agent 都能用 |

**为什么这样落在中间**：约束 3 的精神是「agent 用它自己装的能力，我们不替它管权限」。
技能 / MCP 恰好落在中间——**我们提供通道，但不替 agent 决定能不能用**；
能不能用由**任务级声明（人给的）**决定，不由运行时猜。

**安全边界（写死）**：

- **凭据不进 agent 上下文**：agent 说「用 `db-prod` 执行这条 SQL」，凭据由设备侧注入。
  这是 MCP 相比「把连接串塞进 prompt」的核心价值。
- **每次连接与操作进审计轨迹**。
- 隔离式项目下这些操作**仍不出设备**（本来就是设备侧拨号）。

> 因此 `AGENTS.md` 约束 3 需要改写：保留「不引入多态 Resource 抽象」与
> 「不做设备级多资源管理台」，把「不向 agent 暴露」改为
> 「**只经任务级授予的技能 / MCP 暴露，不开放任意 connector**」。

## D22. 「接意图」靠 skill，不靠写死的意图分类

**日期**：2026-11-01。**状态**：已定（用户裁定）。

### 决定

**不预设「意图类型」枚举**，改为给管家一组**技能（skill）**，由大模型自行决定怎么推进：
`project.status` / `project.history` / `task.create` / `task.clarify` / `memory.read` / `memory.write`。

**约束**：

- 技能只声明「能做什么」，**不规定「必须先做什么」**。
- 意图记录**不存「意图类型」字段**——一旦有类型字段，实现就会退回成分类器。
- **意图记录不是独立表**，是 `project_memory` 的一类事件（`utterance`）。生命周期与记忆一样长，
  没必要为它单开一张要单独清理的表。

### 为什么

> **意图是开放集合，分类是封闭集合。用封闭的东西去接开放的东西，永远差一截。**

用一张固定分类表去接，只能接住表里有的那几种，剩下的全被塞进「其它」，反而更糟。
skill + 大模型恰好反过来：**能力边界由我们定，判断顺序交给模型**——
与 `AGENTS.md` 约束 3 对 agent 的一贯态度一致。

## D23. `done_when` 必须是「判定码 + 人话描述」

**日期**：2026-11-01。**状态**：已定（用户裁定）。

### 决定

```jsonc
{ "criteria": [ { "kind": "command", "run": "cargo test", "expect": { "exit_code": 0 } } ],
  "description": "构建时间降到 60s 内，且测试全绿" }
```

- **`criteria` 机器可判定**（命令 + 期望退出码 / 阈值），判定结果确定，**不依赖模型**。
- **`description` 写给人看**，不参与判定。
- **至少有一个**：只有 `criteria` → 可自动判绿；只有 `description` → **必须标「需人工验收」**。

### 为什么不许纯自然语言

自然语言判定必须经过模型，**模型判定不可复现**——同一个 diff 今天判绿明天判红，
验收就失去了意义。而**验收是本产品唯一的价值锚点**。

## D24. 项目可归档、不可删除；设备有历史则不可删

**日期**：2026-11-01。**状态**：已定（用户裁定）。

- **项目只能归档**：归档后不出现在列表与看板首页、停止派发，但历史执行、总结、轨迹全保留，可取消归档。
- **不提供删除**：项目是真相源，删除会让已合入任务的历史、失败归因、成本记录一并丢失。
- **设备**：**有历史执行记录的设备不允许删除**；只有无历史时才能删，历史执行记录永久保留。

### 为什么

**失败归因和审计需要历史。** 一个项目跑了十次失败的记录，对排障比「一个干净的空项目」更有价值。
删除是本产品里**唯一会让证据消失的操作**，不该在第一版提供。

## D26. 不做 DAG：Hub 不承担工作流编排

**日期**：2026-11-01。**状态**：已定（用户提问后确认）。

### 决定

**明确不做任务依赖 DAG**（「A 完成才能做 B」）。这不是「没有这种场景」，是**刻意的范围切割**。

### 为什么

1. **调度器不是工作流引擎**。Hub 调度器的职责是「把任务丢到哪台设备」，不是编排任务间父子关系。
   加了 DAG 就要处理超时传播、部分失败、循环检测、重试锁，**复杂度指数级上涨**。
2. **已有更简单的替代**：任务 B 的 `done_when` 写「等 A 的分支出现」，或人在 A 完成后建 B。
   管家可以**建议**「A 做完再做 B」，但不强制编排。
3. **产品边界**：`AGENTS.md` 约束 8 已定——Hub 只编排「任务 → 节点」，
   **不编排 agent 运行时的父子关系**。DAG 是往那个禁止方向走。

### 未来的口子（留但不实现）

若出现强需求，依赖关系应表达在**任务模板**或**仓库里的流水线配置**里，
Hub 只负责「按顺序派单个任务」，**不引入任务图**。
