# 任务分发调度 / Task Scheduling

> 问题：一个完整任务要分发到某台设备上执行。**选哪台？**
> 约束 9 已经承诺「按设备能力/性能自动调度」，本文把这句话落成可实现的设计。

---

## 1. 先分清：两种路由，不要混

这是最容易搞错的地方——项目里其实有**两套独立的路由**：

| | 任务路由（本文） | 推理路由（M6） |
|---|---|---|
| 选什么 | **一台设备** | **一个模型副本所在的设备** |
| 看什么 | 能力 + 负载 + 在线状态 | 模型是否已装、内存够不够、当前是否忙 |
| 粒度 | 一次任务分发决定 | 每个 API 请求决定 |
| 里程碑 | M5 | M6 |

**两者都要读 `resources`，但决策目标不同**：
任务路由问「谁有闲力做这件事」，推理路由问「哪个副本能立刻吐出这个 token」。

> **不要**做成一个大一统的调度器。任务路由与推理路由可以各写一套，
> 共享的只有节点能力数据。

## 2. 心跳上报什么

心跳（周期由 Hub 在 `auth_ok` 下发，默认 15s，超时 45s 判离线）带一份
**自描述的能力与负载**。

M2 实际上报的形状见 `crates/node-core/src/heartbeat.rs`。与下面这份目标形状的
**差异都是有意的**：

- `workspace_roots` 是**顶层数组**而不是 `workspace.roots` 嵌套对象——
  协议层 `Heartbeat` 就是这样定义的（§2 的「只报根」约束与嵌套与否无关）；
- `resources` 在 **M0/M1 是 `null`，M2 起真采集**。理由是「取真实负载要读 `/proc`
  或引依赖，而编一个数字比不报坏得多」——这条理由仍然成立，**编造数字依然禁止**；
  M2 排进了真采集（node 读 `/proc/loadavg` + `/proc/meminfo`），所以不再是「没有」，
  而是「有就报、探测失败就留 null」。Hub 侧对缺省字段的约定仍是「保持上一次的值」，
  所以 `null` 依然让 Hub 保留旧事实。**注意 `load_percent` 有 `min(100)` 截断**
  （`hub-server/src/routes/api.rs`），高负载设备恒读 100，不能拿它做精确比较。

- **百分比字段是扁平的**（`cpu_percent` / `mem_percent` 放在顶层，明细另放在
  `load` / `memory` 里），与下面目标形状的嵌套写法不同。原因是**读的那一边**已定：
  `api.rs` 的 `load_percent` 只按顶层键找（`CPU_PERCENT_FIELDS` / `MEM_PERCENT_FIELDS`），
  嵌套对象会让它恒返回 `None`——设备表那两列会继续是 `—`，而「采集已落地」这条
  事实在页面上完全看不出来（这正是那条欠账空了两三个里程碑的原因：目标形状是
  嵌套的，读取口径是扁平的，两边谁也没错，只是对不上）。明细与百分比**都报**：
  前者给将来的路由（需要 `load1` 与 `total_mb`），后者给今天的两列。

- `cpu_percent` 是**每核负载**（`load1 / cores × 100`），**不是 CPU 利用率**：
  load 含不可中断睡眠（等 IO），所以 IO 密集的机器会偏高于它的真实占用。报它
  是因为「谁相对更闲」的排序用得上，而不需要跨心跳存状态的算法只有这一个。
  `mem_percent` 用 `MemAvailable` 而不是 `MemFree`：后者在跑久了的机器上恒接近
  0，会把它读成「内存满了」——那是一份撒谎的事实。

```jsonc
{
  "node_version": "0.1.0",
  "capabilities": {
    "connectors": ["terminal", "files", "git", "exec"],
    "agents": [                     // 本机探测到的 agent（不是「支持哪些」）
      { "id": "opencode", "name": "opencode",
        "version": "2.1.4", "available": true, "error": null }
    ],
    "os": "linux", "arch": "aarch64",
    "container_runtime": null       // 有 docker/podman 则给出，null 表示没有
  },
  "resources": {
    "cpu": { "cores": 4, "model": "cortex-a72", "arch": "aarch64" },
    "memory": { "total_mb": 4096, "available_mb": 2870 },
    "gpu": null,                    // 有则 { "name": "...", "vram_mb": 8192, "count": 1 }
    "load": { "load1": 1.8, "load_per_core": 0.45, "active_sessions": 2 },
    "disk": { "workspace_free_mb": 12800 }
  },
  "workspace_roots": ["/w"]         // 只到配置的根目录一级，绝不递归
}
```

**`agents` 的三态（M2）**：每一项带 `available`，因为「装了」与「能用」是两件事：

| 情形 | `available` | `version` | `error` |
|---|---|---|---|
| 未装 | `false` | `null` | `null` |
| 已装且 `--version` 答出来 | `true` | 版本串 | `null` |
| 已装但跑不起来 / 超时 | `false` | `null` | 可读原因 |

**为什么不是「只报可用的」**：页面要能显示「你装的那个坏了」，只报可用的会让
「装坏」与「没装」在页面上长得一样。而**建会话的门禁只认 `available: true`**，
所以列出来不等于可用（`api.rs` 的 `available_agent_names` 与 `agent_list` 是两个函数）。

**形态从字符串改成了对象**（M1 是 `["opencode"]`）。Hub 侧 `agent_list()`
两种都认——只认一种会让另一侧静默丢数据：认不出新形态则页面 agent 列表变空，
认不出旧形态则升级窗口里还在发旧帧的设备列表变空。

**探测不在心跳路径上做**：探测要起子进程、最多等 2 秒，放进心跳臂等于让心跳
的准时性取决于本机装了什么 agent。心跳只读缓存，刷新在连接建立后、`select!` 之外
（M1 的 `exec` 在 `open()` 里同步跑命令堵住心跳臂就是这个形状）。

**心跳绝不报告任何路径细节**——这是信息泄露面，不是功能缺陷：
- 不报子目录、不报仓库名、不报文件名、不报 `head` 提交号；
- 不报 `<data_dir_root>` 下的任何内容（那是 `identity.json`、模型 key 的所在）；
- 不报 `.git/`、`.env`、`~/.ssh/` 这类高价值路径的存在与否
  （「存在」本身就是情报：泄露了用户在哪有私钥、哪个项目用了什么 secret）。

`workspace_roots` 只用于回答「这台设备上大致有多少工作区可路由」，
**具体路由到哪个仓库由 Hub 侧配置 + 用户显式指定**（见 `workspace-and-sync.md` §3），
不靠心跳枚举。若将来需要完整工作区清单，走**已鉴权的专用查询 API**，不进心跳。

> 已知取舍：`workspace_roots` 本身仍是路径，但它是**调用方给进来**的——
> `heartbeat::workspace_roots` 收的是一串根，模块自己一次都不遍历文件系统。

### 2.1 三类字段，别混为一谈

| 类别 | 例子 | 变化频率 | 谁关心 |
|---|---|---|---|
| **能力**（能做） | connectors / agents / arch / GPU 有无 | 几乎不变（装东西才变；M2 起 `agents` 由探测得出） | 任务路由的**硬过滤** |
| **负载**（忙不忙） | load / available_mb / active_sessions | 每心跳变 | 任务路由的**打分** |
| **存量**（有什么） | workspace / 已装模型 | 按需变 | 推理路由 |

**关键：能力用于「排除」，负载用于「排序」。** 混在一起就会写出「内存高的设备优先」
这种错逻辑——一台 64G 内存但满载的机器，比一台 8G 空闲的机器差。

### 2.2 缓存与新鲜度

Hub 内存里维护一份 `node_id → 上报`，**只在心跳时更新**，路由时读内存不读库。
落库的只有 `last_seen_at` 与一份历史摘要——避免路由路径碰磁盘（多设备高频写会 SQLITE_BUSY）。

## 3. 硬过滤：先排除，再打分

**过滤顺序固定为三层**，与 `task-model.md` §4.1 是同一套（那边定义语义，这边执行）：

```text
候选 = 所有 online 节点
  ↓ ⓪ 任务级 allowed_devices / allowed_agents / required_capabilities？
  ↓    否 → 排除（派活人说了算，先于一切偏好）
  ↓ ① 项目级隔离策略通过？  否 → 排除（隔离式项目只有绑定的那台有资格）
  ↓ ② 有所需 agent？        否 → 排除
  ↓ ③ 有所需 connector？    否 → 排除
  ↓ ④ 内存够？              否 → 排除
  ↓ ⑤ 磁盘够？              否 → 排除（见 §3.2，这是最容易被写漏的一条）
  ↓ ⑥ 能拿到代码？          否 → 排除
  ↓ ⑦ 该绑定是否已有任务在跑？是 → 排除（默认串行，见 §3.3）
得分 → 排序 → 选第一名
```

**过滤器是硬的**：不满足就出局，不靠高分补偿。能力不够的设备再闲也不能用。

> **⓪ 必须在 ①②③ 之前**：如果先按负载挑出「最闲的那台」再检查 `allowed_*`，
> 拒绝就变成了「挑错了再重挑」——`allowed_*` 在语义上从「约束」降级成「偏好」。

### 3.1 「能拿到代码」这一条容易漏

任务说「去跑这个仓库的测试」，但那台设备：

- **本地没有这个仓库** → 从 Hub `fetch`（Hub 就是那个远端，见 `project-and-snapshot.md` §7）
- **连不上 origin**（离线内网、公司墙） → 由 **Hub** 去拉上游（镜像式），节点不直连 origin

所以过滤时要问的是「**这台设备能不能拿到代码**」，而不是「它有没有这个目录」。

### 3.2 磁盘：硬过滤还是打分，取决于「不够会不会导致失败」

**磁盘不是一个数，是两件事，必须分开**：

| | 归属 | 回答 |
|---|---|---|
| **配额与清理策略** | 绑定 / 设备管理面 | 「这台机器上这个项目**允许多大**」 |
| **余量参与派活** | **调度（本节）** | 「现在派过去**跑不跑得动**」 |

判据只有一条：**不够会不会让任务失败。**

```text
剩余空间 − 安全余量 < worktree 基础开销   → 硬排除（⑤）
      否则                            → 进入打分（§4.1 第 3.5 键）
```

**worktree 基础开销怎么算**（这是唯一能事前算准的量）：

```text
基础开销 = checked-out 文件总大小      ← git 能算：tree 的 blob 总大小
         + 依赖重建体积                ← 按 lockfile 类型粗估（不是精确值）
```

**为什么必须前置成硬过滤**：剩余空间不够时，「这台机器比较闲」毫无意义——
派过去只是**把失败推后到 20 分钟后**，而失败形态会变成 `env_broken`（磁盘满）、
归因到设备。但真正的原因是**调度器当初不该派**。这条归因污染必须避免。

**这个数诚实地说只有一半**：任务峰值（agent 会写多少临时文件、构建产物多大）
**事前不可知**。所以：

- **不自作聪明猜一个数**——编数字比不报坏得多（本项目的既有教训）。
- 改成**执行时监控**：Execution 跑的过程中设备上报 worktree 实际占用，
  超预算阈值 → **提前中止**并标 `disk_exhausted`（见 `task-model.md` §3），
  而不是等它把设备写满、把整台机器拖垮。
- 这个中止要**保留前 N 个产物做诊断**，但**不保留整个工作树**——那正是要避免的磁盘灾难。

**「所有设备都被磁盘排除」不是任务失败，是 `rejected(disk_insufficient)`**：
不产生 Execution、不占重试次数，且**必须说清是「磁盘不够」而不是「设备离线」**——
这两种「没设备能跑」处置完全不同，一个去清理，一个去开机。

### 3.3 同一绑定默认串行：这条比估算峰值更有效

> **同一个 `(project, device)` 绑定，默认同一时刻只跑一个任务。**

理由直接来自磁盘：worktree **不共享** `node_modules` / `target`，两个任务并行
= 两份依赖 + 两套构建产物 + 两份构建临时文件，磁盘占用**不是翻倍，是乘上并发数**；
而且它们的构建缓存还会互相失效。

需要并行时**在绑定上显式开启**，且并发上限**按磁盘余量算，不按 CPU 算**。
这不是全局开关——树莓派和服务器该有不同答案。

## 4. 打分：先定偏好，再排序

### 4.1 排序键（依次比较，第一个不同就分出高下）

```text
1. 用户指定 / 任务钉死      → 唯一候选，直接选，不打分
2. 负载（load_per_core）    → 越低越好
3. 剩余内存                 → 越多越好
3.5 剩余磁盘充裕度          → 越多越好（都过了 §3.2 的硬门槛之后）
4. 「亲和」：已在该节点有工作区 → 优先
5. 「亲和」：已装目标 agent 且版本匹配 → 优先
6. 稳定的 tiebreak          → node_id 字典序，保证结果可预测
```

**为什么磁盘排在负载和内存之后**：三台都够跑时，磁盘充裕度是**最弱的信号**——
它只在「吃紧」时有意义（吃紧会中途爆），而任务失败的第一因是负载与内存。
把磁盘排到前面会让「一台几乎没空间的空闲机器」压过「空间充裕的正常机器」。

**为什么负载排在亲和前面**：让设备均衡使用。
**为什么亲和又重要**：已经 clone 过仓库的设备省一次拉取，已经跑着的 agent 少一次冷启动。

### 4.2 一票否决（钉死）

用户可以在任务上说「必须在设备 X 上跑」（比如要访问设备上的串口、
要验证树莓派特有的硬件行为）。**钉死后跳过全部过滤与打分**。

这也是 M3 里程碑里「在某台**指定**设备上开会话」的延续——能力足够时自动选，
用户需要控制时能钉死。

### 4.3 不做的

- **不做加权综合评分**：把内存、负载、亲和揉成一个浮点数 = 权重全靠拍脑袋，
  且不可解释（「为什么它选了这台？」答不上来）。有序比较链可以解释。
- **不做预测式调度**（看趋势提前分流）：个人设备场景不值得，
  且心跳稀疏，预测不可靠。
- **不做优先级抢占**：已派发的任务不因为新任务来了就打断。

## 5. 派发与落定

> **状态机以 `task-model.md` §2 为准**（`pending / queued / running / review / done / failed`）。
> 本节只说调度器**在派发那一步**做什么。

```text
Hub 选定 node
  → 落一条 execution 记录（device_id + agent_id + worktree_path + base_commit）
  → task.state = queued
  → 告诉该 node「项目 P、起点 <commit>、worktree 里的任务内容是…」（project-and-snapshot §6）
  → 节点校验 HEAD == base_commit？不等 → 立刻报 baseline_mismatch，不硬跑
  → task.state = running
  → 每个动作进轨迹（session-and-trajectory §3）
  → 完成后 push 任务分支 → task.state = review（不是 done）
```

- **任务状态在 Hub，不在节点**（状态外置）。节点掉线，任务状态不丢。
- **节点失联超阈值 → `failed(interrupted)`**，先试检查点续跑（`task-continuity.md` §3）。

### 5.1 重试**必须换条件**，且磁盘是换设备的理由之一

> **旧文写「重试不自动换设备（环境一致）」——已作废（2026-11-01）。**
> 该说法假设「同一台设备 = 同样的环境 = 更可靠」，但实测方向相反：
> **同样的条件下重试不会奇迹般成功**，而失败原因往往正是**那台机器的环境**
> （`env_broken`：磁盘满、依赖装不上、工具链缺）。
> 用户已明确要求：**失败重试时换一台设备重新调度。**

| 情形 | 调度器怎么做 |
|---|---|
| `env_broken`（含 `disk_exhausted`） | **必须换设备**——回原机重试是把已知坏环境再试一次 |
| `task_failed` | **换设备**（需人确认或规则放行，见 `task-model.md` §3.2） |
| `agent_error` | **换 agent 优先于换设备**（同 agent 重启大概率同样崩） |
| `interrupted` | **先续跑**（同设备，有检查点）；续不上才换设备 |
| `baseline_mismatch` | 同设备**重新 fetch** 一次；再失败就换设备 |
| `superseded` | **不重试、不换设备**——需求变了，换机器没用 |

**唯一「回到同一台」的合法情形是有检查点可续**（`interrupted`），
因为那时要保的是**现场**，不是环境。

**换设备时的磁盘约束仍然生效**：新设备同样要过 §3.2 的硬门槛。
「换一台试」不等于「换一台不管空间够不够」。

## 6. 数据表

> **旧的 `task( ... node_id, state = pending/dispatched/running/done/failed )` 已作废（2026-11-01）。**
> 旧模型把 `node_id` 放在 task 上、把状态压成五态——两条都与 `task-model.md` 冲突：
> **Task 本身没有设备**（否则重试换设备变成改数据，而不是新生一次执行），
> 状态是**六态**且 `review` 必须在。
> 权威形状见 `task-model.md` §5；本节只列调度器**读**什么、**写**什么。

```text
-- M0 不建 node_report 表：全量心跳摘要只落 device.capabilities / device.resources
-- （见 README.md §3）。历史负载无消费方，建表即负担。
-- 若将来需要冷启动时「离线设备的最后一份能力」，从 device 表读即可，
-- 不必引入第二份存储。

-- 调度器只写这处
execution(
  id, task_id,
  device_id, agent_id,        -- 三件套，只有 execution 有
  worktree_path, branch,
  base_commit,                -- 本次实际起点（baseline_mismatch 的比对依据）
  state,                      -- running / failed / succeeded
  failure_kind, reason, evidence,
  interrupted_by_intent, interrupt_count,
  started_at, ended_at
)

-- 调度器推进的边（六态见 task-model §2）：pending → queued → running → failed
task.state

-- 调度器只读，每次路由现取，不落库
心跳缓存   capabilities / resources / disk.workspace_free_mb / active_sessions
绑定信息   binding(project_id, node_id) → path, quota, cleanup_policy, max_concurrency
```

- `task.state` 每次流转都追加一条事件到轨迹，**不 UPDATE 覆盖历史**。
- **路由路径读内存不读库**（§2.2）：多设备高频写会 `SQLITE_BUSY`。
- SQLite：建库必须 `journal_mode=WAL` + `busy_timeout`。
