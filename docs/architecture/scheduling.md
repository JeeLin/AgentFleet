# 任务分发调度 / Task Scheduling

> 问题：一个完整任务要分发到某台设备上执行。**选哪台？**
> 约束 9 已经承诺「按设备能力/性能自动调度」，本文把这句话落成可实现的设计。

---

## 1. 先分清：两种路由，不要混

这是最容易搞错的地方——项目里其实有**两套独立的路由**：

| | 任务路由（本文） | 推理路由（M6） |
|---|---|---|
| 选什么 | **一台设备** | **一个模型副本所在的设备** |
| 看什么 | 能力 + 负载 + 在线状态 | 模型是否已装、内存够不够、当前是否忙 |
| 粒度 | 一次任务分发决定 | 每个 API 请求决定 |
| 里程碑 | M5 | M6 |

**两者都要读 `resources`，但决策目标不同**：
任务路由问「谁有闲力做这件事」，推理路由问「哪个副本能立刻吐出这个 token」。

> **不要**做成一个大一统的调度器。任务路由与推理路由可以各写一套，
> 共享的只有节点能力数据。

---

## 2. 心跳上报什么

心跳（建议周期 15s，超时 45s 判离线）带一份**自描述的能力与负载**：

```jsonc
{
  "node_version": "0.1.0",
  "capabilities": {
    "connectors": ["terminal", "files", "git", "exec"],
    "agents": [                     // 已装且就绪的 agent（不是「支持」）
      { "name": "opencode", "version": "0.4.2" }
    ],
    "os": "linux", "arch": "aarch64",
    "container_runtime": null       // 有 docker/podman 则给出，null 表示没有
  },
  "resources": {
    "cpu": { "cores": 4, "model": "cortex-a72", "arch": "aarch64" },
    "memory": { "total_mb": 4096, "available_mb": 2870 },
    "gpu": null,                    // 有则 { "name": "...", "vram_mb": 8192, "count": 1 }
    "load": { "load1": 1.8, "load_per_core": 0.45, "active_sessions": 2 },
    "disk": { "workspace_free_mb": 12800 }
  },
  "workspace": {                    // 这个节点上的可用工作区
    "repos": [ { "path": "/w/main", "is_git": true, "head": "abc123" } ]
  }
}
```

### 2.1 三类字段，别混为一谈

| 类别 | 例子 | 变化频率 | 谁关心 |
|---|---|---|---|
| **能力**（能做） | connectors / agents / arch / GPU 有无 | 几乎不变（装东西才变） | 任务路由的**硬过滤** |
| **负载**（忙不忙） | load / available_mb / active_sessions | 每心跳变 | 任务路由的**打分** |
| **存量**（有什么） | workspace / 已装模型 | 按需变 | 推理路由 |

**关键：能力用于「排除」，负载用于「排序」。** 混在一起就会写出「内存高的设备优先」
这种错逻辑——一台 64G 内存但满载的机器，比一台 8G 空闲的机器差。

### 2.2 缓存与新鲜度

Hub 内存里维护一份 `node_id → 上报`，**只在心跳时更新**，路由时读内存不读库。
落库的只有 `last_seen_at` 与一份历史摘要——避免路由路径碰磁盘（多设备高频写会 SQLITE_BUSY）。

## 3. 硬过滤：先排除，再打分

```text
候选 = 所有 online 节点
  ↓ ① 在线？            否 → 排除
  ↓ ② 有所需 agent？     否 → 排除（该任务点名要 opencode）
  ↓ ③ 有所需 connector？否 → 排除（要做 git diff，但这个节点没 git）
  ↓ ④ 内存够？          否 → 排除
  ↓ ⑤ 磁盘够？          否 → 排除
  ↓ ⑥ 能拿到代码？      否 → 排除（git 项目要看节点能否连 origin）
得分 → 排序 → 选第一名
```

**过滤器是硬的**：不满足就出局，不靠高分补偿。
能力不够的设备再闲也不能用。

### 3.1 「能拿到代码」这一条容易漏

任务说「去跑这个仓库的测试」，但那台设备：

- **本地没有这个仓库** → 要么从 origin clone，要么从 Hub CAS 拉快照
- **连不上 origin**（离线内网、公司墙） → 只有 Hub mirror 或已有快照可用

所以过滤时要问的是「**这台设备能不能拿到代码**」，而不是「它有没有这个目录」。
需要预判的话，§4.2 有一票否决的 `pinned` 机制。

## 4. 打分：先定偏好，再排序

### 4.1 排序键（依次比较，第一个不同就分出高下）

```text
1. 用户指定 / 任务钉死     → 唯一候选，直接选，不打分
2. 负载（load_per_core）    → 越低越好
3. 剩余内存                 → 越多越好
4. 「亲和」：已在该节点有工作区 → 优先
5. 「亲和」：已装目标 agent 且版本匹配 → 优先
6. 稳定的 tiebreak         → node_id 字典序，保证结果可预测
```

**为什么负载排在亲和前面**：让设备均衡使用。
**为什么亲和又重要**：已经 clone 过仓库的设备省一次拉取，已经跑着的 agent 少一次冷启动。

### 4.2 一票否决（钉死）

用户可以在任务上说「必须在设备 X 上跑」（比如要访问设备上的串口、
要验证树莓派特有的硬件行为）。**钉死后跳过全部过滤与打分**。

这也是 M3 里程碑里「在某台**指定**设备上开会话」的延续——能力足够时自动选，
用户需要控制时能钉死。

### 4.3 不做的

- **不做加权综合评分**：把内存、负载、亲和揉成一个浮点数 = 权重全靠拍脑袋，
  且不可解释（「为什么它选了这台？」答不上来）。有序比较链可以解释。
- **不做预测式调度**（看趋势提前分流）：个人设备场景不值得，
  且心跳稀疏，预测不可靠。
- **不做优先级抢占**：已派发的任务不因为新任务来了就打断。

## 5. 派发与落定

```text
Hub 选定 node → 落一条 task 记录（node_id + 工作区来源，见 task-continuity §6.1）
             → 告诉子 agent 「你在 node X，工作区 /w/task-123，任务内容是…」
             → 子 agent 的每个动作进轨迹（session-and-trajectory §3）
             → 完成后回报状态 + 产物按 task_id 归档（workspace-and-sync §5）
```

**状态机**（Hub 侧持久化，节点无状态）：

```text
pending ──派发──> dispatched ──节点确认──> running ──> done
   │                  │                      │
   │                  └──节点拒绝─────────────┤
   └───────────────超时 / 节点失联───────────┴──> failed
```

- **任务状态在 Hub，不在节点**（约束：状态外置）。节点掉线，任务状态不丢。
- 节点失联超阈值 → `failed`，可从检查点续跑（见 `task-continuity.md` §3）。
- **重试不自动换设备**：同一任务重试应回到同一台设备（环境一致）；
  换设备等于换环境，等于新任务。

## 6. 数据表

```text
node_report(       -- 不落库全量，只保留最近一次摘要，供调试与冷启动
  node_id, seen_at,
  capabilities TEXT,   -- JSON
  resources    TEXT    -- JSON
)

task(
  id              TEXT PK,
  session_id      TEXT,     -- 归属会话（可能为 NULL：纯后台任务）
  parent_task_id  TEXT,     -- 子任务指向主任务（见 task-continuity §6.1）
  node_id         TEXT,     -- 钉死或路由选定后落定
  pinned          INTEGER,  -- 1 = 用户钉死，跳过路由
  workspace_source TEXT,    -- head / head+dirty / snapshot（分发时用户确认）
  state           TEXT,     -- pending/dispatched/running/done/failed
  created_at, started_at, finished_at
)
```

- `task.state` 每次流转都追加一条事件到轨迹，**不 UPDATE 覆盖历史**。
- SQLite：建库必须 `journal_mode=WAL` + `busy_timeout`。

## 7. 待定

- **多任务队列的优先级**：同一节点上任务排队满了怎么办——拒绝、还是排后？当前不排队，
  派发即执行；任务多了再说。
- **亲和权重的实际取值**：§4.1 的「亲和优先」是排在负载之后还是并列，
  等真实使用后按数据调。
- **任务重试与设备故障的交互**：节点永久损坏时任务是否自动改派另一台
  —— 当前定为**不改派**（换设备=换环境），但用户可手动重派。
