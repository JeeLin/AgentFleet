# 项目与快照 / Project and Snapshot

> 产品的**主轴**是项目，本文定义 Project / Binding / Snapshot 三个实体的模型。
> 产品定位见 `docs/PRODUCT.md` §3；管家与任务见 `butler.md`、`task-model.md`。
> 排期见 `docs/DEVELOPMENT.md`，**本文不排期**。

> 问题：同一个项目的任务分到**不同设备**上执行时，怎么保证它们站在**同一个起点**上，
> 且这个「一样」是可判定、可复现、可审计的？

## 1. 核心概念

| 概念 | 是什么 | 身份 / 主键 |
|---|---|---|
| **Project** | Hub 上的一个 **git 裸仓库** | 项目名 |
| **Snapshot** | 一次快照 = 一个 **commit** | commit hash（内容寻址） |
| **Binding** | 项目 ↔ 设备上的**固定目录** | `(project_id, node_id) → path` |
| **TaskBranch** | 任务产出 = 设备推回来的一条**分支** | 分支名 |

**设计地基**：用 git commit 做快照身份之后，「两台设备的基础一样吗」从一句感觉
变成了一个**可判定的命题**——`HEAD == <commit>`，且这个断言不可伪造（tree hash 是内容寻址的）。

## 2. 三种形态 / Three shapes

形态是 **Project 的一个属性**，不是三种产品。三种形态共用同一套 Task / Binding / 看板 / 管家，
差别只在「代码从哪来、到哪去」。

| 形态 | 代码在哪 | Hub 存什么 | 起点是什么 | Hub 验证内容吗 |
|---|---|---|---|---|
| **中心式** `central` | Hub 的裸仓库 | 全部代码 + 元数据 | Hub 上的 commit | **验证** |
| **镜像式** `mirror` | 上游 + Hub 镜像 | 镜像的全部代码 + 元数据 | Hub 上镜像的 commit | **验证** |
| **隔离式** `isolated` | **只在指定设备上** | **只有元数据** + 按需拉取的 diff / 对话（§2.1.1） | 该设备上的 commit hash | **不验证** |

### 2.1 为什么需要隔离式

有些项目**代码不允许离开某台机器**：客户现场、内网、合规要求、或者用户自己不愿意上传。
如果产品只能做中心式，这些项目就完全用不了——而那恰恰是最需要「多任务排队 + 有人盯」
的场景。

隔离式的取舍必须明说：

- **Hub 不知道代码长什么样**。它只知道「这个任务声称自己的起点是 `abc123`」。
- 但**Hub 能看到这次执行做了什么**：对话、diff、改动清单按需向设备取（§2.1.1）。
  「不知道代码」指的是**没有完整仓库**，不是「什么都看不到」。
- 所以**隔离式项目不能用「同一起点」做保证**——那个保证依赖 Hub 能验证 commit。
  它退化成「设备自己的承诺」。
- 但仍然**有绑定、有看板、有管家、有任务约束**。产品的主体价值不依赖代码在 Hub 上。

### 2.1.1 隔离式：不出设备 ≠ 不给看

**这一节是在纠正一个过严的自我限制。**

「隔离式项目的代码不出设备」的本意是：**代码不落到 Hub 的磁盘上、不随 git 上传**。
它**不是**「Hub 看不到任何关于这次执行的东西」。把后者当前者，会把隔离式项目做成黑盒——
而黑盒恰恰是没人愿意用的功能。

正确的界线按**存储位置**分，不按「能不能看见」分：

| 内容 | 落哪 | 为什么 |
|---|---|---|
| **源码树 / packfile / commit 对象** | **只在设备上** | 这是「不出设备」的**全部**含义 |
| **本次执行的对话详情**（User/Assistant/Tool 事件流） | **Hub 可存** | 用户就是设备的主人，看自己设备的对话在权限内 |
| **本次执行的改动**（文件清单 + diff） | **Hub 可读**，按需拉取 | 「这次改了什么」是看板核心信息，看不到等于看板失效 |
| **环境声明**（lockfile 哈希 + 工具链版本） | Hub 可存（**只报哈希不报内容**） | 见 §4 |
| **决策请求的选项与结果** | Hub 可存 | 见 `butler.md` §2.2.2 |
| **整个仓库的完整历史 / 主干代码** | **只在设备上** | Hub 不需要，也不该有 |

**关键区分：`diff` 与 `仓库` 不是一回事。**

一次执行的产出是 `base_commit..HEAD` 的 diff——那是**这次工作的结果**，几十 KB 到几 MB。
而仓库是**全部历史**，GB 级，那才是「代码」的真正含义。**前者可以到 Hub，后者不行。**

所以隔离式项目在 Hub 上**照样有**：看板、任务详情的对话、本次改动的 diff、管家总结、进度监控。
它**没有**的只是：能 `git clone` 出完整仓库、能用 Hub 的 CI、
**跨设备续跑**（重建工作区需要完整 commit，而 Hub 没有）。

> **一句话**：隔离式 = **Hub 拿不到完整仓库**，不是 **Hub 拿不到任何信息**。
> 用前者的严格度去实现后者，只会把一个有用的功能做成没人用的摆设。

**由此产生的一条硬规则**：隔离式项目的 diff / 对话**按需拉取、Hub 不长期存档**——
想看时向设备要，看完即释放。这样「代码不上传」在存储层面仍然成立，
而你已经能得到「看板 + 对话 + diff + 总结」的全部体验。

### 2.2 形态可迁移，单向

- **隔离式 → 中心式**：把仓库推上 Hub，形态翻转。**允许**，且不需要改绑定。
- **中心式 → 隔离式**：**不提供**。代码已经上传过，产品做不到「真收回去」。
  提供这个操作只会给人虚假的安全感。
- **`mirror` → 任何形态**：**不提供**。镜像式要指一个上游，而改回中心式等于
  凭空造一个上游出来；改成隔离式同样撞上「收回已上传的代码」。
- **同一个形态 → 自身**：**拒绝**（不是 no-op 成功）。转换里要做的事
  （推代码、建裸仓库、`fetch` 校验）一次都不会执行，报成功会让调用方以为做过了。

**实现口径（`v0.7.0` 子任务 2）**：

- 唯一允许的转换是 `isolated → central`，判据集中在
  `hub_storage::project::ProjectShape::can_transition_to`，**业务层不许另写一套**。
- **转换不是改一个字段**：`POST /api/projects/{id}/shape` 是独立入口，不混进
  `PATCH /api/projects/{id}`。要改形态必须先在该绑定设备上把代码推成提交、
  Hub 建裸仓库并 `fetch` 成功——**落库与仓库就绪是同一个事务的两半**
  （子任务 3 落地；在此之前只改字段，因为没有仓库这一步也就没有半成品状态）。
- 被拒时返回 **400**（不是 403）：理由不是「你没权限」，而是「这个变更在产品上不存在」。
  错误体额外带 `{from, to}`——拒绝的理由取决于两端是什么，只说「不允许」
  用户不知道该改成什么。
- **`isolated` 期间 Hub 不验证内容**：起点是该设备上的 commit hash，Hub **不校验**
  这个 hash 对应的内容是否真的存在于该设备。这是隔离式的定义要求，不是遗漏——
  实现时不要「顺手加个校验」（见 §2.1.1 与 `AGENTS.md` 约束 20）。

### 2.3 生命周期：可归档，不可删除

**第一版不提供项目删除**（`PRODUCT.md` §3.2）。原因是删除会连带毁掉三样只挂在项目上的东西：
已合入的任务历史、失败归因、成本记录。

归档的语义：

- 不出现在项目列表与看板首页；任务停止派发新执行。
- **历史执行记录 / 轨迹 / 管家总结全部保留**，单独读取项目仍可拿到（`GET` 不 404）。
- **归档不打断正在跑的执行**：跑完才归档。
- **可随时取消归档**，回到默认列表。

接口面：`POST /api/projects/{id}/archive` 与 `/unarchive`，**没有 `DELETE`**。

## 3. 为什么用真 git，而不是「参考 git 思路自研」

**决策：用真 git。**

最强的理由不是「git 流行」，而是它让一件事**从功能退化成配置**：

```text
模式 A（Hub 是源头）   设备 git fetch → remote = Hub
模式 B（Hub 是镜像）   Hub git fetch  → remote = GitHub
                      设备 git fetch → remote = Hub
```

两者是**同一条命令**，差别只是 remote URL。所以「项目绑定外部 git 仓库做拉取同步」
不是一个要写的功能，是**配一个 URL**（这就是 §2 的「镜像式」）。

自研则必须同时造两个东西：自己的存储格式，加一个 GitHub 客户端。
而后者本质上仍要理解 packfile——等于把 git 的接收端又写了一遍。

其余三条：

- **自研 = 写一个更差的 git。** 概念模型已经是 commit / tree / branch 了，
  那么 packfile 协商、delta 压缩、浅克隆、`gc`、并发 push 的原子性、对象校验
  这些事先想不到的问题会在后面逐个出现——它们都已被解决，且很难做对。
- **逃生口。** 真 git 意味着用户能直接 `git clone` Hub 上的项目到笔记本上
  检查、救急、手动修。数据不被锁在自己的实现里。
- **互操作性免费。** 接 CI、看历史，任何现成工具直接可用。

### 3.1 Hub 侧怎么实现

Hub 持有**裸仓库**（bare repo）。三条路：

| 方案 | 评价 |
|---|---|
| 调 `git` CLI | **推荐先走这条**。最简单可靠，代价是 Hub 环境依赖 git 二进制 |
| `gitoxide`（`gix`） | 纯 Rust 无 C 依赖；将来要去二进制依赖时的选择 |
| `git2`（libgit2） | 成熟，但有 C 依赖 |

**先把实现藏在接口后面，一期用 CLI**，等确定真的需要再换库。

**必须加的运维护栏**：限制单仓大小、限制单次 push 包体积、定期 `git gc`。

## 4. 「同一起点」是两层身份，git 只管一层

**这是本设计最容易被做错的一格。**

git 快照保证「代码一样」，但**保证不了「跑出来一样」**：
两台设备同一个 commit，一台 OpenSSL 3.0、一台 1.1，结果照样不同。

```text
代码身份  = git commit                                  ← git 负责
环境身份  = lockfile 哈希 + 工具链版本 + 系统库声明      ← 元数据，存在 Hub 数据库里
同一起点  = 两者都对得上
```

**所以「环境」不是搬过去，是「声明 + 本地重建」。**

理由已由 `DECISIONS.md` **D9** 钉死并仍然有效：

> **依赖目录按架构分化**。`node_modules` 里是平台相关的二进制，
> x86-64 与 aarch64 装出来的不是同一份东西——**根本不存在「同一份依赖」可搬**。

于是**快照的边界**被定义了：

> **快照 = tracked 源码 + 环境声明。依赖不在快照内，在设备本地按 lockfile 重建。**

`.gitignore` 是这条边界的天然载体，也是三者一致的那一处：
git 内建它、排除清单读取它、D9 的论证指向它。

> **隔离式项目的环境身份仍然有效**：环境声明是本地的元数据（lockfile 哈希 + 工具链版本），
> **不含源码**，因此把环境声明上报 Hub 不违反「代码不出设备」。
> **约定**：只报哈希与版本号，不报 lockfile 内容——某些项目的 lockfile 会泄漏私有依赖名。

## 5. 固定目录 + worktree

### 5.1 固定目录（Binding）

> **每个设备的每个项目，绑定一个固定目录。这条目录一旦定了就不变。**

理由：

- 设备上的**依赖缓存 / 构建缓存 / IDE 配置**都挂在路径上。路径一漂移，缓存全部失效。
- 用户需要一个「我知道它在这台机器上的哪儿」的确定答案。
- 配额与清理策略需要按目录统计，路径漂移会让统计失效。

改绑目录是**允许的**，但代价明确：该设备上这个项目的缓存作废，下次任务冷启动。

### 5.2 用 worktree 分任务，不用多个 clone

在固定目录里，**一个任务一个 worktree**：

```text
<binding.path>/                      ← 主工作树（固定目录），常驻，只做 fetch / 保持干净
<binding.path>/.afleet/worktrees/    ← 任务工作树，每个任务一个，用完即删
  ├── task-1042/                     ← git worktree，共享 object store
  └── task-1057/
```

| | 多个 clone | **worktree** |
|---|---|---|
| object store | 每个 clone 一份完整 objects | **共享一份** |
| 第 N 个任务额外磁盘 | 一份完整历史 | 只有工作树里的文件 |
| `fetch` | 每个 clone 各 fetch 一次 | 主工作树 fetch 一次，全部 worktree 可见 |
| 分支冲突 | 天然隔离 | 天然隔离（同一分支不能被两个 worktree 同时检出） |

**必须明说的代价**：worktree **不共享** `node_modules` / `target` 这类**工作树级**目录。
它们按 worktree 各一份。所以 §5.3 的清理是必需的，不是可选的。

### 5.3 磁盘：四层处置

> **本节的定位是「怎么清」，不是「派活时谁能跑」。**
> 磁盘**也**是任务分配必须考虑的项——那属于**调度**，见 `scheduling.md` §3.2 / §3.3：
> 派活前按 worktree 基础开销做**硬过滤**、执行中监控、同一绑定**默认串行**。
> 两件事必须分开：**配额决定「允许多大」，调度决定「现在跑不跑得动」，清理决定「跑完怎么收回」。**

1. **任务级**：任务跑完 → `git clean -xdf` 后 `git worktree remove`。**工作树不累积**。
2. **缓存级**：依赖缓存按 **lockfile 哈希**复用（存在 binding 目录之外，如 `<path>/.afleet/cache/<lockhash>/`）；
   **任务产物必清**——缓存不是产物，产物不进缓存。
3. **配额级**：Binding 上设磁盘配额；设备上报 `disk.workspace_free_mb`，
   **超 90% 不再往这台派任务**，并在看板与设备页说明原因。
   （这是**配额**这一侧；同样的余量数据在调度里还有第二个用途——硬过滤候选设备，见
   `scheduling.md` §3.2。**两处读同一个数，不要各算各的**。）
4. **策略级**：绑定时可选三档清理策略：

| 档 | 缓存保留 | 产物保留 | 适用 |
|---|---|---|---|
| **保守** | 保留到配额上限 | 保留最近 N 个任务的 | 单机、磁盘大、想快速重跑 |
| **平衡**（默认） | 按 lockfile 哈希，LRU 淘汰 | 任务结束即清 | 大多数情况 |
| **激进** | 任务结束即清 | 任务结束即清 | 磁盘小（树莓派 / 手机） |

**为什么缓存按 lockfile 哈希而不是按分支**：同一个 lockfile 意味着同一份依赖，
分支名不说明任何事。按分支分缓存会在每次换分支时冷启动，等于没有缓存。

## 6. 流程

### 6.1 准备（每个 binding 一次）

- Hub 建项目的裸仓库；设备声明 binding：这个项目在我这儿是 `<path>`。
- 设备首次 `clone` 到固定目录；此后一律 `fetch` 增量。

### 6.2 分发

Hub 下发：`{ project, snapshot: <commit>, env: <env_signature>, task }`。

设备侧：

1. 主工作树 `fetch`（一次 fetch 服务全部 worktree）；
2. 从 `snapshot` 建一个任务 worktree（`git worktree add`）；
3. **校验**：
   - `HEAD == snapshot` → 就绪；
   - 不等 → **说清差什么**（缺哪个 commit / 环境哪一段不符），**不硬跑**。

> **为什么校验必须是显式的这一步**：即使做了 `checkout`，本地仍可能不在期望的 commit 上
> （外部仓库前进了、上一个任务留下了改动、有人手动动过这个目录）。而在错误基线上跑出来的
> 任务结果**看起来正常但实际不可信**——它比报错更危险，因为错误是静默的。

### 6.3 执行

- 任务在**自己的 worktree** 里跑，不碰主工作树。
- 依赖按 lockfile **本地重建**（`npm ci` / `cargo fetch`），命中缓存则跳过。
  重建步骤可断点续跑。

### 6.4 回收

- 任务 worktree 本地 `commit` → `push` 一条**任务分支**回 Hub。
- Hub 侧看到的就是一次干净的 diff：这个任务改了什么。
- **合不合并由 Hub / 用户决定**（即「待验收」→「已完成」），不让多台设备抢同一个分支。
- 合入后 worktree 删除，分支保留到策略决定的上限。

## 7. 五个关键决策

| # | 决策 | 理由 |
|---|---|---|
| ① | **只同步 tracked 文件，依赖不进快照** | D9 第一重硬阻；gitignore 是天然边界 |
| ② | **Hub 自己就是远端，不要求设备连得上 GitHub** | 内网 / 公司墙的设备也能干活。`scheduling.md` §3.1「能拿到代码」已预见并保留了「Hub mirror」这一支 |
| ③ | **按 packfile 协商拉，不按文件拉** | 设备说「我有这些 objects」，Hub 只发缺的。冷启动与增量走同一条路径。**按文件逐个拉会退化成「每个请求一个往返」——那才是真正的性能杀手**（§8） |
| ④ | **判据只认 commit，不认「目录看起来像」** | 不能靠文件数量 / 修改时间猜。tree hash 是证明，且设备无法伪造 |
| ⑤ | **每个任务一条独立分支 + 一个独立 worktree** | 避免多设备并发 push 冲突，也避免同设备多任务互相踩工作树；冲突留到 Hub 侧显式解决 |

### 7.1 与 `README.md` 旧描述的关系

`architecture/README.md` 曾写：

> git 项目走主路径：Hub 只发 commit 引用，**节点自己去 origin 拉**，大文件不进 WebSocket。

## 8. 性能为什么可接受

担心「网络开销很大」时会算带宽，但真正的瓶颈是**往返轮次**：

```text
1 个典型任务：50–200 次工具调用 × 几 KB  ≈ 1 MiB 量级   → 带宽不是问题
按文件逐个拉：同样的数据，每个文件一次 RTT            → 延迟才是问题
```

所以 ⑦③ 那条决策（按 packfile 协商）不是优化，是**必要性**条件：
一次性协商 + 整体传输，把 N 次往返压成 1 次。

配套的既有事实（`protocol.md`）：

- 单帧上限 **1 MiB**，超出即断连（`frame_too_large`）；
- 读侧有令牌桶（4 MiB 突发 / 1 MiB 每秒，**按连接计**）；
- **「每连接不是每通道」**——批量传输会拖慢同一条 WS 上的终端输出，这是已知代价。

因此 bulk 传输走 **git 自己的 HTTP/Smart 传输**，不塞进控制用的 WebSocket。
这与既有裁定「**WS 是控制通道，不是数据通道**」（`workspace-and-sync.md` §2）一致。

## 9. 明确不做 / Non-goals

| 不做 | 理由 |
|---|---|
| 实时双向同步 | 那是 Syncthing 类问题，不是任务分发问题。约束 10 明确不用它当主通道 |
| 依赖目录搬运 | 架构上不可能「一样」（D9） |
| 自建差异格式 | git 对象模型已解决且可审计 |
| 设备间 P2P 直传 | 约束 10：Hub 必须保持唯一真相源 |
| 中心式 → 隔离式 降级 | 「真收回去」做不到，提供它只会给虚假安全感 |
| LayerFS 作为快照载体 | 它的 `init` 明写 **takes everything：`node_modules`、build caches 在内，gitignore 不生效**——搬运的正是 D9 禁止搬运的东西 |

### 关于 LayerFS 的位置

LayerFS 在这套设计**之后**才有位置，且只有三样东西是这里真缺的：

- `fork` — **copies no files**，任意深度成本相同；
- 冲突语义明确 —— 改不同文件自动合并，改同一文件 `Conflict` 且 **nothing is committed or retried**；
- `blame` —— 每一行追溯到**是哪次工具调用**改的。

这三样回答的是「**跑完之后怎么回来**」，不是「怎么出发」。
**顺序对了就不会再问错**：先有同一起点（git ref + 环境声明），LayerFS 才有地方放它的 Branch。
