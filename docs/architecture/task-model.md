# 任务模型 / Task Model

> 任务（Task）是看板上的一个卡片，也是本产品的**真身**：它活在 Hub 上，不活在设备上。
> 产品定位见 `docs/PRODUCT.md` §5；项目实体见 `project-and-snapshot.md`；
> 管家见 `butler.md`；路由见 `scheduling.md`；断点续跑见 `task-continuity.md`。

---

## 1. Task : Execution = 1 : N

> **一个任务可以被执行多次。每次执行都留现场，不覆盖上一次。**

```text
Task #1042 「把构建时间降到 60s 内」
  ├── Execution 1  @device-a / opencode    failed  —— 基线错误：base_commit 缺 commit
  ├── Execution 2  @device-b / opencode    failed  —— 测试未全绿：3 failed
  └── Execution 3  @device-c / claude-code done    —— 已合入 → Task done
```

**为什么必须 1:N 而不是把失败的结果覆盖掉**：

- 失败的现场是**最有价值的证据**。「第一次为什么不行」比「最后成了」更能说明问题。
- 重试要**换条件**（§2.1 ①），换条件的前提是能对比。覆盖掉就无从对比。
- 审计：谁在什么条件下跑过、花多久，都要能查。

**Execution 是唯一有「设备 + agent + 工作树」三件套的东西。** Task 本身没有设备——
一旦 Task 有了设备，重试换设备就变成了改数据而不是新生一次执行。

## 2. 六态 / Six states

| 状态 | 含义 | 进入条件 | 离开条件 | 谁推进 |
|---|---|---|---|---|
| `pending` | 待办 | 被接住（人建 / 管家拆 / 外部导入） | 被派活 | 管家 / 人 |
| `queued` | 排队中 | 调度器选中了 `(device, agent)` | 设备接活 | 调度器 → 设备 |
| `running` | 执行中 | 设备上有一次 Execution 真在跑 | 跑完 / 失败 / 中断 | 设备 |
| `review` | **待验收** | Execution 成功产出了任务分支 | 人 / 规则判定 | **人或显式规则** |
| `done` | 已完成 | 验收通过 + 已合入主干 | 终态 | 人 / 规则 |
| `failed` | 失败 | Execution 失败，**且不再自动重试** | 人工推进 | 设备 → 管家标注 |

### 2.0.1 `running` 的子状态：`waiting_for_user`

**不单开第七个任务状态**，只作为 `running` 的子状态：

```text
running
  ├── active           正常在跑
  └── waiting_for_user 暂停，等人做决定（收件箱里有它的待决策项）
```

**为什么是子状态而不是第七态**：它**仍然在跑**，只是暂时停下等人；
单开一态会让「设备上到底有没有进程活着」变模糊——而这个问题在排查时必须能立刻回答。

**进入 `waiting_for_user` 的三种情形**（都来自 `PRODUCT.md` §5.4 的待决策区）：

1. agent 发起**业务决策**请求（用 Redis 还是 SQLite）
2. 执行中 `disk_exhausted`，等人确认**清理方案**
3. 管家发现任务定义不清（同一 Execution 被打断 ≥2 次），停下来问人

**超时的处置**：按决策请求的 TTL，超时后走**预设降级**（选默认方案继续 / 中止），
中止则转 `interrupted`——**不是 `failed`**，它没做错，是在等人。

### 2.1 三条硬性规则

**① 重试必须有上限，且必须换条件。**

- 上限：默认 2 次重试（共 3 次执行），可按任务配置。
- **必须换条件**：换设备 / 换 agent / 换 `base_commit`。**同一个 `(device, agent, base)` 原地重试
  的第二次起没有意义**——如果第一次失败，同样条件下不会奇迹般成功。
- 用户明确要求：**失败重试时换一台设备重新调度**。这条是产品约束，不是优化。

**② 失败必须留「为什么」。**

没有原因串的失败等于没发生。每条 Execution 失败必须落：

- `failure_kind`（§3 的八种）
- `reason`（人能读的一句话）
- `evidence`（退出码 / stderr 摘要 / 设备日志引用 / 可复现命令），可空但**空要显式标 `none`**

**③ 失败停在「失败」列，不自动回待办。**

自动回待办会让失败被稀释成背景噪声（「待办里那一堆大概都是之前失败的」），
而失败恰恰是最需要人看一眼的东西。人工推进的三个选项：
放宽约束重派 / 改任务本身 / 关掉（并写明为什么不做了）。

### 2.2 状态图的边（不是任意跳转）

```text
pending ──→ queued ──→ running ──→ review ──→ done
   ↑            │          │
   │            │          ↓
   │            └──────→ failed ──→ （人工：回 pending / 关闭）
   │                        ↑
   └──（人主动撤回）─────────┘

running ──（设备掉线，超时）──→ failed(kind=interrupted)
```

- **`running` 不能直接到 `done`**。跳过 `review` 就是跳过了价值锚点。
- **`review` 退回时进 `pending`**（附打回原因），不是进 `failed`——**打回不是失败**，
  任务是对的，产出没达标。
- **`queued` 超时可退回 `pending`**（设备一直不接活），不是 `failed`。

## 3. 失败的八种形态 / Eight failure shapes

不同失败**处置完全不同**。把它们都叫「失败」并给同一种重试，是这一格最容易犯的错。

| # | `failure_kind` | 长什么样 | 该谁处置 | 重试有用吗 | 换设备有用吗 |
|---|---|---|---|---|---|
| 1 | `baseline_mismatch` | 设备上的起点不是期望的 commit；环境声明不符 | 设备 / 绑定 | 有用（重新 fetch） | 有用（换一台也许基线干净） |
| 2 | `env_broken` | 依赖装不上、工具链缺失、系统库不符 | **用户** | 没用 | 有用（换架构 / 换空闲机器） |
| 2.5 | **`disk_exhausted`** | **执行中磁盘写满 / 超预算阈值被提前中止** | **调度 + 用户** | 没用 | **有用**（但要先过 §4 的硬门槛） |
| 3 | `agent_error` | agent 崩了、超时、协议错、上下文爆了 | 产品 / 用户 | 有用（换 agent） | 不一定 |
| 4 | `task_failed` | agent 正常运行，但**事情没做成**（测试红了、构建失败） | **人** | 原地没用 | **有用**（换设备 / 换 agent / 换起点） |
| 5 | `interrupted` | 设备掉线、Hub 重启、任务被取消 | 系统 | 有用（续跑） | 有用，但先试续跑 |
| 6 | `rejected` | 派不出去：无合格设备、被隔离策略挡住、配额不足 | 管家 / 用户 | 立刻重试没用 | 需要改条件 |
| 7 | **`superseded`** | **执行中需求变了，原 `done_when` 不再成立**，任务被新任务取代 | **管家 / 人** | **永远没用** | **永远没用** |

> **第 7 种是「不是失败的失败」，必须单列。**
> 它**不占重试次数**、**不触发重试**、**不进失败归因统计**（否则设备页的「失败集中在哪一类」
> 会被用户自己改需求污染，那条信号就废了）。
> 它的唯一作用是**留痕**：说明这个任务为什么没做完，以及它被谁取代了。
> 处置流程见 `butler.md` §2.2.1。

> **第 2.5 种为什么不并进 `env_broken`**：两者的**责任方不同**。
> `env_broken` 是「这台机器的软件环境坏了」，要人去修；`disk_exhausted` 是
> 「**调度器当初算错了**或者**峰值估低了**」，要改的是调度与配额。
> 并在一起会让「磁盘问题」永远被当成「机器问题」去查，而真正该改的那一层没人看。
> 判定与监控见 `scheduling.md` §3.2。

### 3.1 每种的处置细节

- **`baseline_mismatch`** —— **不硬跑**。设备侧必须说清「缺哪个 commit / 环境哪一段不符」。
  在错误基线上跑出来的结果**看起来正常但实际不可信**，比报错更危险。
- **`env_broken`** —— 重试是浪费。要**标脏这台设备**：同一绑定上的后续任务可以继续派，
  但**同类环境失败连续 N 次就暂停该设备接活**并通知。
- **`disk_exhausted`** —— 分两种情形，**处置不同**：
  - **派活前就被磁盘硬门槛排除** → 根本不产生 Execution，是 `rejected(disk_insufficient)`，
    见 `scheduling.md` §3.2。
  - **跑的过程中写满 / 超预算被中止** → **不直接判失败**，先转
    `running.waiting_for_user`，把**清理方案**放进收件箱（`PRODUCT.md` §5.4）：
    说清准备清理**什么**、各占多大、清理后能释放多少、是否保留诊断产物。
    用户选「清理并续跑」→ 从检查点续；选「不清理」→ 才判 `failed`。
    **清理是不可逆操作，未经选中不得执行。** 超时未选 → 保持中止状态，不在收件箱里消失。

  **必须回头改的是调度**，不是只修磁盘：为什么预算算少了？是 worktree 基础开销低估了，
  还是这个任务确实吃磁盘而 `required_capabilities` 没写够？**不改这一层，下次还会踩。**
- **`agent_error`** —— 换 agent 优先于换设备。同一个 agent 在同一台机器上重启，
  大概率还是同样的崩溃。
- **`task_failed`** —— **唯一一个「必须换条件」的形态**，也是用户明确要求换设备的那个。
  产出必须保留（分支 / diff），因为「它试过但没成」是信息。
- **`interrupted`** —— 先试**续跑**（有检查点就从检查点起），续不了才换设备重跑。
  直接换设备重跑会浪费已经做对的那些步骤。
- **`rejected`** —— 从来不是设备报上来的，是**调度器当场拒的**。它不产生 Execution，
  只产生一条带原因的「未派活」记录。**不占重试次数**。
- **`superseded`** —— 不重试、不换设备、**不进失败归因**。只留痕 + 指向新任务。
  触发路径只有一条：**执行中需求变了，原 `done_when` 不再成立**（`butler.md` §2.2.1 情形 ②）。
  **与 `task_failed` 的区别**：`task_failed` 是「照着要求做了但没做成」，
  `superseded` 是「要求本身变了」——**前者要分析，后者不需要分析，只需要记录**。

### 3.2 重试策略矩阵

| `failure_kind` | 自动重试 | 换设备 | 换 agent | 换起点 | 通知人 |
|---|---|---|---|---|---|
| `baseline_mismatch` | 是（1 次） | 是 | 否 | 否 | 连续 2 次才通知 |
| `env_broken` | 否 | 是 | 否 | 否 | 是 |
| **`disk_exhausted`** | **否** | **是**（须先过磁盘硬门槛） | 否 | 否 | **是**（先问清理方案） |
| `agent_error` | 是（1 次，换 agent） | 否 | **是** | 否 | 达到上限才通知 |
| `task_failed` | 否 | **是**（需人确认或规则放行） | 是 | 可选 | **是** |
| `interrupted` | 是（先续跑） | 断点续不上才换 | 否 | 否 | 是 |
| `rejected` | 否 | — | — | — | 是 |
| **`superseded`** | **否** | **否** | **否** | **否** | **是**（确认新任务已建） |

> **`task_failed` 为什么不自动换设备**：它是「事情没做成」，不是「环境不行」。
> 自动换设备会变成「一直试到某台机器碰巧过」——那不是工程，是赌博。
> 换设备重试是**人（或管家提议、人确认）**的决定。

### 3.3 执行中改需求：不是「重派 vs 通知」二选一

用户对 `running` 的任务说新话时，**判据是「原来的 `done_when` 还成不成立」**：

| 新话的性质 | 处置 | 为什么 |
|---|---|---|
| 目标不变、做法要换 | **通知当前 agent**（`session/cancel` → 新 prompt，保留上下文） | 已有现场（读过什么、试过什么）比重新跑值钱；**丢掉现场比重新跑更贵** |
| 目标变了 | **`superseded` + 新建任务** | 让 agent 追移动的靶子会交出「看板显示完成但你要的不是它」——比报错危险 |
| 只是加约束 | **通知 agent** + **写 `project_memory`** | 否则下一个任务还会踩同一个坑 |

**打断的三条硬规则**（详见 `butler.md` §2.2.1）：

1. **打断不是杀进程**：走 ACP `session/cancel`，不杀 Execution，否则丢现场。
2. **打断必须留痕**：Execution 记 `interrupted_by_intent` + 原话。
3. **打断有上限**：同一 Execution 被打断 ≥2 次 → 判定任务定义不清 → 停下来问人。

## 4. 失败之后人怎么介入 / The human path after failure

> **这一节是这个产品最常被使用的交互，比任何架构决策都更能决定它好不好用。**
>
> 上一节说清了「失败有八种」，但看完之后**能做什么**一直散落在各处。
> 这里把动作收敛成**一个统一形态**：任务详情的失败面板。

### 统一入口：失败面板

点开一张 `failed` 卡，看到的不是一堆散落按钮，而是**一个诊断 + 一组动作**：

```text
┌ task #1042 「把构建时间降到 60s 内」 ─────────────────────────────┐
│ 失败原因  task_failed  测试未全绿（3 failed）                      │
│ 证据      3 条断言失败 → 展开看 stderr / 复现命令                  │
│ 第几次    执行 2 / 3（已在 device-a 失败，device-b 失败）           │
│ 产出      afleet/1042/e2  ·  改了 7 个文件  ·  展开 diff          │
├──────────────────────────────────────────────────────────────────┤
│ [ 换设备重派 ] [ 改任务再跑 ] [ 放宽约束 ] [ 看执行复盘 ] [ 关掉 ]  │
└──────────────────────────────────────────────────────────────────┘
```

| 动作 | 做什么 | 什么时候该选 | 落成什么 |
|---|---|---|---|
| **换设备重派** | 同一个任务、同一个 `done_when`，**换一台设备**再跑一次 | 怀疑是机器问题（换架构 / 环境不同） | 新 Execution；**不改 task 定义** |
| **改任务再跑** | 打开任务编辑：改 `done_when` / 改描述 / 改约束，然后重派 | 要求本身需要调（原来的判定太严 / 太松） | **task 版本 +1**，旧值留痕（不是 `superseded`——目标没变，是细化） |
| **放宽约束** | 只改 `allowed_devices` / `allowed_agents` / `required_capabilities` | 合格设备池太小（`rejected(no_capable_device)`） | task 约束变更留痕 |
| **看执行复盘** | 进入执行复盘模式（`PRODUCT.md` §3.11） | 想知道「它是怎么跑歪的」 | 只读 |
| **关掉** | 任务终止，**必须写明为什么不做** | 这件事不做了 | `failed` 终态，`closed_reason` 必填 |

### 四条硬规则

1. **每个动作都必须落到某条可回溯的记录上**。不许有「点了没反应」或「点了不知道改了什么」
   的动作——尤其「改任务再跑」，必须能看出**改前改后**。
2. **重派不消耗「自动重试」额度**。自动重试是有上限的（§2.1①），但**人点的重派是人的决定**，
   不计入自动额度——否则人手点两次就被告知「超过上限」。
3. **「关掉」必须写明原因**。没有原因的关闭会把失败变成「消失的失败」，
   而失败归因依赖它。
4. **失败面板是唯一的处置入口**。不许在别处（设备页、收件箱、命令行）提供第二套动作，
   否则两处状态会打架。

### 失败面板不该做的事

- **不推荐「一直重试到成功」**。没有「重试 N 次直到过」这个按钮——
  那会把工程变成赌博（§3.2 已说明）。
- **不自动选动作**。管家可以建议（「这台机器上次就是 `env_broken`，建议换设备」），
  但**执行动作必须是你点的**。

## 5. 待验收里能做什么 / The review column

```text
┌ review #1042 ──────────────────────────────────────────────────┐
│ 判定   criteria 2 条全绿（自动判）  ✓ cargo test                │
│                                     ✓ build < 60s (实测 47s)   │
│ 总结   管家写的这次改了什么（3 段）                              │
│ 产出   afleet/1042/e2  ·  diff 7 文件 +214 −38                 │
├────────────────────────────────────────────────────────────────┤
│ [ 合入主干 ] [ 打回重跑 ] [ 只保留分支 ] [ 查看执行复盘 ]         │
└────────────────────────────────────────────────────────────────┘
```

| 动作 | 结果 | 谁能做 |
|---|---|---|
| **合入主干** | `review → done`，任务分支合入 | 人；档 1/2 下管家也可（`PRODUCT.md` §4.5） |
| **打回重跑** | `review → pending`，**附打回原因**，不判失败 | 人 / 管家 |
| **只保留分支** | 不合主干，但保留分支供以后取；任务标 `done(未合并)` | 人 |
| **查看执行复盘** | 只读回放（`PRODUCT.md` §3.11） | 任何人 |

**两条硬规则**：

1. **判定码不全绿时「合入主干」必须二次确认**，并写明「判定未通过，仍要合并」。
   —— 允许人越过判定，但**不许静默越过**。
2. **只有 `description` 没有 `criteria` 的任务**，卡片上必须标
   「**需人工验收**」（`butler.md` §2.2.0），不能让用户以为有自动判定在跑。

## 6. 撤销与回退 / Undo & revert

| 场景 | 能做什么 | 做不到什么 |
|---|---|---|
| **还没合并**（`running` / `review` / `failed`） | **丢弃这次执行**：删分支 + 删 worktree，Execution 标 `discarded` | 恢复被丢弃的 worktree（已删） |
| **已合并**（`done`） | **发起一次回退任务**（生成 revert commit 的新 Task，走完整流程） | 「一键撤销合并」——那需要重写主干历史 |
| **误关掉的任务** | 从 `failed` 重新打开到 `pending` | — |

> **为什么「已合并」不给一键撤销**：主干是共享真相，改写历史会让所有基于主干的执行
> 变得不可信。**回退也应该是一个任务**——它同样值得被记录、被验收。

## 7. 任务级约束 / Task constraints

派活时定，执行时必须满足：

| 约束 | 说明 | 谁给 |
|---|---|---|
| `allowed_devices` | 只许在这些设备上跑 | 人 / 管家（隔离式项目的实现方式） |
| `allowed_agents` | 只许用这些 agent | 人 / 管家 |
| `required_capabilities` | 必须具备的能力（某架构 / 某内存阈值 / 某 connector） | 管家 / 规则 |

### 7.1 过滤顺序（固定，不可调换）

```text
① 任务级 allowed_*      派活人说了算
② 项目级隔离策略        形态决定谁有资格（隔离式：只有绑定的那台）
③ 调度器能力 / 负载排序  谁更合适（scheduling.md）
```

**为什么顺序不能换**：如果先按负载挑出「最闲的那台」再去检查 allowed_*，
那么 allowed_* 的拒绝就变成了「挑错了再重挑」——它在语义上从「约束」降级成「偏好」。
约束先于偏好，这是硬的。

### 7.2 任何一层过滤为空 → 停待办并说明

```text
① 空  → rejected(no_allowed_device)      「任务限定在 A/B/C 上跑，现在都不可用」
② 空  → rejected(isolation_blocked)      「项目是隔离式，只有 device-a 有资格，它离线了」
③ 空  → rejected(no_capable_device)      「没有设备同时具备 git + arm64 + 8G 内存」
配额   → rejected(quota_exceeded)        「device-a 磁盘已用 94%，超过 90% 阈值」
```

**不降级凑数。** 「没合格设备就随便找一台」会产出看似正常、实际不可信的结果。

### 7.3 起点 / `base_commit`

每个任务记一个 `base_commit`：

- 派活时由管家 / 人给出；不给则用项目主干当前 HEAD。
- 设备侧必须校验 `HEAD == base_commit`（`project-and-snapshot.md` §6.2）。
- **产出 diff = `base_commit..HEAD`**——这就是 v0.6.0 会话页「起点 + 产出概览」在项目主轴下的
  正式位置：逻辑是对的，只是原先挂在会话上，现在该挂在 Execution 上。
- **重试换起点时必须显式记录**：新 `base_commit` 与旧的都要留在 Execution 上，
  否则两次执行的产出无法对比。

## 8. 数据形状（草案）

不写进 schema，只定语义；落库形态由里程碑定。

```text
task
  id, project_id
  title, intent_ref
  done_when                   -- { criteria: [...], description } 见 butler.md §2.2.0
  state                       -- pending/queued/running/review/done/failed
  base_commit
  allowed_devices, allowed_agents, required_capabilities   -- JSON
  retry_limit
  version                     -- 每次「改任务再跑」+1，旧值留痕
  superseded_by, supersedes   -- 取代关系（NULL = 无）
  created_by                  -- human / butler / import:<source>
  created_at, updated_at

execution
  id, task_id
  device_id, agent_id         -- ↖ 只有 execution 有三件套
  worktree_path, branch
  state                       -- running/failed/succeeded/discarded
  failure_kind                -- §3 八种，成功为 NULL
  reason, evidence
  base_commit                 -- 本次执行实际用的起点（可能与 task 的不同）
  parent_execution_id         -- 接力来源（可空），见 PRODUCT.md §3.12
  cancelled_by                -- user / butler，人点的重派不计自动额度（§4）
  interrupted_by_intent       -- 执行中被改需求打断时的原话（NULL = 没被打断）
  interrupt_count             -- 被打断次数；≥2 触发「任务定义不清」告警
  queued_at, started_at, ended_at   -- 排队与执行分开记（PRODUCT.md §3.8）
  tokens_in, tokens_out       -- 拿不到为 NULL，**不估算**

-- superseded 需要一条指向新任务的引用（放在 task 上）
task.superseded_by            -- 被哪个新任务取代（NULL = 未取代）
task.supersedes               -- 它取代了哪个旧任务（NULL = 不是取代来的）
```

**关键点**：`base_commit` 在 task 和 execution 上各有一份。task 上的是**期望**，
execution 上的是**实际**。两者不同就是 `baseline_mismatch` 的证据。

## 9. 看板与时间线：同一批事实的两种投影

| 看板 | 时间线 |
|---|---|
| 「现在卡在哪」 | 「什么时候发生了什么」 |
| 按 state 分列 | 按时间排序 |
| 一张卡 = 一个 Task | 一条 = 一个事件（含 Execution 的起止、状态迁移） |
| **默认视图** | 第二视图 |

**两者不是两套数据。** 切视图只改排布，不改事实。任一视图里的操作立即反映到另一视图。
