# 管家 / Butler

> **管家是绑定到一个项目、跑在 Hub 上、拥有该项目长期记忆的 agent。**
> 它是这个项目的唯一入口。产品定位见 `docs/PRODUCT.md` §4；任务模型见 `task-model.md`；
> 项目实体见 `project-and-snapshot.md`；调度见 `scheduling.md`。

---

## 0. 一句话边界

> **调度器管「在哪跑」，管家管「做什么」。**

管家派任务时**调用**调度器，**不自己挑机器**。这是本文最重要的一条：
一旦管家开始按负载挑设备，它就成了一个带记忆的调度器，而记忆会让它的判断**不可复现**——
同一个任务今天派给 A、明天派给 B，没人说得出为什么。

---

## 1. 它不是什么 / What it is not

| 不是 | 为什么 |
|---|---|
| 调度器 | 见 §0。选设备是 `scheduling.md` 的职责 |
| 写代码的人 | 它**没有工作区**。改代码是任务的活，跑在设备上 |
| 合并者 | 「待验收」之后它可以推一把，但**合主干要人或显式规则** |
| 万能问答 | 记忆里没有的说没有，去查、去问，**不编** |
| 会话 | 它不是 `/sessions/:id`。会话是设备上的 ACP 对话；管家是 Hub 上的项目级参与者 |

> 管家**不是**一个新的会话容器。它跑在 Hub 上，不占设备，不经 ACP。
> 这一条必须钉住：否则「管家 = 一个特殊的会话」会把整个会话模型拖进项目层。

## 2. 四项能力 / Four jobs

### 2.1 接意图 / Listen

用户对项目说的每句话，先进管家。

- 落成一条**意图记录**（intent）：原文 + 时间 + 说话人 + 管家当时的理解。
- **不急着拆任务**。一句话可能只够一个任务，也可能根本不该派活
  （「这个项目现在什么状态？」是提问，不是任务）。
- 拿不准就**反问一次**。问得准比问得多重要：一次澄清胜过三次返工。
- **不许自作主张扩大范围**。「顺手把测试也写了」不是默认行为，是另一个任务。

#### 2.1.1 「接意图」靠 skill，不靠写死的意图分类（用户已裁定 2026-11-01）

> **不预设「意图类型」枚举。** 用户可能说「把构建搞快点」、也可能说「昨天那个 bug 还在吗」、
> 也可能只是聊天——**用一张固定的意图分类表去接，只能接住表里有的那几种**，
> 剩下的全被塞进「其它」，反而更糟。

正确的做法是**给管家一组技能（skill），由大模型自行决定怎么推进**：

| 技能 | 作用 | 产出 |
|---|---|---|
| `project.status` | 读项目当前状态（看板摘要、最近执行、待决事项） | 一段可回答的摘要，不建任务 |
| `project.history` | 查时间线 / 过去某次执行为什么失败 | 引用执行 id 与失败原因 |
| `task.create` | 把一个意图拆成任务（含 `done_when` / 约束） | Task 记录，进 `pending` |
| `task.clarify` | 意图不清楚时反问用户一次 | 收件箱里一条待决策 |
| `memory.read` / `memory.write` | 读写两处记忆 | 结构化记忆 / `.afleet/MEMORY.md` |

**约束（必须写死）**：

- **技能只声明「能做什么」，不规定「必须先做什么」**。管家可以连着调 `project.status` 好几次
  再决定建不建任务，也可以一句话都不建就直接答。
- **意图记录是「落痕」，不是「分类」**。存的是**原文 + 时间 + 说话人 + 管家当时的理解**，
  **不存「意图类型」字段**——一旦有类型字段，实现就会退回成分类器。
- **意图记录不是独立表**（回应待定项）：它就是 `project_memory` 里的一类事件，
  类型 `utterance`。**理由**：意图的生命周期与记忆一样长，没必要为它单开一张要单独清理的表。

**为什么这是对的方向**：

> 意图是**开放集合**，分类是**封闭集合**。用封闭的东西去接开放的东西，永远差一截。
> 而 skill + 大模型恰好反过来：**能力边界由我们定（哪些 skill 存在），判断顺序交给模型**。
> 这也是 `AGENTS.md` 约束 3 对 agent 的一贯态度——**我们提供通道，不替它决定怎么用**。

### 2.2 建派任务 / Dispatch

把意图拆成任务：

- 写清 `title` / `intent_ref` / `done_when`（做到什么算完）/ `base_commit`。
- 给出**任务级约束**（`allowed_devices` / `allowed_agents` / `required_capabilities`），
  然后交给调度器。
- **`done_when` 必须可判定**。「优化一下性能」不是 `done_when`；
  「构建时间降到 60s 内，且 `cargo test` 全绿」是。
- 拆不出来就说拆不出来——模糊的意图应该停在这里，不该变成一个模糊的任务去污染看板。

#### 2.2.0 `done_when` 的形状：判定码 + 人话描述（用户已裁定 2026-11-01）

```jsonc
{
  "done_when": {
    "criteria": [
      { "kind": "command", "run": "cargo test", "expect": { "exit_code": 0 } },
      { "kind": "command", "run": "cargo build --release", "expect": { "exit_code": 0, "max_seconds": 60 } }
    ],
    "description": "构建时间降到 60s 内，且测试全绿"
  }
}
```

- **`criteria` 是机器可判定的**（命令 + 期望退出码 / 阈值）。**判定结果确定，不依赖模型**。
  这是「待验收」列能真正工作的前提——**没有判定码，验收就只能是「你自己看看」**。
- **`description` 是写给人看的**。人和管家读它，但它**不参与判定**。
- **两者至少有一个**：
  - 只有 `criteria` → 可自动判绿，人只做最后点头。
  - 只有 `description` → **只能人判**，看板必须明确标「**此任务需人工验收**」，
    不能让用户以为有个自动跑着的判定。
- **`criteria` 至少一条**是自动派活的前提：管家想自动判绿，就必须给出可执行的判定码。

> **为什么不许纯自然语言**：自然语言判定必须经过模型，模型判定**不可复现**——
> 同一个 diff 今天判绿明天判红，验收就失去了意义。而验收是本产品唯一的价值锚点。

### 2.2.1 执行中改需求 / Changing requirements mid-flight

**这是最容易被做错的一格。** 用户对正在跑的任务说了一句新话，管家必须分清是**哪一种改**——
**不是「重新分配 vs 通知 agent」二选一**，判据是「原来的 `done_when` 还成不成立」：

| # | 改的是什么 | 判据 | 管家动作 |
|---|---|---|---|
| ① | **目标不变，做法要换**（「别用 A 方案了，换 B」） | `done_when` **仍然成立** | **通知当前 agent 调整**：ACP `session/cancel` → 发新 prompt，**保留会话上下文**，不重派 |
| ② | **目标变了**（「不要做登录了，改做权限」） | `done_when` **不再成立** | **supersede**：当前任务 → `failed`（`failure_kind = superseded`）+ 新建任务，写明 `superseded_task` 指向旧任务 |
| ③ | **只是加约束**（「注意别动 `src/legacy/`」） | `done_when` 成立，但产生了长期规则 | **通知当前 agent** + **写进 `project_memory`**（否则下一个任务还会踩） |

```text
新话说完，原来的 done_when 还能原样用吗？
  能    → ① 或 ③：通知当前 agent，不重派
  不能  → ②：supersede + 新建任务
  拿不准 → 反问一句「是换个做法，还是目标变了？」
```

**为什么②不能硬塞给当前 agent**：那等于让一个 agent 追移动的靶子，最后它交出来的东西
**看板显示「完成」但你要的不是它**——「静默做错」比报错危险得多。

**为什么①不能改成重新派任务**：任务已有现场（读过哪些文件、试过什么、为什么放弃 A），
**丢掉现场比重新跑更贵**。

**②时旧任务的产出不删**：它可能还有用（那部分代码你还想留着），只是不再追它的 `done_when`。

#### 打断的三条硬规则

- **打断不是杀进程**。走 `session/cancel` 再发新 prompt，保留上下文；直接杀 Execution 会丢现场。
- **打断必须留痕**。Execution 上记一条 `interrupted_by_intent` + 那句原话。
  否则三个月后看这张卡，没人知道它为什么中途换了方向。
- **打断有上限**。同一 Execution 被打断 **2 次以上** → 判定「这个任务定义不清」→
  **停下来问人**，不再把话往里灌。**反复微调一个任务，通常是任务本身没想清楚。**

> ① 的真实风险：agent 可能**部分接受**——嘴里答应，然后在旧上下文里打转。
> 所以打断后必须盯它接下来的动作对不对；不对就**升级成 ②（supersede）**，
> 而不是继续往里追加要求。

### 2.2.2 收件箱与决策请求 / Inbox & decision requests

> **收件箱不是通知列表，是「等你做决定的东西」队列。**
> 通知是广播（「任务完成了」，看不看都行）；收件箱是**待办事项**（「这个必须你选，否则卡住」）。
> 混在一起，完成通知会把真正需要决策的事淹没。

**两个区，默认打开「待决策」**：

| 区 | 内容 | 处置 |
|---|---|---|
| **建议派活**（新，见 §2.2.2） | 管家拆好的任务草稿，等你点「下发」 | 不处理就一直是草稿，**不进看板** |
| **待决策**（默认） | 需要你选一个的事 | 不处理就一直是待决策，相关执行标 `waiting_for_user` |
| **动态** | 完成 / 失败 / 进度提醒 | 可批量已读，**无阻塞** |

#### 三条通路，别混

| 来源 | 走哪 | 能不能经 Hub |
|---|---|---|
| 设备上报的事实（状态、失败原因、磁盘告警） | 控制连接 + 心跳 | 可以，进「动态」 |
| **agent 的权限确认**（能不能执行这条命令） | **只在本机** | **绝不能** |
| **agent 的业务决策**（用 Redis 还是 SQLite） | 控制连接 → Hub → 收件箱 | 可以，进「待决策」 |
| 管家自己的待决事项 | 直接进收件箱 | 可以，进「待决策」 |

> **为什么 agent 的权限确认绝不能经 Hub 中转**：那等于把 Hub 变成设备的**远程控制面**——
> 攻击者拿到 Hub 就能对设备说「用户已批准执行这条命令」。
> `AGENTS.md` 约束 1「Hub 不需要任何到设备的入站访问」的意义就在这里，不是为了省端口。
>
> 界线一句话：**安全许可**（能不能执行）只在本机；**业务决策**（该怎么做）可以进 Hub。

#### 建议派活草稿箱（新）

**管家拆出来的任务不直接进看板，先进这里等你点「下发」。**

理由：**管家理解错了意图就直接派活，会污染看板**——而看板是这个产品的真身，
被污染一次就失去可信度。草稿箱把管家从「执行者」降级为「初审者」，这是对的定位。

```text
「按你刚才说的话，我打算拆成 2 个任务：
  ① 把构建时间降到 60s 内   → device-b / opencode   预计 20 分钟
  ② 给 build.rs 补缓存    → device-a / claude-code 预计 15 分钟
  都只需要 cargo test 全绿（可自动判）
  → [ 全部下发 ] [ 逐个确认 ] [ 改一下 ] [ 都不要 ]」
```

- **草稿不是任务**，不进看板、不占调度、不产生 `Task` 记录（记为 `task.draft`，
  不进六列）。**点「下发」才变成 `pending`。**
- **可以设置「信任模式」**：某个项目攒够一定次数的「草稿被无修改下发」后，
  允许该项目跳过草稿箱直接进看板。**默认关闭**，且**升信任模式必须由人操作**——
  与 `PRODUCT.md` §4.5 合并权的档位是同一套思路（人给规则，不给管家自我扩权的口子）。
- **「改一下」是主要路径**：多数时候用户只是想改一个约束或一个 `done_when`，
  不是全盘否定。**必须能就地改，不能「删了重建」。**

#### 决策请求的形态

```text
{ kind: "decision_required",
  execution_id, question,
  options: [{ id, label, detail }],
  ttl_seconds, default_option_id | null }
```

四条硬规则：

1. **必须带 TTL**。人在睡觉，执行不能无限等。超时 → 执行标 `interrupted`（**不是 `failed`**——
   它没做错，是在等人）。
2. **必须能降级**。超时后按预设处理：选默认方案继续 / 中止。**不能无声卡死。**
3. **答案必须留痕**：谁答的、什么时候、选了哪个、是否超时。否则事后没人知道为什么走这条路。
4. **同一问题的答案可复用**：「以后都别问我这个」→ 写进 `project_memory`，
   下次直接按答案走（这正是 §3.1 的 `preference`）。

#### 隔离式项目的决策请求

**内容由设备侧裁剪，Hub 只存选项标签与你选择的结果，不存上下文原文。**
这条与「环境声明只报哈希不报内容」是同一条原则。
（注意：这**不**意味着隔离式项目没有对话详情——那个可以看，见
`project-and-snapshot.md` §2.1.1。这里限制的是**贴进决策请求里的代码片段**。）

### 2.3 督进度 / Watch

管家是那个**先开口**的人：

| 触发 | 管家做什么 |
|---|---|
| 任务 `queued` 超过阈值 | 说清「没有合格设备」是哪一层过滤空的 |
| 任务 `running` 超时 | 问设备状态，必要时标注 |
| **用户对 `running` 任务说了新话** | **走 §2.2.1**：按 `done_when` 是否仍成立分三种处置 |
| 任务 `failed(superseded)` | 不重试；确认新任务已建好、`superseded_task` 指对了 |
| 任务 `failed` | 读原因，判断是「换条件重试」还是「该人看一眼」 |
| 任务 `review` 停留过久 | 提醒一次，附上自己的判断与 diff 摘要 |
| 绑定设备离线 / 磁盘超 90% | 说清哪台设备、哪个绑定受影响 |
| **任务被 `disk_exhausted` 中止** | 说清是「预算算少了」还是「磁盘真满了」，并**提议改配额或改任务的磁盘要求**——这是调度该回头修的一层，不是只清理 |
| **所有设备被磁盘硬门槛排除**（`rejected(disk_insufficient)`） | **说清是磁盘不够，不是设备离线**（两者处置完全不同：一个去清，一个去开机） |
| 同一 Execution 被打断 ≥2 次 | 停手，问人「这个任务的定义是不是该改了」 |

**督进度的输出必须进「收件箱」**，不能只活在日志里。见 `PRODUCT.md` §5.4 同一条原则：
**东西要到人面前来，而不是让人去看。**

### 2.4 写总结 / Summarize

任务或一批任务结束后写一份人能读的总结：

```text
做了什么       —— 一段话，不是 diff 复述
为什么这么做   —— 决策与取舍
哪里不对       —— 已知问题、没覆盖到的部分
下一步建议     —— 可选，明显才写
```

- 总结**写进两处记忆**（§3）：事实进库，叙事进 `.afleet/MEMORY.md`。
- **总结不是免责声明**。不能写成「任务已完成，请查看 diff」——那是让人自己去读代码。

## 3. 记忆：两处 / Two memory homes

| | 放哪 | 存什么 | 特征 |
|---|---|---|---|
| **结构化事实** | Hub 库 `project_memory` | 约定、决策、偏好、待办钩子 | 可查询、可过滤、可程序读 |
| **叙事记忆** | 项目仓库 `.afleet/MEMORY.md` | 「我们为什么这么改」这类长文 | **随 git 走**，用户可编辑，不锁死 |

### 3.1 为什么必须两处

- **全放库里** = 项目知识锁死在这个产品里。产品一停、库一丢，知识就没了。
  而这些知识**是用户的资产**，不该成为厂商的护城河。
- **全放仓库里** = 没法查询。管家的「回忆」会退化成全文检索，
  「上次我们决定不用 X」这种结构化事实就查不出来。

所以：**可查询的归库，可迁移的归 git。** 两处并存是刻意的，不是没想清楚。

### 3.2 `project_memory` 的形状（草案）

| 列 | 说明 |
|---|---|
| `project_id` | 归属项目 |
| `kind` | `convention` / `decision` / `preference` / `hook` |
| `key` | 短标识，如 `test.command` |
| `value` | 文本 |
| `source_task_id` | 哪次任务学来的（可空） |
| `created_at` / `updated_at` | — |

- **`kind` 有限枚举**，不是自由标签。自由标签会退化成「什么都往里塞」。
- **`hook`** 是给用户的钩子：还没做但别忘了的事。管家督进度时会读它。

### 3.3 `.afleet/MEMORY.md` 的规则

- 它是项目仓库里的**普通文件**，`git` 管理，用户可以手动改。
  **管家下次读到的就是改后的版本。这是特性，不是后门。**
- 追加为主，管家**不删用户写的内容**。要修正就在下面写一段更正并注明日期。
- 上限：单文件超过阈值（如 200 KB）时，管家提示归档，**不自动截断**——
  截断等于静默丢知识。

> `.afleet/MEMORY.md` 在**中心式 / 镜像式**项目里随仓库走，管家直接可读。
> **隔离式**项目里它仍在设备的仓库中（Hub 没有完整仓库），但**可以按需读取与追加**——
> 走「向设备要一段文件内容」这条路，与拉取 diff 是同一条通路
> （`project-and-snapshot.md` §2.1.1：Hub 按需拉取、不长期存档）。
> **不等于放弃叙事记忆**：隔离式项目的管家照样能读写它，只是**每一次都要走设备**，
> 因此不做高频轮询，只在需要时读一次。

## 4. 与调度器的接口

```text
butler.dispatch(task)
  → scheduler.route(task, project)        // scheduling.md
  → { device, agent } | { rejected, reason }
```

- 管家只提交 `task`，**不提交「我建议哪台」**。建议会被误当成约束。
- 调度器返回 `rejected` 时，**`reason` 必须说清是哪一层过滤空的**
  （任务级 allowed_* / 项目级隔离 / 无在线设备）。管家据此决定：
  放宽约束（需人确认）、换条件重试、还是停回待办。

| 情形 | 管家动作 |
|---|---|
| `allowed_devices` 全离线 | 停回待办 + 通知「等设备上线」 |
| `required_capabilities` 无设备满足 | 停回待办 + 说清缺哪项能力 |
| 项目隔离策略排除全部候选 | 停回待办 + 说清隔离策略限制 |
| 选中设备磁盘超配额 | 换下一台；全超了 → 停回待办 + 通知 |

**任何情形都不降级凑数。** 「没设备能跑就随便找一台试试」是本产品要明确避免的失败方式。

---

## 5. 生命周期 / Lifecycle

| 事件 | 管家 |
|---|---|
| 项目创建 | **不自动创建管家**。用户显式「启用管家」才建——自动创建会让每个项目都多一个会说话的实体 |
| 项目删除 | 管家随之失效；`project_memory` 随项目删除（`.afleet/MEMORY.md` 在仓库里，用户自己处置） |
| 绑定新增 / 移除 | 不重建管家；管家只知道「这个项目现在有几台设备能跑」 |
| Hub 重启 | 管家状态全在库里，不丢 |
| 记忆冲突（用户手改了 `MEMORY.md`） | 以文件为准，库里的对应事实标记 `stale`，**不自动覆盖用户** |
