# 任务连贯性 / Task Continuity

> 问题：同一个任务在多设备、多节点之间流转时，状态、上下文、执行进度如何保持一致、
> 不断裂、可续跑？

**第一版不实现任务系统**（见 PRODUCT.md §3.2），本文先钉死模型，避免后期返工。
第一版做到「会话 / 节点级可恢复」；完整的跨节点任务连贯性在任务系统里程碑实现。

---

## 1. 核心原则：状态外置

> **任务的 transcript、工具调用轨迹、工作区快照引用都存 Hub（single source of truth）；
> 节点只持有「当前执行所需的上下文切片」。节点掉线，任务状态不丢。**

这决定了任务连续性的全部设计：

- 任务 = Hub 侧持久化的**状态机 + 事件日志**，不是节点内存里的临时状态。
- 节点是无状态的执行器（对任务而言）；节点重启 / 换设备不影响任务本身的存在。

---

## 2. 状态与上下文 / State & context

- **状态**：任务状态机（pending / running / paused / done / failed）+ 事件日志（append-only）。
- **上下文**：随任务推进累积的上下文切片（transcript、工具结果、产物引用）存在 Hub。
  执行某一步时，只把该步所需的上下文切片下发给节点。
- **工作区 / 产物定位**：跨节点续跑所需的文件与产物，全部经 **Hub 的内容寻址仓库**
  按内容哈希取得（见 `workspace-and-sync.md`），不依赖「上一台机器还在」。
  **不做设备间 P2P 直传**——那会让 Hub 失去唯一真相源的地位。

---

## 3. 断点可恢复 / Checkpoint & resume

- 节点执行带**检查点（checkpoint）**：每完成一个可验证步骤，落一个检查点。
- 节点掉线 / 重启 / 换设备后，从**最后一个成功检查点续跑**，不重做已成功的步骤。
- 检查点与事件日志同源（append-only），既是续跑依据也是审计依据。

---

## 4. 对话恢复走 ACP

- agent 会话恢复走 **ACP `session/load`**，不自建上下文重建。
- Hub 只存 `acp_session_id` + 归属节点；恢复时校验会话仍在该节点，否则标记为需重建。

### 4.1 「节点级可恢复」的确切含义（别误读成跨节点恢复）

- **能恢复**：同一节点上的 ACP 会话重连后，用 `session/load` 取回上下文。
- **不能恢复**：节点已下线 / 换了设备时，原 ACP 会话不存在，标记为「需重建」。
- **第一版的可恢复上限就是节点级**。跨节点续跑要等任务系统（M8）+ 工作区快照
  真正落到 CAS 上，那是靠「从 Hub 重放轨迹 + 用快照重建工作区」，不是靠 ACP。

### 4.2 断线重连与通道重建

连接断开**不等于**会话结束——工作区句柄与 ACP 会话在节点侧仍然存活：

```text
WS 断开 → Hub 标记 node offline，会话仍在
WS 重连 → 同一 node_id + key_fingerprint 认证通过
        → Hub 下发「你有哪些活跃会话 + 各自的工作区」
        → 节点确认 → Hub 按 (node_id, path) 重建 terminal/files/git 通道
        → 缓冲区补发（WS 层序列号，丢了就告知客户端「有 N 条已丢」）
```

PTY 缓冲区与 git 状态在重连后**不复位**：它们在节点进程里活着，只是通道重新接上。
真正的「会话结束」是用户显式关闭，或节点进程退出。

---

## 5. 轨迹即续跑审计源

- 所有动作写入 dsh 式 append-only 轨迹（见 `session-and-trajectory.md`）。
- 轨迹既驱动 Web 回放，也是断点续跑时「已完成到哪一步」的权威依据。

---

## 6. 任务分发与连贯性

Hub 新建一个任务 → 路由到某台 node → 在该 node 上由 agent 会话执行（约束 8：Hub 编排的是
「任务 → node」这一步，不编排 agent 运行时内部的父子 agent）。任务连贯性与任务执行共用同一模型：
任务状态在 Hub，子任务是该任务下可独立执行、可独立续跑的单元；
agent 的每个动作（含它自己 spawn 的子会话里的动作）同样进轨迹，归属到具体子任务与节点。

### 6.1 子任务的工作区（与分发同步同构）

每个子任务 = **独立工作区 + 独立 git 分支**，避免并行时互相踩：

```text
主任务 (node=X, workspace=/w/main, branch=main)
  ├─ 子任务 A → (node=X, workspace=/w/main/wt/task-a, branch=task/a)
  ├─ 子任务 B → (node=Y, workspace=/w/task-b,      branch=task/b)
  └─ 合并 → 主 agent 在主工作区合并 task/* 分支，不是文件同步器
```

> 子任务 A 在 node X、子任务 B 在 node Y，正是「Hub 新建任务 → 分发到不同 node」的体现。
> agent 运行时若在 B 里再 spawn 子 agent，那是节点内部行为，Hub 只观测轨迹。

**子任务拿什么内容？** 分发时在 UI 上让用户确认，三选一：

| 模式 | 内容 | 何时用 |
|---|---|---|
| **`HEAD`** | 主工作区当前 commit | 默认；最轻，节点自己去 origin 拉 |
| **`HEAD` + 工作区** | 当前 commit + 主工作区的未提交改动 | 需要带上正在改的东西 |
| **`snapshot`** | CAS 里的完整树快照 | 项目不是 git，或明确要一个干净副本 |

- git 项目：用 worktree 共享 object store，不复制目录。
- **非 git 项目**：只有 `snapshot` 可用，每个子任务一个独立目录（无 object store 可共享），
  冲突交给主 agent 按轨迹人工/agent 裁决，不做自动三方合并。
- 产物按 `task_id` 归档（见 `workspace-and-sync.md`），跨设备续跑时从 Hub 取。
