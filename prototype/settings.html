AgentFleet 的合并权

项目级设置 · 默认档 0 · 按项目改在项目设置

管家能不能自己合主干，这件事在没用过之前答不了，所以做成三档。 档位是项目级的：不同项目该有不同答案。升档只能你来操作，管家不能自己申请升档。

档管家能做什么适合什么时候
档 0 当前 只能你或预设规则合并。管家能给判断、能推你一把，合主干要你点头 起步阶段，还没建立信任
档 1 管家可以合并，但每次都写进总结并通知你 用过一段时间，想省点操作
档 2 管家可以合并，只通知，不写总结 已经信任，只要知道发生过
为什么默认最保守 合主干是唯一会污染主干的动作。其他所有错误都还能退回到某一次执行， 只有合错了会变成历史里的一行。所以默认不给这个权力。

不管哪一档，合并都要留痕：谁合的、什么时候、把哪个分支合到了哪。

决策请求超时之后怎么处理

按「做错了能不能退回来」区分
请求类型超时默认为什么
业务决策（用 Redis 还是 SQLite） 按标注的默认项继续 做错了下一步还能改回来，让执行继续比停住更有价值。没标默认项就中止
磁盘清理确认 保持中止，不自动清理 删了就没了。不可逆操作不该有「超时默认执行」

两种情况都要留痕（「超时未答，按默认继续」/「超时未答，保持中止」）， 收件箱里那条也不会消失——你回来还看得见它发生过什么。

磁盘

配额决定允许多大，调度决定现在跑不跑得动，清理决定跑完怎么收回
超过多少就不再往这台派新任务
%
磁盘满了不是性能问题，是任务会静默失败的问题，所以它参与派活前的过滤
默认清理策略 绑定项目时可以逐个改
依赖目录永远不搬 node_modules 这类目录按 lockfile 在本地重建，不在设备间搬运。 x86-64 和 aarch64 装出来的不是同一份东西，根本不存在「同一份依赖」可以搬。 复用缓存按 lockfile 哈希命中，产物随工作树一起清。

通知出口

站内收件箱 邮件 IM 机器人
配置通知出口 看 IM 里长什么样 外部来源
外部 issue 只做单向 导入会把外部 issue 变成这里的一条任务，之后任务的真身留在 Hub；导出是把结论回写成一条评论。 不做双向同步：两边都是真相，就得每次冲突都选一边为准，另一边看到的就是假数据。

外观

只影响这台设备，不同步到别的机器
配色方案
跟随系统的明暗设置 打开后不再用上面选的那套，而是按系统自动在冷调 / 暖调里挑
为什么只存在这台设备上 配色是看的人的事，不是项目的事。在笔记本上换成暖色，不该把同伴的屏幕也一起改掉。 所以这条存浏览器本地，不走 Hub，也不占一次同步。

语言

影响界面文字、时间和日期格式
灰色的不是「即将推出」，是现在就切不了
这一版只有中文，是实话不是偷懒 AgentFleet 的整套词都是中文语境里定的：管家、看板、待验收、合并权、隔离式。 这些词翻成英文会同时丢掉字面和含义，而术语一旦不一致，同一件事在不同页面就会被当成两件事。 所以先只做中文，等术语表稳定了再加别的语言 —— 而不是先摆个开关出来。
时间格式
跟着语言走。中文下是「今天 10:18」「昨天 18:30」，不用 2025-11-03 10:18:04 这种
报告里的时间
统一按你所在设备的时区显示，库里一律存 UTC。设备跨时区时，输出里的时间也按那个设备换算
哪些东西不跟语言变
分支名、.afleet/ 目录名、任务编号、commit message —— 这些是数据不是文案，翻译了就对不上
语言是账号级，不是设备级 和上面的配色相反：配色存本地，语言跟着账号走。 因为语言决定你怎么读那些任务的结论，换台机器还得是同一个语言。

哪些东西删不掉

对象能不能删能做什么
项目不能归档。归档后不出现在列表里、不派新任务，历史和总结全留着，随时能取消归档
有历史执行记录的设备不能归档，或先把项目转到别的设备
没有历史执行记录的设备可以直接删掉

这些设置要不要改

管家可以解释，但升档、删设备这类事只能你做
