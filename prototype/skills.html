技能与 MCP

3 个凭据 2 个 MCP server 全局设置 新增凭据
为什么不让 agent 直接连 直接放开等于给所有 agent 开一条统一的提权通道，而且权限由我们替它维护。 所以改成两条路：技能（任务级显式授予，没声明就没有）和 MCP（设备上起一个标准 server，任何支持 MCP 的 agent 都能连）。 一句话：我们提供通道，但不替 agent 决定能不能用 —— 能不能用由人给的任务声明决定。

三条写死的边界

不是策略，是这套东西能成立的前提
① 凭据不进 agent 的上下文 agent 说「用 db-prod 跑这条 SQL」， 凭据由设备侧注入，agent 从头到尾看不见连接串和密码。 这正是 MCP 相比「把连接串塞进 prompt」的核心价值 —— 塞进 prompt 就等于把密码写进了会被记录、会被摘要、会被发到模型服务商的地方。
② 每一次连接与操作都进轨迹 谁、什么时候、连了什么、做了什么 —— 全部记进会话轨迹，和聊天记录一样可复盘。 所以下面每一个凭据都能点开看「谁用过它」，不需要另开一套审计日志。
③ 隔离式项目下，这些操作仍然不出设备 技能和 MCP 本来就是设备侧拨号。设备去连内网数据库， 流量不经过 Hub、不经过浏览器 —— 和隔离式「代码不出设备」是同一件事。

凭据内容在任何页面上都不显示，包括这一页 这一页能看的是「有个叫 db-prod 的东西、连什么、谁用过」。 密码和私钥写进去就不再读得出来，连管理员也一样。 要换只能「轮换」—— 输入一份新的覆盖旧的，旧的立即作废并记一条轨迹。 能读出来的凭据等于能被复制走，那就不是凭据了。

授予：任务可以连什么

任务没声明，就没有这个能力

授予是写在任务上的，不是写在 agent 上的。 同一个 agent，跑这个任务能连 db-prod， 跑另一个任务就摸不到 —— 因为另一个任务没声明。 这和 allowed_devices、required_capabilities 是同一套机制，不是新发明的一套权限系统。

任务被授予在哪跑状态
#1039 会话缓存选型 db-prod 技能 device-a 运行中
#1041 生成月度报告 db-prod 技能 device-a 已结束
#1044 打包并上传 build-host-ssh 技能 device-c 已结束
授予跟着任务走，任务结束就失效 任务结束后，那条授予不再能连任何东西 —— 不需要手工回收。 「已结束」那两行的记录留着重看用，不是还活着。 这也是为什么不做「永久授予某个 agent」：签出去就收不回来的权限，不是权限。

和「Agent」页是什么关系

一个说原则，一个管东西
你想做什么去哪为什么
搞清楚「为什么不让 agent 直接连数据库」 Agent 页 那边是三种暴露方式的对照表，讲原则
加一个数据库凭据、看谁用过 这一页 凭据和授予是「东西」，得有一处管得起来
给某个任务开一个连接 任务详情 · 约束区 授予写在任务上，不在这一页批量开
看某次连接具体做了什么 执行复盘 连接和操作都进了轨迹，复盘里能逐条看输入输出

这一页刻意不做的事

设备级「资源管理台」（把每个连接做成可浏览的对象树） 不做 那是 REX 的多态 Resource 模型，我们只接它的拨号能力，不接它的产品模型
给 agent 一个「永久授权」开关 不做 授权只挂在任务上，任务结束即失效
在页面上查看已存的密码 不做 能读出来就能被复制走
浏览器直连资源（SIP / WS 直通） 不做 与项目主轴无关，只增加攻击面
