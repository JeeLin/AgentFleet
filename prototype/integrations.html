外部 issue 导入

只做单向
为什么不双向 两边都是真相，就得每次冲突都选一边为准，另一边看到的就是假数据。 所以：导入把问题搬进 Hub，导出把结论回写一条评论，任务的真身永远只在 Hub。

一条 issue 进来之后

共四步，第二步是「管家替你看一遍」
  • 第 1 步 拉进来，生成一条任务 标题、正文、报告人作为任务描述落地，标 外部来源， 并记下 source_issue_id 用来回写
  • 第 2 步 管家先看一遍 重复的合并、不清楚的反问、能直接派的直接派。 它替你把「看 issue」这件事做了，你只在它拿不准时报一次
  • 第 3 步 进看板，正常走六态 外部来源的任务和其它任务没有区别 —— 不另开一条流程， 否则两条流程会各自漂移
  • 第 4 步 结论回写一条评论 带 Hub 链接。对方在 issue 那边看得见进展，你不用两边同步； 也不会改原 issue 的状态 —— 一改就成双向了

导入规则

进不来的要说明为什么，不能悄悄丢
按标签和状态筛，不支持表达式
默认不派：外人提的问题不该直接上设备
情况怎么处理
同一条 issue 又更新了 把新内容追加到任务描述，不新建任务、不覆盖你改过的内容
issue 被关了，但任务还没做完 任务照常走。外面关了不等于这里做完了，反过来也一样
拉进来的 issue 缺信息 管家反问报告人，或用 缺信息 标着待在待办
筛选条件外的 issue 不拉，但同步日志里记一条「跳过 N 条」
Token 只存在 Hub，不进 agent 的上下文 拉 issue 和回写评论都由 Hub 自己发请求。agent 看到的是任务内容，看不到 GitHub token —— 所以就算 agent 被提示词攻击，也拿不到能改你仓库的凭据。

回写什么、什么时候回写

回写内容不含代码细节 评论里写「已完成 + Hub 链接」，不贴 diff、不贴日志。 一是外人不该看到内部实现，二是贴出去的东西收不回来。
